# ack_timeout: RETRY_EXC 감지 시간과 ACK 타임아웃 floor

상대가 응답하지 않을 때 RETRY_EXC가 언제 오는지, 재전송 하나하나까지 쪼개서 쟀다.
출발점은 NCCL GIN이 기본값(IB 타임아웃 20)에서 단순 계산 34.4 s가 아니라 57.1–58.4 s 뒤에 오류를 받은 이유다.
이어서 NIC의 ACK 타임아웃 하한(floor)을 끄면 CPU와 GPU 스택에서 감지가 얼마나 빨라지는지 쟀다.

## 무엇을 쟀나

- **장애는 상대 QP 오류 하나.** 응답 쪽(sunny)이 QP를 ERR로 바꾼다.
  요청 쪽(rain)의 쓰기는 ACK를 못 받고 RETRY_EXC 12/0x81로 끝난다.
- **CPU verbs 317회.** IB 타임아웃 T(8–20)와 retry_cnt R(0–7)을 바꿨다.
  - 실행 이력도 바꿨다. 한 프로세스 안 연속 장애, 매번 새 프로세스, 장치 컨텍스트 재생성,
    장애 전 유휴, 장애 전 트래픽.
  - NIC 카운터를 약 0.4 ms마다 읽어 재전송마다 시각을 남겼다.
- **GPU 66회.** NCCL GIN GDAKI(장치 분류기)와 NVSHMEM IBGDA(FT)를 그대로 써서 floor 켬과 끔을 비교했다.
- **조건.** 2026-09-25, rain(요청)과 sunny(응답), ConnectX-6 fw 20.43.4100, RoCE v2 직결, PMTU 4096.
  floor는 rain NIC에서만, 정한 시간 창 안에서만 껐다. 9번 모두 원래 값으로 돌아온 것을 확인했다.

## 결론

- **34.4 s보다 긴 것은 NIC의 재전송 방식 때문이다.** 기본 상태(floor 켬)의 NIC는 "공칭값(4.096 µs × 2^T)으로 R+1번"을 하지 않는다.
  - 먼저 펌웨어 일정에 따른 적응형 재전송이 4–11번 나가며 retry_cnt를 1 쓴다.
  - 이어서 정규 타임아웃 R-1번이 공칭값의 2배 간격으로 온다. T가 16보다 작으면 T=16의 값을 쓴다.
  - T=20, R=7, 연속 장애에서 59.77 s다. 단순 계산 34.4 s의 1.74배다.
- **floor가 켜져 있으면 T를 16 아래로 내려도 소용없다.** 간격이 536.9 ms에 고정된다.
  R=7에서 T=10, 12, 14, 15, 16이 모두 약 3.66 s였다.
- **연속 장애는 미리 맞힐 수 있다.** 측정 전에 적어 둔 예측이 대부분 1.5 ms 안에 맞았고,
  정규 타임아웃 수와 간격은 모두 맞았다.
- **새 프로세스의 첫 장애는 시작점이 이력에 따라 움직인다.** GPU와 NCCL 시험은 모두 이 경우다.
  - 정규 구간(R-1번, 2배 간격, 마지막이 CQE)은 floor 켬 시험 모두에서 0.6 ms 안으로 맞았다.
  - 바뀌는 것은 정규 구간의 시작 시점뿐이다.
  - T=20에서 장애 전 트래픽을 넣으면 57.69–58.24 s다. NCCL GIN 측정(57.1–58.4 s)과 범위가 겹친다.
    GIN 쪽 장애 시각은 추정값이라 시험별 예측이 아니라 범위 일치다.
- **floor를 끄면 적응형 재전송이 사라지고 간격이 공칭값 1배가 된다.** CPU verbs, R=7, T=8에서 9.49 ms다.
- **GPU 스택도 NIC 부분은 CPU와 같다.** floor 끔, T=8에서 장애부터 호스트가 원인 코드를 볼 때까지
  NVSHMEM 13.3 ms, GIN 24.6 ms였다.
  - 실패한 연산을 올린 뒤 오류까지는 9.5 ms, 10.2 ms로 CPU의 9.49 ms와 거의 같다.
  - 나머지는 앱이 다음에 QP를 건드리기까지의 간격이다.
  - floor를 끈 GPU 시험은 모두 RETRY_EXC 12/0x81로 분류됐고, 정리도 정상이었다.

## 결과

| 측정 (R=7) | T=8 | T=14 | T=20 |
|---|--:|--:|--:|
| CPU, floor 켬, 연속 장애 | 안 잼 | 3661.8 ms | 59.77 s |
| CPU, floor 켬, 새 프로세스 | 안 잼 | 3.50–3.76 s | 58.46–58.79 s |
| CPU, floor 끔 | 9.49 ms | 574.9 ms | 37.9 s |
| NVSHMEM IBGDA FT, floor 끔 | 13.3 ms | 585.1 ms | 안 잼 |
| GIN GDAKI, floor 끔 | 24.6 ms | 599.3 ms | 안 잼 |
| NVSHMEM / GIN, floor 켬 | 3.54 / 3.61 s | 3.57 / 3.63 s | 안 잼 |

CPU는 쓰기를 올린 때부터 오류 CQE까지, GPU는 장애부터 호스트가 원인 코드를 볼 때까지다.
값은 중앙값이고, CPU 새 프로세스 행만 10회의 범위다. CPU floor 끔 T=20은 2회다.
GPU floor 끔은 칸마다 10회, floor 켬은 T=8 2회, T=14 1회다.

## 한계와 주의

- **floor 끄기는 NIC function 전체 설정이다.** 우리 QP만이 아니라 그 function의 RC QP 전체에 걸린다.
  - 그 포트에는 NVMe-oF용으로 보이는 커널 QP 18개가 있었다.
  - 새 QP는 T=8, R=7이면 ACK가 약 9.5 ms만 끊겨도 죽는다.
  - 이미 만들어진 QP에 적용되는지는 재지 않았다.
- **GPU에서 거짓 오류가 없었다는 것은 안전의 증거가 아니다.** floor 끔, T=8에서 장애 전 오류는 없었다.
  하지만 유휴 직결 링크에서 짧게 20번 돌린 결과다.
- **연속 장애 모델은 첫 장애를 맞히지 못한다.** 모델 상수(96 ms, 364 ms)는 같은 데이터로 맞춘 값이다.
  - 첫 장애나 이력이 다른 장애는 모델에서 T=14, 17이면 -165–+371 ms, T=20이면 -2.07–-0.71 s 벗어났다.
  - 원인인 펌웨어 상태는 찾지 못했다.
- **설명하지 못한 동작이 있다.** floor 켬에서 R=0인데도 8회 모두 재전송이 7번 나갔다.
  - 예측 검증의 연속 장애 55회 중 3회는 2.6–7.6 ms 일찍 끝났다. 적응형 일정 전체가 당겨졌다.
  - floor 끔의 첫 타임아웃은 재전송 없이 공칭값의 0.51–1.16배에 온다.
- **59.8 s와 9.5 ms는 조건을 붙여 인용해야 한다(2026-10-06 리뷰).**
  - 59.8 s는 한 프로세스 안 연속 장애 값이다. 새 프로세스는 58.46–58.79 s다.
  - 9.5 ms는 T=8, floor 끔 값이다. T=20, floor 끔은 37.9 s다.
- **2026-09-25 리뷰 뒤 고친 것.** GIN 측정값이 모델 범위 안이라는 첫 판 문장은 철회했다(모델은 59.77 s).
  레지스터를 바꾸기 전의 클러스터 잠금 확인에 빈틈이 있어 고쳤다. 고친 뒤로는 floor를 끈 적이 없다.
- **노드 한 쌍, 직결, 스위치 없음.** 펌웨어 문서 없이 카운터로만 본 동작이다. 복구 시간은 재지 않았다.
