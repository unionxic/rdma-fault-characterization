# blind: 실제 application에서 눈가림으로 잰 복구 라이브러리

이 저장소의 복구 라이브러리 셋을 수정하지 않은 application에서 돌렸다. 장애는 다른 에이전트가 무작위로 고르고 봉인했고, 장애를 모르는 평가
에이전트가 출력만 보고 무슨 일이 있었는지 판단했다. 예측 25개는 일정이 생기기 전에 고정했다(태그 `prereg/blind-apps-v1`).

## 무엇을 쟀나

- **application과 라이브러리.** 노드 둘(rain, sunny), rank 둘.
  - PyTorch 2.4.1 DDP로 nanoGPT를 300 반복 학습. NCCL은 다중 요청 복구(NCCL 2.23.4, CPU 프록시 IB 경로).
  - NCCL 2.32.3 공식 예제 GIN ring exchange. GIN 투명 복구 빌드.
  - NVSHMEM 3.8.0 공식 예제 ring-reduce. NVSHMEM 투명 복구 빌드.
  - 예제 코드는 그대로 두었다. MPI가 없어 고유 ID를 나누는 부트스트랩만 바꿨다.
- **장애.** 166회, 셋 중 하나와 장애 없음.
  - 라이브러리 훅으로 QP를 ERR로 옮기기(DDP는 송신, 수신, 알리지 않는 수신), NVSHMEM은 원격 접근 권한 회수도.
  - 프로세스 SIGKILL, 몇 초 SIGSTOP 뒤 SIGCONT, 관리망 TCP 끊김.
  - 종류, 시각, 대상 rank를 장애 에이전트가 `/dev/urandom` 시드로 뽑았다.
- **판정.** 결과 검사는 DDP는 최종 가중치 해시, 예제는 예제 자신의 검증이다. 기계 판정(투명, 거절, 멈춤, 조용한 틀림)과 평가 에이전트의 판단을
  봉인을 연 뒤 예측에 맞춰 채점했고, 다른 에이전트가 원자료에서 다시 셌다.

## 결론

- **DDP의 다중 요청 복구는 수정하지 않은 PyTorch 학습에서 설계대로 동작했다.** QP 오류 26회를 모두 application 모르게 복구했고 가중치 해시가 장애
  없는 실행과 같았다. kill은 0.07 s 안에 오류로 드러났다. 조용히 틀린 결과는 56회 중 0이다.
- **GPU 주도 라이브러리 둘은 양쪽이 기다리는 동안 생긴 장애를 보지 못했다.** CQ를 application이 부르는 `flush`, `quiet` 안에서만 읽고, 신호 대기와
  장벽 대기는 메모리만 돈다. host 쪽에서 장애를 찾는 경로가 없다.
  - GIN: QP 오류 16회 중 14회는 두 rank 모두 아무 줄 없이 멈췄다.
  - NVSHMEM: QP 오류는 14/14 투명했다. 상대의 죽음은 FIN으로 0.5 ms 안에 보고도 판정하지 않아 7/7 멈췄다. 원격 접근 회수는 5–8 ms 안에 거절했지만
    대기가 풀리지 않아 8/8 멈췄다.
  - CPU 프록시 경로(DDP)는 진행 루프를 라이브러리가 쥐어 같은 종류의 장애를 모두 처리했다. 앞 실험들은 매 반복 CQ를 읽는 우리 드라이버로 재서 이
    빈틈이 드러나지 않았다.
- **NVSHMEM의 조용히 틀린 결과 2회는 예제 탓이다.** ring-reduce 예제는 검증 뒤 장벽 없이 다음 크기를 띄운다. 한 PE의 host가 멈춘 동안 상대의 다음
  put이 아직 읽지 않은 결과 버퍼를 덮었다. 라이브러리는 아무 줄도 남기지 않았다.
- **평가 에이전트는 결과를 162/162 맞혔다.** 장애 종류는 141/162였다. 다만 훅 줄을 지운 자리의 빈 줄이 남아 라이브러리 훅 시행의 눈가림이 깨졌다.
  그래서 QP 오류 종류를 맞힌 예측은 근거로 쓰지 않는다.
- **관리망 끊김은 약한 장애였다.** 기존 연결의 포트만 막아 NVSHMEM은 다른 포트로 다시 연결했고, GIN에서는 규칙이 0.5 s도 안 살았다.
- 예측 25개 중 20개가 맞았다.

## 결과

유효 시행 162(장애가 걸리지 않은 NVSHMEM 4회 제외).

| 장애 | DDP(다중 요청 복구) | GIN 예제(GIN 투명 복구) | NVSHMEM 예제(NVSHMEM 투명 복구) |
|---|---|---|---|
| 장애 없음 | 8/8 투명 | 8/8 투명 | 8/8 투명 |
| QP 오류(훅) | 송신 10/10, 수신 10/10 투명, 복구 2.32–3.06 ms | 2/16 투명, 14/16 멈춤 | 14/14 투명, 복구 5.8–15.4 ms |
| 알리지 않은 수신 QP 오류 | 6/6 투명(보내는 쪽이 3.57–3.76 s 뒤 재시도 초과로 알아채고 복구) | | |
| 원격 접근 회수 | | | 8/8 멈춤(5–8 ms 안에 거절) |
| kill | 8/8 거절, 오류 0.056–0.070 s, 종료 0.30–0.38 s | 거절 3, 멈춤 7(죽음 판정은 0.002 s 안) | 7/7 멈춤, 오류 줄 없음 |
| 몇 초 멈춤 | 8/8 투명 | 10/10 투명 | 5/7 투명, 2/7 조용한 틀림(예제의 경합) |
| 관리망 끊김 | 6/6 투명 | 12/12 투명 | 6/6 투명 |

- 투명은 오류 없이 결과가 맞음, 거절은 오류가 드러나 스스로 끝남, 멈춤은 하네스가 끝내거나 시간 제한 오류로 끝남이다. 범위는 그 칸의 모든 시행에
  걸친 범위다.
- 틀린 예측: 알리지 않은 수신 QP 오류는 멈출 것(실제 6/6 투명), GIN QP 오류 투명(2/16), NVSHMEM kill은 3 s 안 오류(0/7), NVSHMEM 멈춤 투명(5/7), GIN과
  NVSHMEM 조용한 틀림 0(2).

## 한계

- 메인 세션과 평가 에이전트가 같은 사용자 권한이라 눈가림은 순서와 sha256 기록으로만 지켰다. 라이브러리 훅 시행은 빈 줄 흔적으로 눈가림이 깨졌고,
  kill은 종료 기록이 드러낸다.
- 장애는 모두 소프트웨어로 만든 QP 상태 변경, 신호, iptables다. 실제 link down과 주소 변경은 재지 않았다.
- 예제의 검증에도 약점이 있다. NVSHMEM 예제는 host 멈춤에 경합하고, GIN 예제는 결과가 틀리면 종료 코드 1이라 조용한 틀림이 나올 수 없다.
- 부트스트랩 대체가 실행기의 "한 rank가 죽으면 함께 끝나기"를 없앴다. kill에서 살아남은 rank의 멈춤 일부는 이 때문일 수 있다.
- 원인 분석은 다시 돌려 확인하지 않았다. 노드 둘, 셀마다 시행 6–16회다.
