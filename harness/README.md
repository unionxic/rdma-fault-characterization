# harness: CPU verbs 장애 측정

RDMA 연결에 장애를 일부러 내서, 요청 쪽이 오류를 얼마나 빨리 알아채는지, 오류 코드로 원인을 구분할 수
있는지, 해당 연결만 다시 살릴 수 있는지를 잰다. GPU 스택 실험의 기준선이다.

## 무엇을 쟀나

- **장애 7가지.** 아래 표 참고.
- **장애마다 30회씩.** 감지 시간, 오류 코드(status와 vendor_err), 복구 시간, 복구 뒤 데이터 검증을 기록했다.
- **조건.** 2026-09-23, rain(요청)과 sunny(응답), ConnectX-6, IB 타임아웃 14, PMTU 4096.

## 결론

- **감지 시간은 장애 종류에 따라 크게 다르다.**
  - 로컬 오류와 응답 쪽 거절은 1 ms 안에 보인다.
  - 응답 없음(상대 QP 오류, 상대 종료)은 재전송을 다 써야 보여서 약 3.7 s가 걸린다.
- **오류 코드만으로는 7가지가 5묶음으로 갈린다.**
  - 로컬 QP 오류와 부분 쓰기는 같은 코드(5/0xf5)다.
  - 상대 QP 오류와 상대 종료도 같은 코드(12/0x81)다.
  - 뒤의 둘은 상대가 살아 있는지 따로 확인해야 갈린다. 그러면 6묶음이 된다.
- **해당 QP만 재설정하면 0.8 ms 안팎에 복구된다.** QP를 새로 만들면 1.8 ms다. 복구 뒤 데이터 검증은 모두 통과했다.
- **부분 쓰기의 도착량은 정확히 셀 수 있다.** 4 MiB 쓰기를 중간에 끊으면, 요청 쪽이 보낸 양과 응답 쪽에 실제로 도착한 양이 130/130회 일치했다.

## 결과

| 장애 | 오류 코드 | 감지 (중앙값) | QP 복구 (중앙값) | 검증 |
|---|---|--:|--:|--:|
| 로컬 QP 오류 | 5 / 0xf5 | 225 µs | 0.79 ms | 30/30 |
| 부분 쓰기 중단 | 5 / 0xf5 | 338 µs | 0.78 ms | 30/30 |
| 원격 잘못된 요청 | 9 / 0x8a | 304 µs | 0.77 ms | 30/30 |
| 원격 접근 오류 | 10 / 0x88 | 323 µs | 0.77 ms | 30/30 |
| 수신 버퍼 없음(RNR) | 13 / 0x87 | 12.79 ms | 0.78 ms | 30/30 |
| 상대 QP 오류 | 12 / 0x81 | 3.749 s | 0.81 ms | 30/30 |
| 상대 프로세스 종료 | 12 / 0x81 | 3.732 s | 해당 없음 | - |

원격 접근 오류와 원격 잘못된 요청은 30회 중 5회가 1.6~3.0 ms로 느리다. 그래서 평균보다 중앙값이 대표값으로 맞다.

## 한계와 주의

- **"상대 프로세스 종료"는 SIGKILL이 아니다.** 상대가 QP를 먼저 정리하고 정상 종료한 경우다. 실제 SIGKILL에서는 270회 중 111회가 다른 코드(0x88)로 나온다(`fingerprint_teardown/`).
- **"상대 QP 오류" 행의 라벨이 틀려 있다.** CSV에서 `auto_recoverable`이 0으로 찍혔는데, 기록 코드의 라벨 버그다. 실제로는 30/30 복구됐다.
- **link down은 재지 않았다.** 링크를 실제로 내리는 시험은 하지 않았다. 공유 링크라서 그렇다.
- **기록하지 않은 신호가 있다.** 응답 쪽 QP 상태와 비동기 이벤트는 이 실험에서 기록하지 않았다. 다음 캠페인에서 잰다(`gpu-initiated/propagation/`).
- **부하가 높으면 복구에 꼬리가 생긴다.** 호스트 부하가 높을 때 복구 시간이 12~17 ms로 튀는 경우가 있었다. 표의 값은 부하가 낮을 때 잰 것이다.
