# boundary: 오판이 시작되는 경계

살아 있지만 잠시 멈춘 상대를 탐지기가 "응답 없음"이나 "복구 불가"로 잘못 판정하는 경계가 정확히 어디인지 쟀다. 이전 실험은
마감의 양쪽에 정지 시간 하나씩만 쟀다. 이번에는 마감 근처의 정지 시간을 촘촘히 바꿔 가며, 경계 위치를 소스의 상수와 측정한 지연으로
미리 예측하고 확인했다.

## 무엇을 쟀나

- **CPU verbs harness, PROBE를 받는 순간 정지:** 1 s 생존 확인 마감 근처에서 정지 길이를 0–1100 ms로 바꿨다.
- **CPU verbs harness, 장애 순간 정지:** 상대 QP 오류와 함께 상대 프로세스를 4.3–5.0 s 멈췄다.
- **GIN 복구:** 복구 요청을 받은 상대를 3 s 핸드셰이크 마감 근처인 2900–3100 ms 동안 멈췄다.

## 결론

- **CPU harness의 1 s 마감은 실제로 1001.6–1027.1 ms에 끝났다.** 커널 타이머가 1 s를 32 ms 격자로 올려 잡기 때문이다. 정지가 990 ms
  이하면 늘 살아 있음, 1040 ms 이상이면 늘 응답 없음이었고, 그 사이는 섞였다.
- **장애 순간부터 멈춘 상대는 정지가 약 4.5–4.8 s를 넘으면 오판된다.** 첫 오류 완료까지 3.5–3.7 s가 걸리고, 그 뒤에 1 s 마감이 붙는다.
- **GIN 복구는 정지 2992 ms 이하면 늘 복구, 2998 ms 이상이면 늘 거절이었다.** 경계 근처에서는 상대가 이미 깨어났는데도 응답이 마감보다
  1–2 ms 늦어 복구 불가로 판정됐다.
- **경계의 위치는 소스의 상수와 측정한 지연으로 미리 맞혔다.** 틀린 두 예측은 경계 위치가 아니라 기준 시각의 정의와 타이머 만료 위치의
  분포에 대한 것이었다.

## 한계

- PROBE를 보내는 시각이 무작위가 아니라 일정한 격자 위를 천천히 움직였다. 그래서 경계 근처에서 어느 비율로 살아 있음이 되는지는 검증하지
  못했다.
- 장애 순간 정지의 시작이 한 번 10.85 ms 늦었고, 원인은 모른다.
- GIN은 복구 v2 하나만, 노드 한 쌍에서만 쟀다.
