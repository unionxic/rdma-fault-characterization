# teardown_order: 죽은 상대의 오류 코드가 갈리는 이유

같은 "상대 프로세스 종료"에서 CPU verbs, NVSHMEM IBGDA, GIN GDAKI는 약 3.7 s 뒤 RETRY_EXC 12/0x81을 받았다.
NCCL GIN proxy는 약 60 ms 뒤 REM_ACCESS 10/0x88을 받았다. CQE만으로 원인을 가른다는 가정이 깨지는지, 왜 갈리는지 쟀다.
처음 가설은 "죽을 때 CUDA fd가 먼저 닫혀 GPU 메모리가 풀리고, 그래서 MR이 무효화된다"였다.

## 무엇을 쟀나

- **상대를 SIGKILL로 죽이는 시험 270회.** 27가지 변형, 변형마다 10회.
  MR 메모리(호스트, GPU peermem, GPU dma-buf), MR과 QP의 등록 순서, CUDA를 여는 순서,
  일반 QP와 DEVX QP, MR 크기, 죽는 쪽 노드를 바꿨다.
- **살아 있는 상대가 하나씩 정리하는 대조군 140회.** 14가지 변형이다. MR 해제 90회, QP 파괴 20회,
  QP를 둔 채 GPU 메모리 해제나 CUDA 컨텍스트 리셋 30회.
- **기록한 것.** 첫 오류 CQE(코드와 시각), 마지막 성공 ACK, 상대 OOB 소켓의 FIN 시각,
  죽는 프로세스의 fd가 풀린 순서, 회수 시각, 일부는 요청 쪽 HW 카운터.
- **조건.** 2026-09-25, smoke 7회 포함 417회. ConnectX-6 fw 20.43.4100, RoCE v2, PMTU 4096,
  IB 타임아웃 14, retry_cnt 7. 보통은 sunny(OFED 25.10)가 죽고 rain(OFED 23.10)이 요청했다. 일부는 반대로 했다.

## 결론

- **이 시스템에서 가설은 틀렸다. fd 순서도 GPU 메모리 해제도 코드를 정하지 않는다.**
  - CUDA를 먼저 열든 나중에 열든 같았다. GPU MR을 QP 뒤에 등록하면 둘 다 0x88, 앞에 등록하면 둘 다 0x81이었다.
  - 죽는 프로세스의 fd는 번호가 큰 것부터 풀렸다. 가설의 오름차순이 아니다.
  - QP를 둔 채 GPU 버퍼를 해제하거나 컨텍스트를 리셋해도 오류가 전혀 없었다.
    NIC는 해제된 메모리에 1.5 s 동안 시험마다 약 74,000번 64 KiB 쓰기를 계속 완료했다.
- **코드는 죽는 프로세스의 QP와 MR 중 무엇이 먼저 사라지느냐에 달려 있다.**
  - QP가 먼저면 아무도 응답하지 않는다. 마지막 ACK 뒤 3.51–3.76 s에 RETRY_EXC 12/0x81이 온다.
  - MR이 먼저이고 QP가 아직 응답하면 NAK가 온다. 마지막 ACK 뒤 0.38–3.51 ms에 REM_ACCESS 10/0x88이다.
  - 살아 있는 상대도 같다. MR 해제는 0x88, QP 파괴는 0x81이었다.
- **등록 순서와 QP 종류가 무엇이 먼저 사라질지 정한다.**
  - 0x88은 MR을 QP보다 나중에 등록한 시험에서만 나왔다. 먼저 등록하면 한 번도 나오지 않았다.
  - sunny(OFED 25.10)는 DEVX QP를 다른 무엇보다 먼저 지운다(소스 확인).
    GPU MR을 나중에 등록해도 DEVX QP는 0x81, 일반 QP는 0x88이었다.
  - rain(OFED 23.10)에는 이 규칙이 없다. 같은 DEVX 상대가 0x88이었다.
- **MR이 먼저여도 0x88은 경쟁의 결과다.** 살아 있는 상대가 MR을 해제하면 응답 쪽은 1.0–2.2 ms(세션별 중앙값) 동안
  ACK도 NAK도 보내지 않았다. 그 사이에 죽는 프로세스가 QP까지 지우면 0x81이 된다고 본다.
  - 호스트 8 MiB MR을 QP 바로 뒤에 등록하면 0x88과 0x81이 섞여 나왔고, 0x88은 sunny에서 더 드물었다.
  - 그 간격을 늘리면(1 GiB MR, 사이에 MR 32개) 모두 0x88이다. GPU peermem MR도 두 노드에서 모두 0x88이었다.
- **0x88만으로는 원인을 못 정한다. 상대 생존 확인이 필요하다.**
  - 살아 있는 상대의 앱 버그와 죽어 가는 상대가 같은 코드를 낸다. NAK 전 침묵 시간도 비슷하다(약 1–2 ms).
  - SIGKILL 시험에서는 OOB 소켓 FIN이 항상 첫 오류 CQE보다 먼저 왔다. 하지만 여유가 0.43 ms까지 작았다.
  - 그래서 "FIN을 이미 봤나" 대신 오류 뒤 최대 1 s 동안 생존을 확인하는 분류 규칙을 제안했다.
    0x81과 0x88 모두에 적용한다.

## 한계와 주의

- **CPU verbs 기준선의 "상대 프로세스 종료"는 SIGKILL이 아니다.** 상대가 QP를 먼저 정리하고 정상 종료한 경우다(소스 확인).
  같은 등록 순서(MR 먼저)로 실제 SIGKILL을 내도 10회 모두 0x81이었다.
- **GPU 스택의 코드는 같은 원리로 설명한 추정이다.**
  - GDAKI와 NVSHMEM IBGDA는 DEVX QP를 쓴다(소스 확인). rain에 죽는 쪽을 둔 GPU 스택 시험은 없다.
  - GIN proxy는 QP를 연결한 뒤에 GPU 신호 버퍼를 등록한다(소스 확인). 실패한 요청이 어느 MR을 쳤는지는 모른다.
  - 같은 조건을 흉내 낸 최소 프로그램은 sunny 40회 모두 39.5–41.7 ms, rain 10회 모두 31.5–33.4 ms에 0x88을 냈다.
  - GIN proxy의 0x88은 6회 측정이다. 경쟁이므로 0x81도 나올 수 있다(2026-10-06 리뷰).
- **GPU 메모리 무효화 경로는 시험하지 않았다.** 이 시스템의 nvidia_peermem은 페이지를 고정하고 무효화 알림을 주지 않는다.
  다른 방식은 모듈 재적재가 필요해서 하지 않았다.
- **"커널이 지우는 순서가 정한다"로 줄이면 과장이다(2026-10-06 리뷰).** 순서는 필요조건이고 결과는 경쟁이다.
  DEVX QP를 먼저 지우는 규칙은 OFED 25.10에만 있다.
- **응답 쪽 커널 로그 집계는 원본이 레포에 없다(2026-10-06 리뷰).** "커널 로그는 죽음 신호가 못 된다"는 판단은 그 집계에 기댄다.
  sunny의 GPU peermem 0x88 kill 40회에서 최대 2줄, rain의 0x88 kill 35회에서 0줄이었다.
- **재지 않은 것.** 죽어 가는 상대가 0x8a 같은 다른 NAK도 낼 수 있다는 것은 추정이다.
  오류 CQE 뒤는 flush 개수만 셌다. 노드 한 쌍과 링크 하나에서만 쟀다.
- **버린 데이터.** 첫 smoke 세션(7회, 417회와 별개)은 요청 쪽 버그로 모든 시험이 바로 끝나서 쓰지 않았다.
