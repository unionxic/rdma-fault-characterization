# nvshmem: NVSHMEM IBGDA 장애 전파

GPU가 직접 RDMA를 거는 NVSHMEM IBGDA에 장애를 내고, 그 장애가 어디까지 보이는지 쟀다.
GPU 쪽 대기가 멈추는지, 실패를 성공으로 알리는지, 오류 코드가 보이는지, 종료가 되는지를 봤다.
CPU verbs 기준선과 같은 장애를 썼다.

## 무엇을 쟀나

- **장애 6가지.** 정상, 로컬 QP 오류, MR 안쪽으로 넘친 쓰기, 잘못된 rkey, 상대 QP 오류, 상대 프로세스 kill.
- **대기 방식 3가지.** 자체 시간 제한 대기, 라이브러리의 blocking 대기(quiet), DeepEP식 대기(완료 카운터만 봄).
  - 조건마다 3회, 정상은 5회. 잘못된 rkey는 시간 제한 대기만. 본 측정(matrix)은 모두 54회.
  - IB 타임아웃 20(기본값) 참고 측정으로 상대 QP 오류를 2회 더 돌렸다(대기 예산 15 s, 40 s).
- **CQ 내용.** 대기가 끝날 때마다 GPU가 CQ 슬롯을 읽었다. CQ 1024칸 전체 스캔과 연속 snapshot(45개)도 떴다.
- **조건.** 2026-09-23, rain(요청)과 sunny(응답), ConnectX-6 RoCE, NVSHMEM devel 7bb2e99, IB 타임아웃 14. 당시 PeerMappingOverride가 없어 NIC 핸들러는 CPU 프록시였다.

## 결론

- **오류 CQE가 한 번도 오지 않았다.** 장애 5가지 모두에서 GPU가 읽은 슬롯은 정상 완료(opcode 0x0)였다.
  - 대기 뒤 읽기 363회와 snapshot 45개가 모두 0x0이었다. CQ 1024칸 전체에도 오류 CQE는 없었다.
  - IB 타임아웃 20에서도 38.1 s까지 없었다.
- **원인은 이후 원인 분석 실험에서 찾았다.** CPU 프록시가 송신 인덱스를 doorbell record의 엉뚱한 칸에 쓴다.
  그래서 QP는 ERR로 가지만 오류 CQE가 생기지 않는다.
- **blocking 대기는 끝없이 멈췄다.** 로컬 QP 오류, 상대 QP 오류, 상대 프로세스 kill에서 quiet가 돌아오지 않아 30 s 감시 타이머가 끝냈다.
  - release 빌드는 오류 CQE를 받아도 무시하게 되어 있다(소스 확인). 그래서 이 대기는 멈추거나 성공만 알릴 수 있다.
- **시간 제한 대기는 멈춤만 알고 원인은 모른다.** 예산이 끝나면 "미완료"를 알렸다. GPU에 보이는 신호는 완료 카운터가 멈춘 것뿐이었다.
- **MR 안쪽으로 넘친 쓰기는 조용한 데이터 오류다.** NIC는 이 쓰기를 정상으로 수행한다. 대기는 모두 성공했고 상대 데이터는 틀렸다. 종료는 정상이었다.
- **장애가 나면 정상 종료하지 못했다.** 본 측정에서 로컬 QP 오류, 잘못된 rkey, 상대 QP 오류, 상대 프로세스 kill을 낸 시행은
  모두 감시 타이머(exit 7)로 끝났다.
  - blocking 9회는 대기에서 멈췄다. 대기를 넘긴 나머지 21회는 종료 과정에서 멈췄다.
  - 종료 과정의 GPU barrier가 오류 난 QP를 지나가지 못해서다(장애 분류와 복구 실험의 설계 문서 9절).

## 결과

| 장애 | 대기 결과 | 상대 데이터 | 오류 CQE | 종료 |
|---|---|---|--:|---|
| 정상 | 15/15 성공 | 일치 | 0/15 | 정상 |
| 로컬 QP 오류 | 시간 제한은 만료, blocking은 멈춤(3/3) | 실패한 put 미도착 | 0/9 | 멈춤 9/9 |
| MR 안 넘침 | 9/9 성공 | 틀림(조용한 성공) | 0/9 | 정상 |
| 잘못된 rkey | 만료 3/3 | 미도착 | 0/3 | 멈춤 3/3 |
| 상대 QP 오류 | 시간 제한은 만료, blocking은 멈춤(3/3) | 실패한 put 미도착 | 0/9 | 멈춤 9/9 |
| 상대 프로세스 kill | 시간 제한은 만료, blocking은 멈춤(3/3) | 죽기 전 데이터는 도착 | 0/9 | 멈춤 9/9 |

- 만료 시각(로컬 QP 오류 1.46 s, 잘못된 rkey 3.85 s, 상대 QP 오류와 상대 프로세스 kill 5.75–5.79 s)은 각 대기에 준 예산이다. 감지 시간이 아니다.
- 종료가 멈춘 30회는 모두 감시 타이머(exit 7)로 끝났다.

## 한계와 주의

- **NIC 핸들러는 CPU 프록시뿐이었다.** GPU 핸들러로 잰 원인 분석 실험과 장애 분류, 복구 실험에서는 오류 CQE가 오고,
  blocking 대기가 실패한 put을 성공으로 알린다.
- **일부 측정은 무효다.** 진단용 감시 스레드가 CPU 프록시를 막아서, 비교 측정(`ab/`)의 로컬 QP 오류, 상대 QP 오류 조건은
  실패한 put이 아예 나가지 않았다.
  - "상대 QP 오류에서 QP가 16 s 동안 RTS"와 "QUERY_QP가 init과 경쟁했다"는 이 인공물이다. 실제로 상대 QP 오류에서 QP는 put 뒤 약 3.6 s에 ERR로 간다.
  - 감시 스레드 없이 돈 본 측정과 잘못된 rkey 조건은 영향이 없다.
- **상세 기록에는 기각된 설명이 남아 있다.** "collapsed CQ가 오류를 숨긴다", "무한 RNR 재시도", "put이 끝나지 않는다",
  "finalize가 깨진 QP를 정리하려다 멈춘다"는 모두 틀렸다.
  - 링 CQ(cc=0)에서 init이 멈춘 결과도 이 인공물과 겹쳤다. 다시 재 보니 멈춤은 사실이었다. 원인은 GPU가 CQ 첫 칸만 읽기 때문이다.
- **숫자 정정.** 정상 완료 읽기는 364회가 아니라 363회다. 본 측정은 51회가 아니라 54회다(잘못된 rkey 포함).
- **호스트 쪽 신호는 없다.** NVSHMEM에는 비동기 이벤트를 읽는 경로가 없다(소스 확인). 이 실험에서도 기록하지 않았다.
- **규모가 작다.** 노드 한 쌍, 펌웨어 하나, RoCE만. 장애 조건은 3회씩이다.
- **DeepEP 자체는 돌리지 않았다.** 이 GPU에서는 돌지 않아서 대기 방식만 흉내 냈다.
