# gin_recovery: GIN GDAKI 장애 복구

`../gin_q4/`의 장치 쪽 오류 분류 위에 복구를 얹었다. 일시적 장애(F1, F3)는 QP 쌍을 양쪽에서 다시 연결해 실패한 연산만
다시 보내고, 복구할 수 없는 장애(F2, F4)는 거절해 오류를 드러낸다. 데이터와 signal을 잃지도 두 번 세지도 않는 것이 목표다.
앱이 복구를 이끄는 방식과, NCCL 안에서 앱 모르게 복구하는 방식(GIN 투명 복구 1단계)을 차례로 쟀다.

## 무엇을 쟀나

- **장애.** F1 로컬 QP 오류, F2 원격 접근 오류, F3 상대 QP 오류(상대 살아 있음), F4 상대 SIGKILL.
  F1과 F3는 한 실행에 5번 내는 칸(x5)도 있다. 그중 1번은 직전 복구 도중에 내서 재전송 자체를 맞힌다.
- **앱이 이끄는 복구.** 2026-09-24 CPU doorbell(v1) 64회와 확인 18회, GPU doorbell(v2) 40회.
  2026-09-25 N30 재측정 210회(v2 190회, CPU doorbell을 강제한 v1 20회).
- **앱 모르게 하는 복구(투명 복구 1단계).** 2026-09-25, GPU doorbell. 복구 코드가 전혀 없는 put, signal, flush 반복 프로그램.
  본 측정 뒤 외부 리뷰 두 차례에 맞춰 추가 측정을 했다.
- **조건.** rain(보내는 쪽)과 sunny(받는 쪽), ConnectX-6 RoCE, IB 타임아웃 14,
  반복마다 256 KiB put과 signal ADD 하나, 한 번에 연산 하나.

## 결론

- **복구 가능한 장애는 잃거나 겹치는 것 없이 복구된다.**
  - v1(CPU doorbell): 장애를 낸 32/32 실행과 강제 d=0 6/6 실행에서 데이터가 bit-exact, signal이 정확했다.
  - v2(GPU doorbell): 장애 실행 18/18. N30: 장애 실행 100/100(Wilson 하한 96.3%), 강제 d=0 30/30.
- **signal ADD는 정확히 한 번 적용된다.** 받는 쪽 signal 값을 보고 ADD가 빠졌을 때만 다시 보낸다.
  09-24 복구 130회(장애 뒤 112회, 강제 18회)에서 signal이 기대값과 모두 맞았다. 재전송이 다시 장애를 맞은 20회도 포함이다.
- **복구는 감지 뒤 약 8 ms 걸린다.**
  - 커널 반환에서 복구 완료까지 v1 8.0–8.2 ms, N30 v2 8.30–8.87 ms(칸별 중앙값).
  - 그중 약 6 ms는 QP 상태 전환 펌웨어 명령이다(한쪽에 QP 4개). 쓰인 쌍만 재설정하면 줄 것으로 본다(시도 안 함).
  - 장애에서 복구까지는 감지 시간이 정한다. F1 약 24 ms(15 ms 반복 간격 포함), 진행 중 연산에 맞으면 9.7 ms.
    F3 약 3.6–3.7 s(RETRY_EXC 감지).
- **복구할 수 없는 장애는 깨끗하게 거절된다.** 09-24 v1에서 F2(REM_ACCESS)는 장애 뒤 3.9–4.1 ms, F4는 RETRY_EXC에
  상대 소켓 종료가 겹쳐 약 3.7 s 뒤 거절했다. N30에서 60/60이 맞는 이유로 거절됐다.
  F3와 F4는 CQE로는 같고, 상대 프로세스가 살아 있는지로만 갈린다.
- **투명 복구 1단계에서는 앱이 장애를 보지 못한다.** 복구 가능한 장애 95/95 실행에서 모든 flush가 성공했고,
  데이터와 signal이 정확했고, 양쪽 호스트의 비동기 오류가 0이었다.
  - 받는 쪽이 실제로 실행한 WQE 수를 NIC에서 읽어 나머지만 다시 보낸다. 진행 중 연산 칸 14/30에서
    ADD가 이미 실행돼 아무것도 다시 보내지 않았다. 쓰기만 실행된 경우는 강제로 만들어 30/30 맞았다.
  - 앱이 보는 것은 느린 반복 하나다. F1 10.4 ms, F3 3.60 s.
  - 대가는 장애가 없을 때의 비용이다. 4 KiB에서 +60%(10.24 → 16.42 µs), 256 KiB에서 +7.6%.

## 한계와 주의

- **한 번에 연산 하나, 보내는 쪽 하나만 쟀다.** 양쪽이 동시에 복구를 시작하거나 여러 스레드가 한 QP에 쓰는 경우는 재지 않았다.
- **설정 범위가 좁다.** ring CQ, 카운터 QP 없음, 랭크 2개, Hopper 아님. collapsed CQ는 복구와 함께 쓰지 않았다.
- **d=0(ADD가 이미 실행된 경우)은 앱이 이끄는 복구에서 강제로만 쟀다.** 실제 장애로는 일어나지 않았다.
- **거절이 깨끗한 것은 드라이버가 받는 쪽 대기를 스스로 풀기 때문이다.** 투명 복구 1단계는 앱 자신의 signal 대기를 풀 수 없어서,
  F2에서 받는 쪽 abort가 돌아오지 않았다(30/30).
- **투명 복구 1단계의 blocking 대기 상한은 앱이 정하지 못한다.** 라이브러리 유지 시간(기본 30 s, 경쟁에서 지면 60 s)만 상한이다.
  재전송 직전 검사와 복구 완료를 알리는 시점 사이의 경쟁도 남아 있다.
- **투명 복구 1단계의 동시 상태 전환 버그를 고친 효과는 추정이다.** 수정 전 1/30 멈춤, 수정 뒤 0/150이다. 통계로는 가를 수 없고 근거는 메커니즘이다.
- **투명 복구 1단계 측정 후반은 펌웨어 명령 슬롯 하나가 샌 상태에서 돌았다.** 그 버그로 09-25 06:45부터 rain NIC의 명령 슬롯 하나가 샜다.
  이 시험의 동시성에서는 측정된 영향이 없었다. 모든 슬롯이 필요한 부하는 확인하지 않았다.
  이 폴더의 N30 재측정(02:11–03:29)은 그 전에 끝났다.
- **F4 blocking 칸은 사실상 timeout 칸이다.** 앱이 이끄는 복구의 드라이버는 F4 확인에 늘 timeout 대기를 썼다.
  진짜 blocking F4는 투명 복구 1단계에서만 쟀다.
- **09-24 v1 실행의 CPU doorbell은 추정이다.** 시각과 v1의 모드 검사로 판단했다. v2와 투명 복구 1단계는 모드를 로그로 남겼다.
