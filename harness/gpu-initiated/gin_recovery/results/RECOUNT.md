## Definitions

- **Round**: one completed Prepare -> handshake (REQ/ACK) -> Commit -> replay cycle on the initiator,
  i.e. one rank-0 `rec ev=` line with `outcome=recovered` or `outcome=replay_failed`. With d = 1 the replay
  is the put + signal ADD; with d = 0 nothing is replayed.
  - **after a fault**: the round's `fault ev=` record carries a classified error (LOCAL_QP_ERR, RETRY_EXC).
  - **forced**: a D0 round (`class=FORCED_TEST`): no fault; recovery forced after a completed operation to
    exercise d = 0. Not "after a detected fault", so always reported separately.
  - **rec** = recovered (replay succeeded, or d = 0); **rf** = replay failed (the replay met a QP in ERR;
    the next round reads V again, or the initiator declines if the replay error is not `ncclRemoteError`).
- **Decline**: a rank-0 `rec ev=` line with `outcome=declined`. **pre-HS**: before any REQ was sent
  (policy: `class_*`, `retry_exc_peer_dead`; guard: `prepare_failed`). **HS**: REQ sent but the handshake or
  commit did not complete (`handshake_timeout`, `peer_nack`, `bad_delta`, `commit_failed`, ...). **after round**:
  Commit done but the replay failed with a non-remote error (`replay_error`); that round is also counted as rf.
- **Run categories**: *recovered* = both ranks completed every iteration, no decline, >= 1 round after a
  fault; *forced-only* = completed, only forced rounds; *no fault* = completed, no rounds, no shot fired;
  *declined* = rank 0 declined, split into *declined as designed* (a pre-HS decline: the policy refuses
  the class or a dead peer, or v1's guard refuses a non-proxy doorbell mode) and *declined after a failed
  round* (negative controls whose broken resync made the replay fail, as predicted); *flag off* =
  `NCCL_GIN_FAULT_RECOVERY` off (classifier only, no recovery); *other* = none of these.
- **Bit-exact**: rank 1 checks every iteration (all 256 KiB equal the pattern and the signal equals
  base + it + 1) and logs `okit` only if both hold. *r1 ops verified* = rank-1 `okit` count / iterations
  configured. *run exact* = all iterations verified, `data_check=ok` and final `signal_exact=1`.
- **V + d = expected**: checked on every responder ACK (`rxrec ... outcome=ack`).
- **Ops recovered (r0)**: rank-0 iterations that completed through a recovery after a fault
  (`okit=N rec=1`); a multi-fault run can need two rounds for one operation.

## What the raw data cannot settle

- **Doorbell mode of the 2026-09-24 CPU-doorbell sets.** Those logs carry no doorbell-mode line and no
  proxy-thread probe (both were added for the GPU-doorbell re-run). Two indirect facts support "CPU-doorbell
  fallback": their rank-0 timestamps span 12:07:56 to 12:47:48, after the second temporary override window
  (12:00-12:06, driver restored; `harness/gpu-initiated/gpu_doorbell/README.md`) and before the override
  became permanent at 13:53; and v1 declines at Prepare in any non-proxy mode (`20260924_gpudb/v1/`:
  "doorbell mode is not CPU proxy"), so every v1 run that completed a round ran with the CPU proxy. Runs
  that never reached Prepare (none, F2, F4, flag off, lat) are covered only by the timestamps.
- **Which build ran which batch** in `20260924/`: the per-trial files record no library or driver md5
  (`20260924_gpudb/` records the bundle name only). The batch-to-build mapping in the README comes from the
  run notes, not from these files.
- **Bit-exactness on rank 1 after an F4 kill or a decline**: rank 1 checks only the iterations it completed
  before it was killed (F4) or released its waiter (declines); "r1 ops verified" counts those. No check exists
  for operations after that point, by design.
- **d = 0 after a real fault**: occurred in 0 of the 209 rounds after a fault in all
  sets above; d = 0 is covered only by the forced D0 rounds, which are not rounds after a detected fault.
- **Operations vs rounds in multi-fault runs**: the logs give rounds and recovered operations (rank-0
  `okit ... rec=1`), not which shot caused which round; that mapping (rec_rows.py) is inferred from timestamps.
