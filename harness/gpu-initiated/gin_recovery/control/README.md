# gin-control: 복원 계층의 제어와 생존 판정을 관리망 TCP에서 데이터망 RDMA로 옮긴다

앞 실험 gin-restore와 gin-mirror는 GPU가 직접 통신하는 NCCL GIN에서 죽은 rank를 예비 프로세스에 되살렸지만, 제어 메시지와 생존 판정은 1 GbE 관리망의 TCP
소켓에 기댔다. 그래서 소켓에 읽지 않은 자료가 남은 죽음(RST)은 약 1 s 늦게 판정됐고, 멈춘 상대(SIGSTOP, GPU 정체)는 커널과 NIC이 대신 답해 아무도 몰랐고,
소켓을 물려받은 자식이 있는 죽음은 FIN이 오지 않았다. 이 실험은 제어 기록을 rank 사이 RC 링으로, 생존 판정을 상대 상태 페이지의 RDMA READ와 21행 판정
표로, 되살리기를 노드마다 띄운 launcher의 펜스(옛 프로세스 종료와 pidfd 확인) 뒤로 옮긴 라이브러리 계층을 만들고, 측정 전에 고정한 예측 33개로 쟀다.
연구의 중심은 GPU가 직접 통신하는 실행에서 어떤 장애 정보가 사라지며, 생존 rank를 되돌리지 않고 실패한 rank를 안전하게 교체하려면 무엇이 필요한가다.

## 무엇을 쟀나

- **바꾼 것(라이브러리).** gin-mirror 계층 위에 제어 계층을 얹었다(호스트 파일 하나, 장치 코드 0줄). 상대마다 100 ms에 READ 1 + GIN 문맥 수로 상태 페이지(호스트
  박동, 문맥과 QP마다의 장치 진행 줄)를 읽고, 관측을 행동으로 바꾸는 판정 표 21행(확인 창 20 ms, 멈춤 문턱 10 s, 분할 막이, 데이터 경로 거부권, 멈춘 상대를
  기다리는 정상 rank는 판정하지 않는 의존 대기자 규칙), 노드마다의 launcher(예비 등록과 띄우기, 활성화 중계, 펜스 집행과 종료 보고), 생존 rank가 확정한 중단
  결정을 상대와 나중 화신에게 전하는 기록. 관리망 소켓은 죽음의 증인(FIN)으로만 남기고 옛 TCP 제어 길은 빌드 스위치로 회귀용으로 남겼다.
- **조건.** 노드 둘, GPU 둘, rank 넷(GPU마다 둘), 4 KiB put 600걸음 또는 학습 모양 2 MiB. 장애는 SIGKILL(증인 켬과 끔, RST), FIN 없는 죽음 셋(fd 자식이 소켓만,
  소켓과 uverbs 매핑, 보고 없음), SIGSTOP 1.5–12 s(펜스 켬과 끔), 박동만 멈춤, helper만 멈춤, GPU 진행 정체(전체, 문맥 1만, 기다리는 정상 rank 있음), 조용한 긴
  계산, 느린 상대, 관리망 8 s 끊김, 기록 QP 오류, REJOIN datagram 잃음, credit 멈춤, 예비 프로세스 없음, 장애 없음. 대조는 같은 소스의 TCP 제어 빌드 셀 하나.
- **잰 것.** 이 실험 셀 28, 시행 180; gin-mirror와 gin-restore 회귀 198; 비용 24; 클러스터 실행 402회(2026-11-18, 약 2 h 48 min). 다른 에이전트가 채점기 코드를
  보지 않고 원자료에서 다시 셌고, 맞지 않은 예측의 원인을 소스와 원자료에서 따로 조사했다. 하드웨어 smoke 여섯과 pilot 여덟이 구현 결함 셋과 채점기 결함을
  잡아 고친 뒤 사전 등록했다.

## 결론

- **제어를 RDMA로 옮겨도 복원은 그대로 되고 TCP 판의 빈틈 넷 가운데 셋이 닫혔다.** RST 죽음이 다른 kill과 같은 20.9–21.9 ms에 판정됐다(TCP 판은 약 1 s). SIGSTOP
  12 s와 GPU 진행 정체는 10.0–10.1 s에 판정되어 펜스 뒤 복원됐다(TCP 판은 아무도 모름). FIN 없는 죽음은 launcher의 종료 보고로 53.8–98.3 ms에, 보고가 없으면 READ
  실패로 3.6–3.8 s에 판정됐다. 옛 화신의 쓰기는 펜스 뒤에만 활성화해 막았고 펜스 뒤 window 검사에서 바뀐 칸은 0이다.
- **복원은 kill 뒤 144–159 ms로 TCP 판(174–221 ms)보다 짧다.** 판정 20.8–22.9 ms, launcher의 SIGKILL → 펜스 확인 70–100 ms, 활성화 뒤 61–63 ms다. 멈춤과 GPU 정체는
  약 10 s 감지 뒤 170–268 ms에 복원됐다.
- **정상 rank는 교체되지 않았다.** 짧은 멈춤 30회, 느린 상대 5회, 조용한 긴 계산 5회, 멈춘 상대를 기다리는 정상 rank 5회, 관리망 끊김 5회, 장애 없음 15회에서
  판정과 거절은 0이고, 안전성 예측 11행이 실패 0으로 맞았다. 관리망으로 간 제어 바이트는 326 시행 모두 0이다.
- **비용은 4 KiB put마다 0.1 % 안이다**(sunny 12.86 대 12.845 µs).
- **살아서 도는 대상의 복원에 결함이 남았다.** 박동만 멈춘 프로세스와 helper만 멈춘 rank 열 시행 가운데 넷이 펜스와 복원 게시까지 되고도 끝나지 못했다. 생존 rank의
  판정이 약 95 ms 벌어져 hold 때 보낸 걸음이 2 차이 났고, 되살린 rank가 기다리는 다음 걸음 메시지가 INJECTED 전의 gate에 묶여 21 s 뒤 fallback했다. 데이터 손상은
  없지만 복원이 끝나지 못한 성능 실패다.
- **예측 33개 가운데 28개가 맞았다.** 틀린 하나는 체크포인트 멈춤 중 kill 셀의 복원이 예측 띠보다 빨랐기 때문(145.6–153.7 ms, 하한 154.5 ms)이고, 재검토 둘은 위
  결함이다. 자료 없음과 자료 부족이 하나씩이다(문서화한 한계와 관문 프로그램의 미구현 모드).

## 한계

- 되살린 rank는 다시 보호받지 않고, 동시 둘 이상의 죽음, 노드 고장, 실제 link down은 다루지 않았다. exec 없는 fork 자식이 uverbs 매핑까지 물려받은 죽음은 READ로
  못 보고 약 10 s 박동 멈춤으로 판정되며, 남은 일이 없는 계산 구간의 GPU 멈춤은 못 본다. 두 rank 고리에서는 먼저 판정된 rank가 fallback 전에 펜스된다.
- 살아서 도는 대상의 복원은 생존 rank 사이 걸음 차가 2 이상이면 끝나지 못한다(위 결함). 사전 등록 뒤라 이 실험에서 고치지 않았고, 고침(INJECTED를 생존 rank마다)과
  검증 셀은 EXPERIMENT.md 19절에 있다.
- hold 끝의 남은 프로세스 검사가 실행기의 snapshot 대기 프로세스를 두 번 잡아 사슬이 멈췄다. 시행 자료에는 영향이 없다.
- 노드 둘, rank 넷, 셀마다 5–10회, 장애는 소프트웨어 주입이다. 비용은 시험 프로그램의 put이고 실제 학습의 단계 시간은 재지 않았다.
