# gin-control 다섯째 하드웨어 smoke (2026-10-23, 채점 안 함): 죽은 rank의 페이지가 왜 답했나

넷째 smoke a4([../20261023_smoke4/SMOKE.md](../20261023_smoke4/SMOKE.md) 셀 4, 요청 1)에서 `NO_EXIT_REPORT`와 FD_HOLDER를 켠 셀의 죽은 rank 3 페이지와 GPU 줄이
10 s 동안 READ에 답해, 판정이 READ 실패 길(11행)이 아니라 호스트 박동 멈춤(15행)으로 났다. 이 smoke는 그 까닭을 가르는 진단이다. 셀은 둘이고 시행마다 n 1, 셀마다 n 2,
시도 넷(한도 여섯)이다. 본 실험과 pilot에 들지 않는다. 표시: `[측정]` 원자료에서 다시 셈, `[소스]` 코드를 읽음, `[추론]` 해석, `[미확인]` 확인 안 함.

- 라이브러리, driver, launcher는 고치지 않았다. 묶음 `gc_smoke4`를 그대로 썼다(두 노드 md5: libnccl `3b901b12…`, `gin_mi` `563cb460…`, `gin_launcher` `3af84d2a…`, smoke4와 같음; meta의 `lib_md5`, `driver_md5`도 같음) `[측정]`.
- 실행: 시도마다 `harness/gpu-initiated/common/cluster_run.sh` 안에서 세션 스크래치의 `agent_gc_smoke4/run_smoke4.sh`(바꾸지 않음) → `impl/test/cells_gc.sh` → `run_gc.sh`(worktree 판).
  실행기 고침 둘(자원 캡처 `RES_CAPTURE=1`, 판정 줄 기다림의 정규식)과 새 pilot 셀은 [../../impl/test/notes_test.md](../../impl/test/notes_test.md) 끝 절.
- 로그는 모두 `sed -E 's/([0-9]{1,3}\.){3}[0-9]{1,3}/<addr>/g'`를 거쳤다(run_gc.sh 안의 가림과 run.out). 이 폴더에 IPv4 꼴 0건, 관리망 주소 0건 `[측정: grep]`.
- 시각은 모두 sunny의 CLOCK_MONOTONIC이다(kill 줄, 캡처 줄, rank 1 줄이 같은 노드). 판정 시간의 생존 rank 셋 범위는 `rows_gc.py`의 `kill_judge_ms_*`(노드 사이는 시계 차로 옮김).
- 정리 스크립트(저장소 밖, 세션 스크래치 `agent_gc_smoke5/`): `capsum.py`(캡처 표), `probesplit.py`(판정 줄 앞뒤 READ 줄 셈). 아래 표는 원자료 `aN/raw/*_rescap.out`, `*_r[0-3].log`에서 다시 뽑았다.

## READ 요약을 판정 앞뒤로 나눔

라이브러리는 READ마다 줄을 내지 않는다. 실패한 READ는 줄(`liveness READ of rank 3: …`)을, 500 ms 안에 CQE가 없는 READ는 시한 줄을 내고, 성공은 끝의 요약 수에만 든다 `[소스: gc_layer_int.diff 4550–4620]`.
요약의 `reads`, `ok`는 상대마다 한 수이고 세대가 바뀌어도 0으로 돌리지 않는다. `gen=`은 마지막 세대만 적는다 `[소스: 3920, 4554–4555, 4160–4172행; 초기화하는 곳 없음(grep)]`. 그래서 줄 차례로는 줄만 나누고, 성공 수는 시간 상한으로 나눴다.

| 시도 | 판정 줄 앞: 시한/실패/의심 | 판정 줄 뒤: 시한/실패 | 요약 peer 3 (생존 셋) | 다른 상대의 `reads` |
|---|---|---|---|---|
| a1 | 1/2/0 (셋 모두) | 1/0 | `reads=67–68 ok=66–67 noresp=1 broken=1 timeout=2` | 125 |
| a2 | 1/2/0 | 1/0 | `reads=69 ok=68 noresp=1 broken=1 timeout=2` | 125 |
| a3 | 0/0/1 | 1/0 | `reads=169 ok=169 timeout=1 gen=1048577` | 189 |
| a4 | 0/0/1 | 1/0 | `reads=168 ok=168 timeout=1 gen=1048577` | 188–189 |

- 판정 줄 뒤의 시한 하나는 복원된 세대에서 났다(복원 뒤 4.7–4.9 s, 네 시도와 smoke4 a4 모두). 까닭은 `[미확인]`.
- (나)에서 kill과 판정 사이에 성공한 페이지 READ 수의 하한(rank 1): 요약 168–169 − 짝 맺기부터 kill까지의 상한(2 236–2 323 ms, 100 ms 주기로 23–24) − 다시 짝 맺기부터 요약까지의 상한
  (6 957–6 966 ms, 70) = **75 이상** `[측정에서 셈; 주기 100 ms, 한 번에 READ 하나라는 가정은 소스]`. 같은 셈이 (가)에서는 음수다(그 사이 READ가 실패함).
  곧 "169/169 ok"는 복원 뒤 세대의 READ만이 아니다. 죽은 프로세스의 MR이 10 s 동안 READ에 성공으로 답했다 `[추론, 위 두 측정에서]`.

## 가설마다

| 가설 | 판정 | 근거 |
|---|---|---|
| H1 자식이 쥔 fd가 uverbs context를 붙잡음 | 기각 | 자식의 fd는 모든 점에서 0–2(`/dev/null`)뿐이고 fork 줄도 `holds 0 fd(s)` `[측정]` |
| H2 fd 없이 물려받은 매핑이나 드라이버 참조가 MR과 QP를 붙잡음 | 지지 | 자식에 `uverbs0` 매핑 18개(rank 3과 같은 수). 자식이 있는 동안 rank 3의 1/2/10/17/50이 kill + 0.56–10.35 s 내내 pid 없이 남고, 자식 SIGKILL 뒤 0.5 s 점에서 사라짐; 자식이 없으면 kill + 0.6 s 점에 이미 없음 `[측정, n 2씩]`. 매핑이 uverbs 파일을 열어 둬 context의 해체가 마지막 매핑이 풀릴 때까지 미뤄진다는 길은 `[추론: 커널 소스는 읽지 않음]`. uverbs 매핑만으로 충분한지, nvidia 매핑(`nvidiactl`, `nvidia0`)도 몫이 있는지는 `[미확인]` |
| H3 요약이 앞뒤 세대를 섞어 "169/169 ok"가 옛 MR의 답을 증명하지 못함 | 기각(섞는 것은 맞음) | 요약 수는 세대를 섞는다 `[소스]`. 그래도 (나)에서 판정 줄 앞 실패 줄과 시한 줄 0, kill과 판정 사이 성공 READ 75 이상 `[측정에서 셈]`, 의심이 `kind=watch`(READ가 멈춘 박동을 읽음)였다. 같은 요약 꼴로 (가)는 실패 줄 둘과 시한 줄 하나를 낸다 `[측정]` |
| H4 자식이 없어도 장치 자원 해체가 느림 | 기각 | (가)에서 rank 3의 몫이 kill + 0.6 s 점(캡처 해상도)에 모두 없음, 프로세스 끝을 본 때가 kill + 104.2–122.5 ms(자식이 있으면 60.4–61.8 ms: 해체가 끝 경로에 든 차이로 봄 `[추론]`) `[측정]` |

- 맺음 `[추론]`: smoke4 a4의 10 s는 FD_HOLDER 자식이 fork(exec 없음)로 물려받은 uverbs 매핑 때문이다. 이 설계로는 FD_HOLDER 셀이 "FIN 없는 죽음 → READ 실패 길"을 잴 수 없고,
  3절 `finless_read_fail`은 `gc4_fdhold_sock_kill3_noreport`에서 참이 될 수 없다. FD_HOLDER를 뺀 (가)에서는 그 예측대로 났다(n 2).
- 실제 쓰임의 뜻 `[추론]`: verbs를 연 뒤 exec 없이 fork한 자식이 살아 있으면, 죽은 프로세스의 QP와 MR은 READ에 계속 답한다. 그때 이 계층에서 죽음을 보는 것은 호스트 박동 멈춤(15행, 약 10 s)뿐이다.

## 가르는 다음 시험 (고치지 않음)

1. **fork 뒤 exec 하는 자식** (라이브러리 고침): `gdakiCtrlFdHoldChild`가 넘겨받은 증인 소켓을 지닌 채 작은 holder 프로그램으로 execve하면 매핑이 모두 풀린다. 예측: (가)처럼 kill + 0.6 s 안에
   rank 3 몫이 사라지고 NORESP 3.5–4.5 s. 이것이 7절이 FD_HOLDER 셀로 재려던 "소켓은 열려 있고 프로세스는 죽음"을 실제로 만든다.
2. **어느 매핑이 붙잡나** (라이브러리 고침): 자식이 uverbs 매핑만, 또는 nvidia 매핑만 munmap하는 두 변형. 또는 NCCL 밖의 작은 verbs 프로그램이 fork 뒤 죽는 시험(이 계층과 무관한 커널 사실인지 확인; 새 도구).
3. `RDMAV_FORK_SAFE`/`ibv_fork_init`이 uverbs 매핑을 자식에게서 빼는지 `[미확인]`(커널 5.13 이후 rdma-core는 fork 지원이 있으면 이것을 안 할 수 있음 `[추론]`). 셀 env만으로 시험 가능.
4. `gc4_fdhold_uverbs_kill3`(uverbs fd도 넘김)의 예측 `fdhold_uverbs_refuse`는 이 결과와 모순되지 않는다: 그 셀은 fd와 매핑 둘 다로 붙잡는다 `[추론]`.
