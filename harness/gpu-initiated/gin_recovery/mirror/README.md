# gin-mirror: 보낸 버퍼를 곧바로 다시 쓰는 application에서도 죽은 rank를 되살린다

앞 실험 gin-restore는 GPU가 직접 통신하는 NCCL GIN에서 죽은 rank 하나를 예비 프로세스에 되살렸지만, 다시 실행할 때 보낸 쪽의 원본 버퍼를 다시 읽었다.
그래서 application은 상대의 다음 체크포인트가 확정될 때까지 보낸 버퍼를 바꾸면 안 됐고, gradient 버퍼처럼 단계마다 다시 쓰는 학습에는 맞지 않았다. 이
실험은 보내는 rank의 NIC이 put의 내용을 받는 rank의 짝(그 rank의 체크포인트를 가진 rank)의 호스트 메모리에 한 번 더 써 두고, 복원이 원본 대신 그 사본을
쓰게 하는 라이브러리 계층(mirror)을 만들고, 측정 전에 고정한 예측 53개로 정확성과 비용을 쟀다.

## 무엇을 쟀나

- **바꾼 것(라이브러리).** gin-restore 계층 위에 mirror 계층을 얹었다. put마다 따로 된 QP로 내용을 짝의 호스트 메모리 영역에 한 번 더 쓰고(GPU 스레드의 복사
  없음), 그 영역을 받는 rank의 체크포인트 간격마다 나눠 확정되면 버리고, 차 가면 다음 체크포인트를 앞당긴다. 그래도 넘치면 그 rank의 보호를 끄고 fail-fast로
  돌아간다. 체크포인트와 사본은 데이터망 RDMA로 옮기고, 예비 프로세스는 체크포인트 뒤의 입력을 단계마다 그 커널 전에 넣는다. 짝이 되살아난 뒤에는 그 짝이
  맡은 rank가 전체 이미지로 보호를 되찾게 하고, 프로세스의 세대(화신) 판정을 한 곳으로 모았다.
- **조건.** 노드 둘, GPU 둘, rank 넷. 4 KiB put을 600단계 보내며 보낸 칸을 put의 local 완료 직후 단계마다 다른 표시 값으로 덮는 workload, 그리고 rank마다
  상대 셋에 단계마다 2 MiB를 보내고 곧바로 덮는 2 000단계의 학습 모양 전송. 장애는 rank 3이나 rank 1의 SIGKILL, 체크포인트 입력 멈춤 중의 kill, 짝 rank 2가
  죽었다 되살아난 뒤 rank 3의 죽음. 대조는 mirror 없이 되살리기와 checksum 표본, 회귀는 앞 실험들의 셀. 비용은 4 KiB, 256 KiB, 2 MiB put 지연과 묶음 대역.
- **잰 것.** 복원과 거절 시행 168회, 회귀 20회, 비용 실행 240회. 다른 에이전트가 채점 코드를 보지 않고 원자료에서 다시 셌고 판정이 모두 같았다. 채점하지 않는
  pilot 여섯이 잡은 구현 결함 넷을 고친 뒤 사전 등록했다.

## 결론

- **보낸 버퍼를 곧바로 다시 써도 죽은 rank를 비트 단위로 되살린다.** 4 KiB 덮어쓰기에서 rank 3 kill 10회, rank 1 kill 5회, 학습 모양에서 무작위 단계의 rank 3
  kill 10회 모두 생존 rank의 대기가 오류 없이 붙잡혔다가 끝났고 모든 rank의 최종 데이터가 장애 없는 실행과 비트 단위로 같았다. rank 3 kill에서 다시 실행한
  내용은 모두 짝의 사본에서 왔다(원본 읽기 0). mirror 없이 같은 workload를 되살리면 5회 모두 데이터가 틀렸다.
- **짝이 되살아난 뒤의 둘째 죽음도 되살린다.** 4 KiB와 학습 모양 각 5회에서 rank 3이 되살린 짝에 전체 이미지를 다시 맡겨 보호를 되찾은 뒤, rank 3의 죽음을
  그 짝의 이미지와 사본으로 되살렸다.
- **복원은 약 0.18–0.30 s에 끝났다.** 4 KiB 174–221 ms, 학습 모양 250–298 ms로, 같은 계층에서 mirror를 끈 길(310–403 ms)보다 짧다. 절반 넘게는 죽은 프로세스가
  `/proc`에서 사라지기를 기다리는 시간이다.
- **비용은 NIC 쓰기 하나다.** 4 KiB put 지연이 7.2–8.8 µs(put 하나의 지연보다 작게) 늘고, 2 MiB 지연은 1.86–1.93배, 묶음 대역은 0.55–0.64배가 됐다. 같은
  원본을 NIC이 두 번 읽는 구조와 맞는다.
- **예측 53개 가운데 51개가 맞았다.** 틀린 하나는 체크포인트 멈춤 중 kill이다. 복원 자체는 5회 모두 맞았지만, 시험 장치의 kill 시점이 네 rank가 함께 하는
  체크포인트와 겹쳐 "생존 rank 셋이 모두 멈춤 안에서 죽음을 맞는다"는 장애 위치가 5회 중 1회만 만들어졌다. 나머지 하나는 보고만 한 256 KiB 지연이다.

## 한계

- 되살린 rank는 다시 보호받지 않는다(예비 프로세스를 다시 둘 장치가 없고, rain GPU의 BAR1에 넷째 프로세스가 들지 않는다).
- 예비 프로세스는 죽은 프로세스가 zombie로 보이면 곧바로 활성화돼 복원 시간이 두 덩어리로 갈린다. 체크포인트를 청한 rank가 죽은 상대의 답을 시한까지 기다려
  생존 rank가 2 s 서는 일이 3회 있었고, 소켓이 RST로 닫히면 죽음 판정이 약 1 s 늦다.
- 노드 둘, rank 넷, 셀마다 3–10회이고 장애는 SIGKILL 하나다. 학습 모양은 전송 모양만 흉내 내고 실제 학습의 단계 시간은 재지 않았다.
