**2026-10-06 리뷰 정정**
- `retry_proc_kill`은 SIGKILL이 아니다. 상대가 QP를 먼저 정리하고 정상 종료했고, 요청 쪽은 300 ms 뒤에 썼다. 실제 SIGKILL은 270회 중 111회가 0x88이다(`../../fingerprint_teardown/`).

**2026-10-06 README 점검 때 CQE별 기록으로 다시 센 정정**

Question Q1 of the GPU-initiated fault study (`../DESIGN.md`). NVSHMEM IBGDA polls a
**collapsed CQ**: one CQE slot that the NIC overwrites with every CQE it writes, so the GPU
sees only the CQE the NIC wrote last. This experiment records, on a normal CQ, the full
ordered CQE sequence that a ConnectX-6 (VPI, MT28908) writes after each fault, and from it predicts what
a collapsed slot ends up holding: the root-cause CQE or a flush CQE.

## Why a normal CQ answers the question (an inference, not a measurement)

On a normal CQ every CQE the NIC writes gets its own slot, and `ibv_poll_cq` returns them
in the order they were written. On mlx5 user QPs the flush CQEs are written by the NIC,
not generated by software: their `vendor_err` is a raw firmware syndrome (0xf5/0xf9 here),
not the driver's software-flush constant `MLX5_CQE_SYNDROME_WR_FLUSH_ERR` = 0x05. So the
sequence below is the sequence of CQE writes the NIC performs, and the order in which a
collapsed slot would be overwritten. This rests on one assumption: the NIC writes the same
CQEs in the same order when the CQ is collapsed. A separate experiment reads a real
collapsed CQ from GPU code (Q3); it checks this prediction.

## Answer to Q1

**A collapsed slot ends up holding the root-cause CQE only if the failing WQE is the last
WQE outstanding on the QP. If any WQE is posted behind it, the NIC overwrites the slot with
one flush CQE per trailing WQE, and the slot ends up holding
`WR_FLUSH_ERR (5) / vendor_err 0xf9` for the last posted WQE. The fault's fingerprint is
then gone.** The root-cause CQE stays visible for about 60 µs before the first flush
overwrites it (measured on a normal CQ; the collapsed CQ itself is Q3's measurement).

Evidence: 470 trials and 9,004 CQEs. Every cell of the main matrix and of the
bad-WQE-last run gave the same CQE sequence (status, vendor_err, WQE index) in 5 of 5
trials. In the 64 KiB local_qp_err run, the number of WQEs that completed before the ERR
varied by one (13 or 14). No drain hit its bound, and there were no late, foreign,
duplicate or out-of-order CQEs. Every recovered trial passed verify, and the QP was in ERR
after every trial.

1. **The sequence is always the same.** First come SUCCESS CQEs for the signaled WQEs that
   completed before the fault. Then comes exactly one root-cause CQE, for the failing WQE:
   `REM_ACCESS 10/0x88`, `REM_INV_REQ 9/0x8a`, `RNR_RETRY_EXC 13/0x87`, `RETRY_EXC 12/0x81`
   (both retry causes), or `WR_FLUSH 5/0xf5` for `local_qp_err`, on the WQE at the head of
   the send queue. Then comes one `WR_FLUSH 5/0xf9` CQE for **every** WQE behind it, in WQE
   order. After that nothing arrives (500 ms quiet period plus a late sweep). Every WQE at
   or after the failing one got exactly one CQE.
2. **Selective signaling does not suppress error CQEs.** Unsignaled WQEs that were pending
   behind the root cause each got a flush CQE; for example, all 62 of 62 for N = 64 with the
   bad WQE first. An unsignaled failing WQE still produced its root-cause CQE. Unsignaled WQEs
   that succeeded produced no CQE: none of the 2,057 SUCCESS CQEs came from an unsignaled
   WQE. So with `last` signaling
   the root cause is the first CQE; with `all` signaling, k SUCCESS CQEs come before it.
   For N ≥ 4 the flush count is N − 1 − k (N for local_qp_err, whose root cause is itself
   the first flush), in both signaling modes.
3. **What the slot ends up holding.** In 120 of 120 error trials where the failing WQE was
   the last one (N = 1: 60 trials; bad WQE at k = N − 1: 60 trials), the last CQE is the
   root cause. In 290 of 290 trials with at least one WQE behind the failing one, the last
   CQE is `5/0xf9` at WQE N − 1.
4. **How long the root cause stays visible.** The NIC wrote the first flush CQE 58–66 µs
   after the root-cause CQE (median 59.5 µs, n = 290; one outlier at 223 µs, in the 64 KiB
   local_qp_err run). After that it
   wrote one flush every 9.35 µs (p1–p99 9.24–9.77 µs, n = 6,247). Root cause to last CQE
   is therefore about 59 + 9.35 × (flushes − 1) µs: 78 µs for 3 flushes, 190 µs for 15 and
   640 µs for 63. The spacing is the same for all six faults. The even ~9 µs pace fits
   firmware writing the flushes one at a time (inference).
5. **0xf5 and 0xf9 mean different things.** 0xf5 appears only on the first flush of
   `local_qp_err`, the WQE at the head of the send queue when the host moved the QP to
   ERR. The 64 KiB supplementary run shows this: 13–14 WQEs completed with SUCCESS, the
   first incomplete WQE got 0xf5, and all the rest got 0xf9. Every other flush, whether behind
   that head WQE or behind a remote or transport error, is 0xf9. The harness catalogs
   `local_qp_err` as 5/0xf5 because it records only the first error CQE. After a local
   error with two or more WQEs outstanding, a collapsed slot holds 5/0xf9.
6. **A local error with nothing outstanding writes no CQE at all.** With 4 KiB WQEs
   (N ≤ 64) or 64 KiB WQEs (N ≤ 4), every WQE finished before the ERR took effect
   (`ibv_modify_qp` takes ~217 µs). No error CQE was written, although the QP was in ERR.
   A collapsed slot would still hold the last SUCCESS CQE; only `ibv_query_qp` shows the fault.

**Implications for the GPU side (inference, for Q3/Q4).** In the usual case a batch is in
flight when the fault hits. Device code that reads the collapsed slot afterwards then sees
`5/0xf9` whatever the fault was. The slot says "flushed behind an earlier error" but not
which error, and its `wqe_counter` points at the last posted WQE, not at the failing one. A
device-side classifier can only see the fingerprint if it reads the slot within about 60 µs
of the root-cause write. Otherwise the fingerprint has to come from another source, for
example a CQ with more than one slot, or a host-side check of the QP and the peer.
IBGDA's check (`REQ_ERR` → assert) would still fire on the flush, because a flush CQE is
also an error CQE, but without the cause.

## Method

Requester `cqe_seq_client` on rain (mlx5_1), responder = the harness's `probe_server` on
sunny (mlx5_0), **unchanged** (same source, built into this directory on sunny; the build
step checks that sunny's harness sources are byte-identical to rain's). The client speaks
the harness control protocol over sunny's management IP (TCP port 18591):

```
TRIAL <fault> qp_only -> OK -> GO -> GOACK          (retry_proc_kill: the server exits on GO,
   -> post the batch (one ibv_post_send)               no GOACK; the client waits 300 ms,
      [+ trigger]                                      as probe_client does)
   -> drain the CQ, timestamp every CQE
   -> ibv_query_qp, one late sweep of the CQ
   -> RECOVER qp_only -> RESET/INIT/RTR/RTS on both ends (fresh PSNs) -> RECOK
   -> verify: 4 KiB WRITE + READ-back, byte compare   (no recovery for retry_proc_kill:
                                                       the runner starts a new server per trial)
```

QP and CQ come from the harness core (`../../common/probe.c`): RC, PMTU 4096, `timeout` 14,
`retry_cnt` 7, `rnr_retry` 6, `min_rnr_timer` 12, max_rd_atomic 1, `sq_sig_all = 0`, one
QP on one CQ (depth 1024), no receives posted on the requester, so every CQE in the CQ
belongs to that QP's send queue and the order is unambiguous.

**Batch.** N WQEs, N ∈ {1, 4, 16, 64}, chained and posted with a single `ibv_post_send`
(one doorbell, like a GPU thread that writes a batch and rings once). Every WQE except the
bad one is a valid RDMA WRITE to its own 4 KiB offset. The bad WQE sits at k = 0 ("first")
or k = N/2 ("middle"); for N = 1 only "first" exists. A supplementary run also puts it at
k = N − 1 ("last").

| fault | batch and trigger | root-cause fingerprint (harness catalog) |
|---|---|---|
| `local_qp_err` | N valid WRITEs of **4 MiB** (the harness's `MSG_SIZE`, so they are still outstanding), then the client moves its own QP to ERR | WR_FLUSH 5 / 0xf5 |
| `rem_access` | WQE k = 4 KiB WRITE at remote `addr + buf_size` (past the end of the remote MR) | REM_ACCESS 10 / 0x88 |
| `rem_inv_req` | WQE k = 8-byte fetch-and-add; the responder QP does not enable REMOTE_ATOMIC | REM_INV_REQ 9 / 0x8a |
| `rnr` | WQE k = 64 B SEND; the responder never posts a receive | RNR_RETRY_EXC 13 / 0x87 |
| `retry_server_qp_err` | N valid WRITEs; the server moved its QP to ERR before GOACK | RETRY_EXC 12 / 0x81 |
| `retry_proc_kill` | N valid WRITEs; the server process exited on GO | RETRY_EXC 12 / 0x81 |

(`rnr` also runs k ∈ {first, middle}. That is cheap and shows the same pattern.) `link_down` is
never run: the link carries the user's NVMe-oF storage.

**Signaling.** `all`: every WQE carries `IBV_SEND_SIGNALED`. `last`: only WQE N−1 is
signaled (selective signaling, the way GPU-initiated stacks post). The QP has
`sq_sig_all = 0` in both modes.

**wr_id** = `0xC5E0 << 48 | trial_uid << 16 | wqe_index`. libmlx5 maps each CQE to its
WQE through the CQE's `wqe_counter` (`wr_id = wrid[wqe_counter]`), so `wqe_idx` in the
CSV is the WQE that the NIC reported. A CQE from another trial would be flagged `foreign`.
None were flagged.

**Drain.** Tight `ibv_poll_cq(cq, 1)` loop on a pinned core (CPU 2 on both nodes). Each CQE
is stamped with `CLOCK_MONOTONIC_RAW` right after it is polled, relative to t0 = just before
`ibv_post_send`; for `local_qp_err`, t0 = just before `ibv_modify_qp(ERR)`. The drain ends
when the CQ has been empty for **500 ms** after the last CQE and an error CQE has been seen.
Without an error CQE it ends 10 s after t0 (`drain_end = no_error`; 1 s in the small-WQE
local_qp_err runs). The hard bound is that timeout + 0.5 s + 1 s (`drain_end = bound`;
never hit). Then `ibv_query_qp` records the QP state,
and one more sweep of the CQ looks for late CQEs (`late`, none found). The timestamps are
poll times. Because the poller spins and each poll costs about 0.1 µs, a gap of several µs
between two CQEs is the NIC's spacing, not the poller's.

**Independence.** Recovery is the harness's `qp_only`: coordinated
ERR→RESET→INIT→RTR→RTS on both ends with fresh PSNs. The RESET also makes libmlx5 discard
any CQE of the QP still in the CQ; the drain and late sweep run before it. Every
recovered trial must pass the 4 KiB WRITE+READ verify, otherwise the client aborts.
`retry_proc_kill` starts a fresh server per trial (one client invocation per trial, as
the harness runner does).

**Matrix.** 5 trials per cell. local_qp_err, retry_server_qp_err and retry_proc_kill:
4 N × 2 signaling = 8 cells (40 trials each). rem_access, rem_inv_req and rnr: 4 N × 2
signaling × 2 positions − 2 (N=1 middle) = 14 cells (70 trials each). That makes 330 trials in
the main matrix. The supplementary runs add 140 more (see Results), for 470 in total.

## Results

Run on 2026-09-23 (rain → sunny, ConnectX-6 (VPI, MT28908) fw 20.43.4100, RoCE v2, PMTU 4096; CPU 2
pinned on both nodes; link idle as checked by `cluster_run.sh`). Nine locked runs (a smoke
test, one per fault, and two supplementary runs) held the cluster lock for about 15 minutes
in total, including the 30 s idle-link check at the start of each run.

### Pattern (main matrix, 5 of 5 trials in every cell, both signaling modes)

`a/b@i` = status / vendor_err at WQE index i. "k succ." = the SUCCESS CQEs of the signaled
WQEs before the bad one (only with `all` signaling).

Supplementary runs:
- **Bad WQE last** (`supplast`: rem_access and rem_inv_req, k = N − 1, N ∈ {4, 16, 64}, both
  signaling modes, 60 trials). The sequence is [N−1 succ.] then 10/0x88@N−1 (or 9/0x8a@N−1),
  with 0 flushes. The last CQE is the root cause in 60 of 60 trials.
- **local_qp_err with small WQEs** (`supp4k`, `supp64k`, 80 trials). With 4 KiB WQEs (any N)
  or 64 KiB WQEs (N ≤ 4), every WQE had completed before the ERR took effect: no error
  CQE, QP in ERR (`drain_end = no_error`). With 64 KiB WQEs and N ∈ {16, 64}, 13–14 WQEs
  completed, the next WQE got 5/0xf5, and every later one got 5/0xf9.

Time from t0 to the root-cause CQE (secondary; it does not change the order):
local_qp_err 222–230 µs from the start of `ibv_modify_qp` (which itself takes ~217 µs);
rem_access 1.77–3.06 ms; rem_inv_req 0.36–1.70 ms; rnr 12.2–13.0 ms; retry_server_qp_err
3.52–3.61 s; retry_proc_kill 3.55–3.69 s. rem_access and rem_inv_req latencies depend on the
cell in a repeatable way. For example, rem_inv_req takes ~1.6 ms with N ≤ 4 and ~0.36 ms with
N ≥ 16, and rem_access ~3.0 ms with N ≤ 16 and ~1.78 ms with N = 64. The harness saw a
bimodal 0.3 ms / 1.6–3.0 ms spread for N = 1. This was not investigated.

## Files

| file | what |
|---|---|
| `cqe_seq_client.c` | requester: batch, trigger, drain, QP query, recovery, verify, CSV rows |
| `Makefile` | `make` builds the client; `make probe_server` builds the unchanged harness responder |
| `run_cqe_seq.sh` | `build` (both nodes; checks sunny's harness sources match rain's, writes only into `gpu-initiated/cqe_seq` there), `run <fault...>` (starts and stops the responder with `pkill -x probe_server`; `timeout` on client and server), `analyze` |
| `analyze_cqe_seq.py` | python3 stdlib: per-trial derivation and per-cell summary (`summary.csv`, `summary.md`) |
| `results/raw_<fault>_<tag>.csv` | one row per CQE, in poll order: trial keys, `seq`, `wqe_idx`, `wqe_kind`, `wqe_signaled`, `wr_id`, `status`, `vendor_err`, `opcode` (255 = left unset by the provider, which is the case for every error CQE), `byte_len`, `qp_num`, `t_ns`, `late`, `foreign` |
| `results/trials_<fault>_<tag>.csv` | one row per trial: `n_cqes`, `drain_end`, `drain_ns`, `post_ns`, `trigger_ns` (ibv_modify_qp duration, local_qp_err), `qp_state_after`, `verify_ok` |
| `results/log_<fault>_<tag>.txt` | client trace (one line per trial) and the responder log tail |
| `results/summary.csv`, `results/summary.md` | per-cell summary (all columns) and the full table above |
| `.gitignore` | the two binaries |

Tags: `main` = the main matrix; `supp4k` / `supp64k` = local_qp_err with 4 KiB / 64 KiB WQEs;
`supplast` = rem_access and rem_inv_req with the bad WQE last.

## Reproduce

```bash
cd ~/rdma-error/harness/gpu-initiated/cqe_seq
./run_cqe_seq.sh build                        # client here, probe_server on sunny (no lock needed)
# one locked batch per fault (cluster lock + idle-link wait); ~1 min each for the fast faults,
# ~4 min retry_server_qp_err, ~5 min retry_proc_kill
for f in local_qp_err rem_access rem_inv_req rnr retry_server_qp_err retry_proc_kill; do
  CQE_TAG=main ../common/cluster_run.sh -t cqe_seq_$f -- ./run_cqe_seq.sh run $f
done
# supplementary: local_qp_err with small WQEs (some or all complete before the ERR)
../common/cluster_run.sh -t cqe_seq_supp -- bash -c \
  'CQE_TAG=supp4k LOCAL_WQE_BYTES=4096 FIRST_ERR_MS=1000 ./run_cqe_seq.sh run local_qp_err &&
   CQE_TAG=supp64k LOCAL_WQE_BYTES=65536 FIRST_ERR_MS=1000 ./run_cqe_seq.sh run local_qp_err'
# supplementary: bad WQE last (k = N-1)
../common/cluster_run.sh -t cqe_seq_supplast -- bash -c \
  'CQE_TAG=supplast POSS=last NS="4 16 64" ./run_cqe_seq.sh run rem_access rem_inv_req'
./run_cqe_seq.sh analyze                      # -> results/summary.csv, results/summary.md
```

Manual client invocation (the responder is `./probe_server -d mlx5_0 -i 1 -g 3 -p 18591` on sunny):

```bash
./cqe_seq_client -s 192.0.2.194 -d mlx5_1 -i 1 -g 4 -p 18591 -f rem_access \
    -N 1,4,16,64 -m all,last -k first,middle -n 5 -S 4096 -q 500 -t 10000 -C 2 \
    -o results/raw.csv -O results/trials.csv
```
