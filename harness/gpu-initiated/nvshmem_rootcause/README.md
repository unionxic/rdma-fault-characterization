# nvshmem_rootcause: NVSHMEM 오류 CQE가 사라진 원인

앞선 장애 전파 측정에서 NVSHMEM은 어떤 장애에도 오류 CQE를 받지 못했다. 그 원인을 찾고, 누가 영향을 받는지 따졌다.
원인은 CPU 프록시의 doorbell record 버그다. NIC가 오류 상태에서 doorbell record를 어떻게 읽는지도 직접 쟀다.
수정하지 않은 공식 3.8.0에서도 재현했고, 그 CQ를 직접 읽어 확인했다.

## 무엇을 쟀나

- **CPU 재현(GPU 없음).** NVSHMEM과 DOCA의 QP, CQ 설정을 그대로 만드는 작은 프로그램으로 57회. 두 스택의 설정 차이를 하나씩 바꿔 봤다.
- **NVSHMEM 안에서.** 문제의 칸만 고치는 스위치를 넣고 18회. 같은 드라이버 상태에서 GPU 핸들러, CPU 프록시, CPU 프록시+수정의 3자 비교 53회.
- **NIC 규칙.** doorbell record 값을 일부러 바꿔 가며 225회(smoke 5회 별도).
- **조건.** 2026-09-24–25, rain(요청)과 sunny(응답), ConnectX-6 펌웨어 20.43.4100, RoCE v2, PMTU 4096, IB 타임아웃 14, 재시도 7.

## 결론

- **원인은 CPU 프록시의 doorbell record 버그다.** CPU 프록시가 송신 인덱스를 doorbell record의 엉뚱한 칸에 써서, QP가 오류에 빠져도 오류 완료가 생기지 않는다.
  - CPU 재현에서 그 칸이 비어 있으면 오류 CQE가 하나도 없었고, 제대로 쓰면 매번 나왔다. QP는 두 경우 모두 ERR로 갔다.
  - 다른 설정 차이 15가지는 하나씩 바꿔도 결과를 바꾸지 않았다. CQ 모양(collapsed 여부)도 무관했고, GPU 없이도 재현됐다.
  - NIC는 장애 자체는 셌다(ack timeout +6, remote access +1). 오류 완료를 세는 카운터만 0이었다(제대로 쓰면 2).
- **3자 비교에서 GPU 핸들러와 CPU 프록시+수정은 같다.** 둘 다 장애 시행마다 오류 CQE가 왔고, 고치지 않은 CPU 프록시는 한 번도 오지 않았다.
  정상 시행 9회에는 없었다.
- **NIC 규칙을 직접 확인했다.** 오류 상태의 NIC는 doorbell record 값까지만 완료를 쓴다.
  - 첫 미완료 WQE부터 record 값 앞까지 정확히 완료가 나왔다. record 값이 그보다 작거나 같으면 원인 CQE조차 없었다.
  - 오류 상태에서 나중에 record를 올리면 빠진 완료가 14–73 µs 안에 나왔다.
- **고쳐도 앱은 실패를 모른다.** GPU 핸들러와 수정본에서 blocking 대기(quiet)는 장애 뒤에도 매번 돌아왔다.
  - 시작 쪽은 8/8을 셌지만 상대는 4개(잘못된 rkey) 또는 6개(상대 QP 오류)만 받았다.
  - 대기는 원인 CQE가 아니라 뒤따르는 flush(5/0xf9)에서 깬다. 고치면 멈춤이 조용한 성공으로 바뀐다.
  - 오류 뒤 finalize는 어느 설정에서나 멈췄다.
- **"상대 QP 오류에서 QP가 RTS로 남는다"는 측정 도구가 만든 인공물이었다.** 진단 스레드가 CPU 프록시를 막아 put이 나가지 않았다. 막지 않으면 put 뒤 약 3.6 s에 ERR로 간다. 재전송도 verbs와 같았다(0.5 s마다 65–69 패킷, 약 3 s).
- **영향 범위.** 3.5.x부터 3.8.0까지 같은 코드다. 3.4.5는 맞는 칸에 쓴다(소스 확인).
  - PeerMappingOverride가 없는 노드에서 일반 사용자로 돌리면 기본 설정이 이 CPU 프록시로 떨어진다. 관리자 설정 없이 쓰라고 안내되는 경로다.
  - QP가 오류에 빠질 때만 드러난다. 정상 트래픽은 영향이 없다.

## 한계와 주의

- **버전 범위는 대부분 소스 확인이다.** 실제로 돌린 것은 devel 7bb2e99와 공식 3.8.0뿐이다. 3.8.0에서는 상대 프로세스 kill만 돌렸다.
- **업스트림에 이슈로 보고했다**(2026-10-07, [NVIDIA/nvshmem#117](https://github.com/NVIDIA/nvshmem/issues/117)). 2026-10-08 NVIDIA 내부 조치가 완료됐다.
  수정 내용은 아직 공개되지 않았다. 이슈는 "오류 CQE가 생긴다"까지만 기대 동작으로 적었다. 고쳐도 API 수준에서는 조용한 성공이라,
  수정만으로 앱이 실패를 알지는 못한다.
- **GPU 핸들러가 오류를 돌려주는 경로는 소스로만 봤다.** 그 반환값을 직접 관측한 적이 없다. release 빌드에 남는 유일한 오류 메시지도 한 번도 나오지 않았다.
- **원인 CQE가 슬롯에 머무는 시간은 이 스택에서 재지 않았다.** 약 60 µs라는 값은 CPU verbs와 GIN의 GPU 쪽 오류 분류 측정에서 온 것이다.
- **DCI 쪽 피해는 추론이다.** DCI가 여럿이면 다른 DCI의 record에 쓴다(소스). 측정하지 않았다.
- **비동기 이벤트는 어느 설정에서도 확인하지 않았다.**
- **표본이 작다.** NVSHMEM 조건은 1–3회, 로컬 QP 오류의 스위치 조건은 1회다. CPU 재현의 차이 하나씩 바꾸기도 1회씩이다. 효과는 전부 아니면 전무였다(0/35 대 21/21).
- **NIC 규칙은 한 NIC, 한 펌웨어, RC에서만 쟀다.** record 값과 첫 미완료 WQE의 차이는 -8–+18(그리고 record 0)만 시험했다.
