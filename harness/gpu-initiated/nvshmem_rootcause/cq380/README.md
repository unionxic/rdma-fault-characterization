# cq380: 공식 3.8.0에서 오류 완료를 직접 확인

NVSHMEM 이슈 #117은 "CPU 프록시에서는 QP 오류 뒤 오류 완료가 생기지 않는다"고 보고했다. 공식 3.8.0에서는
지금까지 대기가 멈추는 것만 봤고, 완료 기록(CQ)을 직접 읽은 것은 devel 빌드였다. 공식 3.8.0에서 CQ를 직접
읽어 확인했다. 예측은 측정 전에 고정했다(태그 `prereg/cq380-v1`).

## 무엇을 쟀나

- **변형 세 가지:** CPU 프록시 공식본, GPU 처리 공식본, CPU 프록시 + doorbell record 수정본.
- **조건:** 상대 kill(세 변형)과 장애 없음(두 공식본), 각 5회씩 모두 25회.
- **기록:** 시작 쪽이 끝나기 직전 모든 큐(DCI 1개, RC 1개)의 CQE를 읽어 오류 완료가 있는지 셌다.
  대기가 멈춘 경우에는 프로그램 안에서 읽을 수 없어서 디버거로 GPU 메모리를 읽었다.

## 결론

- **공식 3.8.0의 CPU 프록시는 상대가 죽은 뒤 오류 완료를 하나도 만들지 않는다.** 대기는 매번 멈췄고, 두 큐에
  남은 완료는 모두 성공이었다.
- **GPU 처리와 두 줄 수정본은 같은 장애에서 오류 완료를 만든다.** 재전송이 끝난 뒤 대기가 돌아왔다.
- **그래서 차이는 doorbell record를 쓰는 칸 하나뿐이다.** 오류 전파 규칙 1(오류 상태의 NIC는 record 값까지만
  완료를 만든다)이 예측한 대로다.
- **다섯 예측이 모두 맞았다.** 원자료에서 독립적으로 다시 센 결과도 같았다.

## 결과

| 변형 | 상대 kill: 오류 완료 | 상대 kill: 대기 | 장애 없음: 오류 완료 |
|---|---|---|---|
| CPU 프록시 공식본 | 0/5 (남은 완료는 성공) | 30 s 안에 안 돌아옴 5/5 | 0/5 |
| GPU 처리 공식본 | 5/5 (flush 오류, 0x05/0xf9) | 3536–3655 ms 뒤 돌아옴 | 0/5 |
| CPU 프록시 수정본 | 5/5 (같은 오류) | 3526–3776 ms 뒤 돌아옴 | 재지 않음 |

시간 범위는 변형마다 5회 전체의 범위다.

## 한계

- **큐 한 칸만 보인다.** 3.8.0은 이 설정에서 완료를 한 칸에 덮어써서, 보이는 것은 마지막 완료 하나다. 오류 쪽에서
  보인 것은 flush 오류이고, 그 앞의 재전송 소진 오류는 덮였을 수 있다.
- **멈춘 경우의 읽기 방법이 사전 등록과 다르다.** 프로그램 안 읽기가 멈춘 커널 뒤에 막혀서, 본 실행 전에 디버거
  읽기로 바꿨다. 사전 등록 문장을 글자 그대로 따르면 그 조건은 관측 불가다(사전 등록 뒤 변경 기록 1, 3항).
- 장애는 상대 kill 하나, CPU 프록시는 `cpu_host_memory` 방식만 쟀다. 노드 한 쌍, NIC 한 종류, PE 2개다.
