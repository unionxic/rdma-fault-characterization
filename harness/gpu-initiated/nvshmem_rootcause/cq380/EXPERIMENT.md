# 3.8.0에서 오류 완료 직접 확인 (cq380)

**목적:** NVSHMEM 이슈 #117의 핵심 주장("CPU 프록시에서는 QP 오류 뒤 오류 완료가 생기지 않는다")을 공식 3.8.0에서
완료 기록(CQ)을 직접 읽어 확인한다. 지금까지 3.8.0에서는 대기가 멈추는 것만 봤고, CQ를 직접 읽은 것은 devel
빌드였다.

## 1. 배경과 연구 질문

- 공식 3.8.0에서 CPU 프록시는 상대 kill 뒤 quiet가 30 s 안에 돌아오지 않았고(3/3), GPU 처리와 두 줄 수정본은
  재시도가 끝난 뒤 돌아왔다(각 3/3). 이때 CQ는 읽지 않았다
  ([../official380/README.md](../official380/README.md)).
- 질문: 3.8.0에서 CPU 프록시는 오류 CQE를 하나도 만들지 않는가. GPU 처리와 수정본은 만드는가.

## 2. 가설

- CPU 프록시는 송신 인덱스를 doorbell record의 수신 칸에 써서, 오류 상태의 NIC가 완료를 만들 범위가 없다.
  그래서 오류 CQE가 하나도 없다. GPU 처리와 수정본은 송신 칸에 써서 오류 CQE가 생긴다.
- CPU 프록시에서 오류 CQE가 하나라도 나오면 가설은 틀린 것이다.

## 3. 사전 예측

원문은 [predictions.csv](predictions.csv), 해시는 [PREREG.txt](PREREG.txt).

| id | 칸 | 예측 | 판정 기준 |
|---|---|---|---|
| C1 | CPU 프록시 공식본, 상대 kill | 어느 큐에도 오류 CQE가 없다. RC 큐에는 성공 CQE가 있다 | 5/5 |
| C2 | GPU 처리 공식본, 상대 kill | RC 큐에 오류 CQE가 하나 이상 있다 | 5/5 |
| C3 | CPU 프록시 수정본, 상대 kill | RC 큐에 오류 CQE가 하나 이상 있다 | 5/5 |
| C4 | CPU 프록시 공식본과 GPU 처리 공식본, 장애 없음 | 오류 CQE가 없다 | 변형마다 5/5 |

예측 밖 결과가 하나라도 있으면 그 칸은 틀림이다.

## 4. 범위

- **포함:** NVSHMEM 공식 v3.8.0-0, IBGDA, RC 1개와 DCI 1개, PE 2개, 상대 kill.
- **제외:** 다른 장애. 3.8.0 재현 프로그램은 상대 kill만 낸다.

## 6. 변수

- **독립변수:** 변형(CPU 프록시 공식본, GPU 처리 공식본, CPU 프록시 수정본), 상대 kill 여부.
- **종속변수:** PE 0이 끝나기 직전 모든 DCI와 RC 큐의 유효 CQE 수, 오류 CQE 수(opcode 0xd 또는 0xe), 첫 오류의
  syndrome과 vendor syndrome. CPU 프록시 kill에서는 30 s 대기 상한에서, 나머지는 마지막 반복 뒤에 읽는다.
- **통제변수:** 기존 실행기 설정(반복 40회, 256 KiB, 주기 250 ms, 3번째 반복 뒤 kill, IB 타임아웃 14, 재시도 7).

## 8. 제외 기준과 중단 기준

- **제외 기준:**
  - CQ 읽기가 실패한 시행(`CQSCAN failed`)은 관측 불가로 따로 센다.
  - C1에서 RC 큐에 유효 CQE가 하나도 없으면, CQ를 제대로 읽지 못한 것으로 보고 관측 불가로 센다.
- **중단 기준:** `cluster_run.sh`가 3600 s 안에 잠금이나 유휴 링크를 얻지 못하면 미룬다. 다른 사용자 작업은 건드리지
  않는다.

## 9. 실행 방법과 경로

- `../official380/run.sh`를 `NVS_BIN=nvs_cq_repro CQSCAN=1`로 부른다. 모두 `cluster_run.sh` 안에서 돈다.
- 출력: `results/20261007/`. 원시 로그는 Release.
