# 3.8.0에서 오류 완료 직접 확인 (cq380)

**목적:** NVSHMEM 이슈 #117의 핵심 주장("CPU 프록시에서는 QP 오류 뒤 오류 완료가 생기지 않는다")을 공식 3.8.0에서
완료 기록(CQ)을 직접 읽어 확인한다. 지금까지 3.8.0에서는 대기가 멈추는 것만 봤고, CQ를 직접 읽은 것은 devel
빌드였다.

## 1. 배경과 연구 질문

- 공식 3.8.0에서 CPU 프록시는 상대 kill 뒤 quiet가 30 s 안에 돌아오지 않았고(3/3), GPU 처리와 두 줄 수정본은
  재시도가 끝난 뒤 돌아왔다(각 3/3). 이때 CQ는 읽지 않았다
  ([../official380/README.md](../official380/README.md)).
- 질문: 3.8.0에서 CPU 프록시는 오류 CQE를 하나도 만들지 않는가. GPU 처리와 수정본은 만드는가.

## 2. 가설

- CPU 프록시는 송신 인덱스를 doorbell record의 수신 칸에 써서, 오류 상태의 NIC가 완료를 만들 범위가 없다.
  그래서 오류 CQE가 하나도 없다. GPU 처리와 수정본은 송신 칸에 써서 오류 CQE가 생긴다.
- CPU 프록시에서 오류 CQE가 하나라도 나오면 가설은 틀린 것이다.

## 6. 변수

- **독립변수:** 변형(CPU 프록시 공식본, GPU 처리 공식본, CPU 프록시 수정본), 상대 kill 여부.
- **종속변수:** PE 0이 끝나기 직전 모든 DCI와 RC 큐의 유효 CQE 수, 오류 CQE 수(opcode 0xd 또는 0xe), 첫 오류의
  syndrome과 vendor syndrome. CPU 프록시 kill에서는 30 s 대기 상한에서, 나머지는 마지막 반복 뒤에 읽는다.
- **통제변수:** 기존 실행기 설정(반복 40회, 256 KiB, 주기 250 ms, 3번째 반복 뒤 kill, IB 타임아웃 14, 재시도 7).

## 8. 제외 기준과 중단 기준

- **제외 기준:**
  - CQ 읽기가 실패한 시행(`CQSCAN failed`)은 관측 불가로 따로 센다.
  - C1에서 RC 큐에 유효 CQE가 하나도 없으면, CQ를 제대로 읽지 못한 것으로 보고 관측 불가로 센다.
- **중단 기준:** `cluster_run.sh`가 3600 s 안에 잠금이나 유휴 링크를 얻지 못하면 미룬다. 다른 사용자 작업은 건드리지
  않는다.

## 9. 실행 방법과 경로

본 실행 25회, smoke 10회는 따로 뒀다. 범위는 셀 하나의 5회 전체 범위다. 근거:

| 칸 | 예측 | 결과 | 판정 |
|---|---|---|---|
| CPU 프록시 공식본, 상대 kill (C1) | 오류 CQE 없음, RC 큐에 성공 CQE 있음 | `[측정]` 5/5 멈춤(5번째 반복, 30 s 상한). cuda-gdb로 읽은 두 큐 모두 기록된 CQE 1개, 둘 다 성공. 오류 CQE 0 | 맞음 5/5. 8절을 글자 그대로 읽으면 관측 불가 |
| GPU 처리 공식본, 상대 kill (C2) | RC 큐에 오류 CQE | `[측정]` 5/5 오류 CQE 1개(syndrome 0x05 작업 요청 flush, vendor 0xf9). 5번째 반복이 3536–3655 ms 뒤 돌아옴 | 맞음 5/5 |
| CPU 프록시 수정본, 상대 kill (C3) | RC 큐에 오류 CQE | `[측정]` 5/5 같은 오류 CQE. 3526–3776 ms 뒤 돌아옴 | 맞음 5/5 |
| 두 공식본, 장애 없음 (C4) | 오류 CQE 없음 | `[측정]` 10/10 오류 CQE 0 | 맞음, 변형마다 5/5 |

- `[측정]` 모든 큐(50개)에 기록된 CQE가 하나뿐이다. cuda-gdb로 읽은 10개 큐와 오류 큐 10개에서는 그 자리가 슬롯 0이다.
  3.8.0은 이 설정에서 CQE를 한 칸에 덮어쓴다. 그래서 보이는 것은 마지막 CQE다.
- `[추론]` RC 큐 하나는 QP 하나의 완료만 받고, 오류 상태 QP는 성공 완료를 더 만들지 않는다. 그러므로 CPU 프록시에서
  마지막 CQE가 성공이면 그 큐에는 오류 CQE가 한 번도 쓰이지 않았다.

## 16. QA와 재현성

- 다른 에이전트가 `score.py`와 채점 결과를 보지 않고 원자료(로그와 cuda-gdb 출력)를 직접 풀어 다시 셌다. 판정이
  같다. 시행 집합은 사전 등록한 5×5와 정확히 같고, 고정 파일과 2, 3, 7, 8절은 태그 뒤 바뀌지 않았다.
- cuda-gdb 읽기 검증: 버퍼마다 65536 바이트, 주소가 프로그램이 알린 주소와 같고, CQE 안의 QP 번호가 그 큐의 QP 번호와
  같다(0이 아닌 실제 내용). 읽기는 kill 뒤 38.3–38.5 s에 끝났고 PE 0은 그때도 같은 대기에 있었다.
- 원자료와 충돌한 기존 숫자는 없다. 재계산이 찾은 사소한 점: PE 0 로그에 kill 시각 줄이 덮여 없다(행 파일에는 있음),
  NIC 카운터 열이 25회 모두 0이다(채점에 쓰지 않음). 공식 3.8.0 재현에서도 포트 카운터는 11회 모두 +0이었다
  ([../official380/README.md](../official380/README.md)). 원인은 `[미확인]`.

## 17. 결론

공식 3.8.0에서도 CPU 프록시는 상대가 죽은 뒤 오류 완료를 하나도 만들지 않고 대기가 멈춘다. GPU 처리와 두 줄 수정본은
같은 장애에서 오류 완료를 만들고 재시도가 끝난 뒤 돌아온다. 이슈 #117의 핵심 주장이 3.8.0에서 CQ 직접 읽기로
확인됐다.

## 18. 한계

- CPU 프록시 방식에서는 GPU 쪽에 QP doorbell record 주소가 없어서, record 값 자체는 읽지 않는다.
- CQ가 한 칸이라 마지막 CQE만 보인다. 오류 칸에서 보인 것은 flush 오류이고, 그 앞의 재전송 소진 오류는 덮였을 수 있다.
- 멈춘 칸은 사전 등록한 방법(프로그램 안 읽기)이 아니라 cuda-gdb로 읽었다([DEVIATIONS.md](DEVIATIONS.md) 1, 3).
- 장애는 상대 kill 하나, 처리 방식은 `cpu_host_memory`만 쟀다.
