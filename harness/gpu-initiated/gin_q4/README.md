# gin_q4: GDAKI CQ 모양 비교와 장치 쪽 오류 분류

`../gin/`에서 GDAKI는 오류 코드를 버렸고, blocking 대기는 실패한 쓰기를 성공으로 보고했다. 여기서는 두 가지를 했다.
첫째는 CQ 모양 비교다. 슬롯 하나짜리 collapsed CQ가 정말 오류 CQE를 못 받는지 GDAKI 안에서 확인한다.
둘째는 GDAKI 장치 쪽 분류기다. GPU가 원인 CQE를 읽어 분류하고 호스트에 바로 알리게 한 뒤, 정확도와 속도와 비용을 잰다.

## 무엇을 쟀나

- **장애.** 로컬 QP 오류, 원격 접근 오류(등록 영역 밖 쓰기),
  상대 QP 오류(상대 QP를 오류 상태로, 상대 살아 있음, 요청 쪽에는 재시도 초과로 보임), 상대 프로세스 kill(SIGKILL). `../gin/`과 같다.
- **2026-09-23, CPU doorbell fallback.** CQ 모양 비교는 ring과 collapsed CQ, 분류 켬과 끔으로 56회.
  장치 쪽 분류기는 ring CQ, 분류 켬과 끔, timeout과 blocking으로 54회. 칸마다 3회(분류 끈 collapsed는 2회).
  장애 없는 지연 측정 40회.
- **2026-09-25 30회 재측정, GPU doorbell(추정).** ring과 collapsed CQ, 장애 네 가지 각 30회(240회),
  분류를 끈 stock 대조 로컬 QP 오류 blocking 10회.
- **조건.** rain(보내는 쪽)과 sunny(받는 쪽), ConnectX-6 RoCE, IB 타임아웃 14,
  반복마다 256 KiB put과 signal 하나.

## 결론

- **collapsed CQ도 오류 CQE를 받는다.** 감지 순간 슬롯에는 원인 CQE(5/0xf5, 10/0x88, 12/0x81)가 있었다(27/27).
  - 500 µs 뒤 다시 읽으면 뒤따른 WQE의 flush 5/0xf9로 덮여 있었다(18/18).
  - "collapsed CQ가 오류를 숨긴다"는 가설은 기각됐다. NVSHMEM에서 오류 CQE가 없던 원인은 따로 있다(`../nvshmem_rootcause/`).
  - stock NCCL은 CPU doorbell 모드에서 collapsed CQ를 쓰지 못한다. 고치지 않으면 첫 SQ 한 바퀴(64회)에서 멈췄다.
- **장치가 원인을 정확히 분류한다.**
  - 09-23: 로컬 QP 오류 LOCAL_QP_ERR 5/0xf5, 원격 접근 오류 REM_ACCESS 10/0x88,
    상대 QP 오류 RETRY_EXC 12/0x81, 칸마다 6/6.
  - 상대 프로세스 kill도 RETRY_EXC 12/0x81이다. GDAKI에서 상대 QP 오류와 상대 프로세스 kill은 CQE로는 갈리지 않는다.
  - 30회 재측정: 240/240회 정확했다.
  - ring CQ에서 기다리던 CQE는 늘 5/0xf9였다. 원인은 그 앞 슬롯에 있다. 기다린 CQE만 읽으면 모든 장애가 flush로 보인다.
- **호스트가 바로 안다.** 장치가 감지한 뒤 호스트가 기록을 읽기까지 94 µs, 비동기 오류 조회가
  ncclRemoteError를 돌려주기까지 190 µs였다(중앙값, n=33).
  - 장애에서 호스트까지는 로컬 QP 오류 약 15 ms, 원격 접근 오류 약 2.8 ms, 상대 QP 오류와 상대 프로세스 kill
    약 3.6–3.7 s다(09-23). 분류를 끄면 8.0–10.0 s다.
  - API가 돌려주는 값은 여전히 ncclRemoteError 하나다. 원인 코드와 분류는 로그(WARN)에 있다.
- **조용한 성공이 사라진다.** blocking 대기가 실패 시 ncclRemoteError를 돌려준다.
  - 로컬 QP 오류, 원격 접근 오류, 상대 QP 오류의 blocking 대기에서 0/9(09-23), 0/90(30회 재측정).
  - 분류를 끄면 매번 1회를 성공으로 셌다(09-23 9/9, 30회 재측정의 stock 대조 10/10).
- **비용은 작다.** 장애가 없을 때 4 KiB p50이 0.06–0.10 µs(1% 이하), 256 KiB가 0.5% 이하 늘었다.

## 한계와 주의

- **받는 쪽은 여전히 모른다.** 받는 쪽은 아무것도 보내지 않으므로 오류 CQE가 없다. blocking 대기는 상한까지 멈춘다.
- **abort가 돌아왔다는 기록은 보내는 쪽 기준이다.** 받는 쪽 abort는 blocking의 로컬 QP 오류, 원격 접근 오류,
  상대 QP 오류에서 돌아오지 않았다(30회 재측정 90/90, stock 대조 10/10).
- **상대 프로세스 kill의 "한 번 앞섬"은 조용한 성공이 아니다.** 보내는 쪽이 받는 쪽보다 1회 더 센 경우가
  1/6(09-23), 5/60(30회 재측정) 있었다. 마지막 쓰기는 성공 CQE를 받았으므로 데이터는 kill 전에 도착했다고 본다(추정).
- **상대 프로세스 kill의 blocking 칸은 사실상 timeout 칸이다.** 상대 프로세스 kill은 두 대기 방식 모두
  timeout 대기로 끝을 확인했다.
- **30회 재측정의 GPU doorbell은 추정이다.** 이 빌드는 doorbell 모드를 기록하지 않는다. CPU proxy 스레드와 DOCA 경고가
  없다는 두 지표로 판단했고, CPU doorbell을 강제한 대조 2회로 지표를 확인했다.
- **30회 재측정은 모두 펌웨어 명령 슬롯 하나가 샌 상태에서 돌았다.** 09-25 06:45에 rain의 NIC에서 슬롯 하나가 샜고
  (`../gin_recovery/TRANSPARENT_S1.md`), 30회 재측정의 분류기 시행은 07:31–09:34에 돌았다. 영향이 있었는지는 따로 재지 않았다.
- **이 드라이버에는 동기화 경쟁이 남아 있다.** 받는 쪽이 동기화 응답 뒤에 버퍼를 초기화한다(`../gin_recovery/`에서 발견).
  틀린다면 거짓 불일치 쪽이고, 이 폴더의 실행에서는 나타나지 않았다.
- **연산 모양이 하나다.** 반복마다 WQE 2개(put과 signal)만 썼다. 뒤에 WQE가 더 있으면 collapsed 슬롯에는 감지 때
  이미 5/0xf9가 있을 것이다(추정). 분류는 GDAKI backend에만 있다.
