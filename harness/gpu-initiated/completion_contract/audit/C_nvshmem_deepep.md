# C: NVSHMEM IBGDA and DeepEP, doorbell record (DBR) audit

Rule under test: after a QP error the NIC completes only `[c, P)` (c = first incomplete WQE,
P = DBR send counter, word 1). A stack shows faults at the CQE layer only if P eventually
reaches the posted index.

Tags: **[source]** read in the code at the cited lines; **[inferred]** reasoning from source,
not executed; **[unknown]** not determined. Nothing in this audit was built or run.

## Notes

1. **Earlier finding confirmed** [source]. Proxy line numbers (DCI / RC / GPU handler):
   - v3.4.5-0: one combined proxy loop, 475-476 (`ep->dbr_offset + sizeof(__be32)`, word 1); GPU handler 2416-2417, word 1.
   - v3.5.19-1: 533-534 / 595-596 / 3529-3530.
   - origin/main "Version: 3.5.0-0" 2c7f5a3: 534 / 592 / 3532, already buggy.
   - v3.8.0-0: 517-518 / 581-582 / 3910-3911.

   Commit ce9d487 "ibgda_device: Add qpair-specific APIs" (2025-10-08) is an ancestor of v3.5.19-1 and not of v3.4.5-0 (checked with `git merge-base --is-ancestor`). It changed the proxy from `+ sizeof(__be32)` to `* sizeof(__be32)`. The GPU handler was never affected.
2. **The DCI case is worse than "another DCI's record".** The proxy multiplies a byte offset (8k) by 4, so it writes byte 32k. That is always word 0 of some record and never word 1. For k >= num_dci/4 the write lands past the `posix_memalign`'d `8 x num_dci` host buffer [source for the arithmetic; the heap effect is inferred]. With the default `NUM_DCI=1` only DCI 0 exists.
3. **The 16-bit wrap is untested.** With P = 0 stuck, once the SQ counter has wrapped past 65536, `(0 - c) mod 2^16` can be small. The earlier measurement tested "record 0" only at small c [unknown].
4. **The GPU handler is not affected by deferral after errors.** The device `ibgda_poll_cq` returns -1 on `MLX5_CQE_REQ_ERR`, but callers only `assert`, which release builds remove. So GPU threads keep submitting, and each later post raises P. The measured rule says raising P in ERR releases the missing completions [source + inferred].
5. **Batch-RMA regions are new in 3.8.0** (`nvshmemx_region_start/stop`, hint `NVSHMEMI_REGION_HINT_BATCH_RMA`). They are the only NVSHMEM path found where the DBR is deliberately held back, and it is opt-in. `IBGDA_NUM_REQUESTS_IN_BATCH` defaults to 32 in all three versions.
6. **The proxy thread's liveness is not tied to the CQ.** In v3.8.0, `src/host/proxy/proxy.cpp` 1614-1637 and 1662-1689 loop until `stop`, which is set only by `nvshmemi_proxy_finalize`. `nvshmemt_ibgda_progress` always returns success. The CPU handler forces the full proxy (`no_proxy = (nic_handler == GPU)`, ibgda.cpp v3.8.0 5323).
7. **DeepEP facts outside Q1-Q5** [source]:
   - The legacy `ibgda_poll_cq` never checks the CQE opcode, so error CQEs count as progress (legacy/ibgda_device.cuh 465-486). The legacy code also never waits for SQ slots.
   - At a56d615 the legacy `ibgda_get_rc` uses the NVSHMEM v1 RC layout. NVSHMEM >= 3.5 typedefs `nvshmemi_ibgda_device_state_t` to v2, so legacy DeepEP at that commit would pick the wrong RC on 3.5+ [inferred]. The V1 file at 567632d (after 29d31c0) handled both layouts.
8. **Refinement of the earlier README.** The earlier README says DeepEP's "GDRCopy instead of regkeys" route goes through the buggy proxy. For DeepEP's own IBGDA kernels on NVSHMEM >= 3.4.5 the proxy is never told about DeepEP's WQEs at all (row 13, inferred). NVSHMEM's own APIs on the same setup do go through the word-0 proxy.
9. **Not audited:**
   - NVSHMEM's `gpunetio` (GDAKI/DOCA) transport in v3.8.0.
   - NCCL GIN internals, which DeepEP main depends on.
   - The DeepEP non-main branches (`hybrid-ep`, `v2.5`, `nvDev`, and others).
