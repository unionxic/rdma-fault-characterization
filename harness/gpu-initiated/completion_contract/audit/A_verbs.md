# A_verbs: DBR audit of CPU-initiated verbs paths (libmlx5, NCCL net_ib, NCCL GIN proxy)

Rule under test: after a QP error the NIC produces error/flush CQEs only for WQEs from the first incomplete one up
to the DBR send counter (DBR word 1). A stack shows faults at the CQE layer only if its DBR send value eventually
reaches the posted index.

Tags: [read] = read in source; [binary] = static disassembly of the installed library (nothing was run);
[inferred] = my reasoning, not read verbatim; [not determined] = open.

## Notes

1. **Binary check of the installed provider [binary].** `objdump -d` of
   `/usr/lib/x86_64-linux-gnu/libmlx5.so.1.24.47.0` gives 10 `sfence` instructions in 5 doorbell sites. Every site
   has the same shape: `movzwl <cur_post>` (16-bit), `bswap %eax`, `mov %eax,0x4(<db>)` (DBR word 1), `sfence`,
   the UAR store (`mov %rdx,(%rax)` or the BF copy), then `sfence`. Four sites use `cur_post` at struct offset
   `0x2f4`: post_send, wr_complete, srq_ops and one more inlined copy. One uses offset `0x58`, which matches
   `dr_send.c:415` (the internal steering QP). This agrees with the source; the installed binary does not differ.
   The listing is in `libmlx5.dis`.
2. **Barriers are x86-specific in strength [read].** On x86_64, `udma_to_device_barrier()` is only a compiler
   barrier; TSO keeps the WQE stores (WB) ordered before the DBR store (WB). `sfence` orders the DBR store before
   the write-combined UAR store. On aarch64 these become `dsb st`. Not relevant to ConnectX-6 on x86, but noted.
3. **Error state does not block posting in libmlx5 [read].** `set_qp_operational_state` disables posting only in
   RESET. A hardware-driven move to ERR does not go through user space at all. So a CPU poster that keeps posting
   after the error still advances the DBR, and those WQEs are flushed. A poster can stop only at SQ overflow
   (`ENOMEM`), which happens when nobody polls the CQ; that case returns an error and posts nothing.
4. **What "visible" means for NCCL [read].** The NIC-level prediction is "visible" for both NCCL paths. At the
   application layer both NCCL versions act only on the **first** non-success CQE and stop: net_ib returns
   `ncclRemoteError`, and the GIN progress thread exits and stores `asyncResult`. The remaining flush CQEs sit in
   the CQ unread. This does not contradict the DBR rule, but a measurement that counts "CQEs seen by NCCL" will
   see 1, not n.
5. **The GIN proxy batch is not a DBR lag [read + inferred].** The `aggregate` deferral holds `ibv_send_wr`
   structs in process memory before `ibv_post_send`; the NIC has no WQE for them. Under normal progress the batch
   is empty at the end of every progress pass, because the last GFD of each per-peer run has `aggregate = false`.
   The first `Test()` of the next pass flushes it anyway. The error-CQE path therefore cannot strand a batch:
   `Test()` posts the batch before it polls. Only a non-CQE failure in the middle of a run can strand it (row 8,
   caveat 2).
6. **Possible double post at teardown [inferred, not tested].** If `wrap_ibv_post_send` fails inside
   `ncclRmaIbProxyPostBatch` (`gin.cc:437`), the function returns before `batch->nWrs = 0`. libmlx5 has already
   posted the WRs before `bad_wr`. A later `destroyContext` then calls `PostBatch` again on the same array and
   would re-post those WRs. This matters only after a failure and at teardown.
7. **Host-side RMA (not GIN) on the same backend [read].** `src/rma/rma_proxy_progress.cc:24-29,158` calls
   `iput`/`iputSignal` with `optFlags 0`, so those post immediately: no aggregation.
8. **NCCL 2.32.3 net_ib p2p (not asked) [read].** It still posts only through `wrap_ibv_post_send` /
   `wrap_ibv_post_recv` (`p2p.cc:251,447,602,762`, `common.h:517`, resiliency `p2p_resiliency.cc:541`,
   `p2p_resiliency_recovery.cc:180,862,892`). Its QPs come from `ibv_create_qp` or `mlx5dv_create_qp` with the
   OOO flag only. Prediction as for 2.23.4: visible.
