## Notes

1. **UCX CPU path, DBR memory and reset.** [read] Verbs-created QPs use rdma-core's DBR. DEVX-created QPs use the UCX pool, with `send_dbr_mode = DBR_VALID`, because every in-tree `uct_ib_mlx5_qp_attr_t` is zero-initialized. When a DCI is reset, `uct_ib_mlx5_devx_modify_qp_state(RESET)` does not zero the DBR word, unlike rdma-core (`verbs.c:2775`). The reset happens only after `!uct_dc_mlx5_iface_dci_has_outstanding` (`dc/dc_mlx5.c:1831`), and the next post overwrites the word, so this does not change the prediction. [inferred]
2. **GDAKI, 1-entry CQ.** [read] The CQ is one 64-byte slot that the NIC overwrites. `check_completion` compares the slot's `wqe_counter` with the request and reads the opcode of whatever CQE is in the slot. Two consequences [inferred]: (a) after an error, a request that had already succeeded but is polled late also returns `UCS_ERR_IO_ERROR`, because the slot now holds a later flush CQE; (b) posts without a request object have no error path at all. In the delayed mode, if `TX_QUEUE_LEN` is set below 128, the reservation can fill the SQ with WQEs that were never rung and spin forever on `NO_RESOURCE`. [inferred, not tested]
3. **GDAKI, two doorbells.** [read] UCX rings the UAR once before and once after the DBR store. Under the PRM model the first ring finds a stale DBR and starts nothing; the second does the work. The fence between the DBR store and the second ring is `fence.release.gpu` (GPU scope) followed by an `st.mmio.relaxed.sys` store. Whether that orders a GPU-memory DBR store before a PCIe MMIO write, as seen by the NIC, is a PTX/platform question this audit cannot settle. [unknown]
4. **rocSHMEM, 32-bit DBR value.** [read] The value written is the low 32 bits of a 64-bit counter. After 65 536 posts, bits 31–16 are no longer zero. The PRM field is 16 bits, and rdma-core masks it. Tests with that many posts presumably work, so the NIC probably ignores the upper bits [inferred], but this is not verified.
5. **rocSHMEM, missing WQE-to-DBR fence.** [read] Only compiler fences separate the lanes' WQE stores from the leader's DBR store. The hardware release comes with the later doorbell store. If ownership passes when the DBR changes, a NIC that is already fetching for that QP could see the new DBR before the WQE bytes land. This is a possible race; it does not change the CQE count. [inferred]
6. **rocSHMEM, error reporting.** [read] No mlx5 GDA file tests for `REQ_ERR`, `RESP_ERR` or the syndrome (grep over `src/gda`). An error is therefore present in the CQ but dropped before the application, at the same layer where NVSHMEM's CPU proxy loses it.
7. **Scope.** The rocSHMEM `reverse_offload` backend, a CPU proxy over libibverbs, and the bnxt and ionic providers are out of scope (not mlx5 self-posting). This audit did not trace UCX's handling of an error CQE after `uct_ib_mlx5_check_completion` → `uct_ib_mlx5_completion_with_err` → `uct_rc_mlx5_iface_handle_failure`.
8. **Not determined.** (a) The D2P/GDP plugin's DBR handling and whether it sets `sq_no_dbr`; (b) whether ConnectX-6 supports `send_dbr_mode = NO_DBR_INT`, because the UCX comment says "Caller must ensure the device supports it"; (c) the NIC behavior for the non-zero upper 16 bits in rocSHMEM's DBR value; (d) any runtime confirmation. All predictions are source-derived.
