# NVSHMEM IBGDA fault tolerance v2: ring send CQs, device bounds check, resync negative controls

Patch: `nvshmem_ibgda_ft_v2.diff`, a full diff against NVSHMEM `7bb2e99c` +
`../nvshmem/nvshmem_ibgda_fault_inject.diff` + `../nvshmem_rootcause/nvshmem_nrc_proxy_sq_dbr.diff`
(the same base as `nvshmem_ibgda_ft.diff`). It contains v1, so apply one or the other. v1 design:
`DESIGN.md`. v1 results: `README.md`. v2 answers three review points:

- **A.** The `cc=0` (ring CQ) result was invalidated and never re-run. A ring CQ is the simplest
  fix for root-cause loss on the collapsed CQ, yet a heavier resident sentinel thread was chosen.
- **B.** An out-of-bounds write that stays inside the heap MR (silent corruption) ended as
  "undetectable".
- **C.** The recovery resync items had no negative controls, but the summary listed them as
  verified.

Design rule (the user's): detection and recovery live inside the library (transport and device
code), not in the application. Everything in v2 sits behind `NVSHMEM_IBGDA_FT=1`.

## TL;DR

- **A1, stock `cc=0` re-run (GPU handler, no watch thread):** stock NVSHMEM cannot run at all on
  non-collapsed send CQs. The first `nvshmem_malloc` never returns (6/6 runs, v1 and v2 builds,
  flag off). The NIC delivered every CQE, but the device poll reads slot 0 only. Dump taken while
  it hung (both PEs, 5/5 runs): 6 WQEs posted and rung, slot 0 = CQE `wqe_counter` 2, slot 1 = CQE
  `wqe_counter` 5, `cons_idx` stuck at 3. No fault-free put and no fault could be tested.
- **A2, ring mode in v2 (`NVSHMEM_IBGDA_FT_RING_CQ=1`):** the device walks the ring by consumer
  counter and never consumes an error CQE, so the root cause waits at the consumer position until
  a wait reaches it.
  - Capture: the pattern that defeated v1's in-loop read is put+signal, then 200 us or 2 ms of
    compute, then `nvshmem_quiet` (F1 and F2b, 30 trials per cell). Ring mode kept the root cause
    in **90/90**, v1's in-loop read in 0/90, the sentinel in 90/90. The ring needs no resident
    thread.
  - Concurrency: 32 threads quiescing on one QP, 100-300 iterations of 256 put+signal+quiet, 2
    wraps of the 16-bit `wqe_counter`. All 9 ring runs verified byte-exact.
  - Single-GPU stress test of the walker: passed 8/8 configurations (up to 4.2 M WQEs, 64
    `wqe_counter` wraps, 128 concurrent waiters), and failed as it must (2/2) when the ring
    precondition was violated.
  - Recovery works in ring mode: F1 18/18, F3 9/9, F1 x5 9/9, and forced d = 0 11/11 after a
    driver-race fix (the library was not involved). In 188/188 commits the ring counter was
    consistent.
- **A3, fault-free cost (put+signal+quiet p50, 6 runs x 10k ops per cell):** v2 flag off = v1 flag
  off (4 KiB 12.48 vs 12.51 us; 256 KiB 40.18 vs 40.29 us). Ring mode +0.34 us at 4 KiB (+2.7 %
  vs the v2 collapsed classifier), +0.37 us at 256 KiB (+0.9 %). Collapsed classifier and sentinel
  as in v1 (within 0.1 us of flag off).
- **B, bounds check (`NVSHMEM_IBGDA_FT_BOUNDS=1`):** detected and not posted in 30/30 for each
  overrun that leaves the object's allocator chunk: into a freed gap, across the object's end, past
  the last object. The canary outside the object and the object itself were intact in 90/90. A
  write past the heap end was caught too (5/5). The existing F2a fault (`dst = dbuf + bytes`) was
  **not** detected (0/30, corruption 30/30). `dbuf` and `sbuf` are adjacent 256 KiB chunks, so that
  write is a well-formed write to all of `sbuf`, and no address-range check can reject it. With an
  optional 512 B red zone after every allocation (`NVSHMEM_IBGDA_FT_BOUNDS_GUARD=512`), the same
  fault was detected in 30/30 (and in 5/5 in blocking mode) with nothing corrupted. Cost: +0.64 us
  per put+signal at 4 KiB (+5.1 %), +0.58 us at 256 KiB (+1.4 %). No false positive in any
  fault-free run with the check on: 18 verified runs (15 x 200 put+signal, 3 x 25 600 concurrent
  put+signal), 24 latency runs of 10k ops, plus init, barriers and teardown.
- **C, negative controls (N = 5 per knob, F1 recovery unless noted):**
  - Necessary (the run fails without the step): device indices, sticky record, collapsed-CQ 0xff
    refill, host error record, finalize barrier skip, and in ring mode the ring-counter resync.
    - indices: the NIC re-executed the old WQEs left in the send queue. That gave 52 duplicate
      signal ADDs (signal 104 vs 52) and a data mismatch, 5/5.
    - sticky record: every later wait failed at once, and the run was declined 5/5.
    - collapsed-CQ refill: the stale trailing flush was read as a new error, and the run was
      declined 5/5.
    - host error record: the next fault (REM_ACCESS) was reported as the stale LOCAL_QP_ERR and
      "recovered" 6 times before the round limit, 5/5.
    - finalize barrier skip: teardown hung, F2b 5/5 and F4 3/3.
    - ring-counter resync (ring mode): the replay wait expired, 5/5.
  - Not needed in these tests (recovered 5/5 without the step): `post_send_lock`, `ibuf`, the
    doorbell-record zeroing, the DCI reset (DCIs idle here), fresh PSNs (no stale packets here). The
    0xff refill is not needed in ring mode either (owner bit). The v1 summary's "verified" is
    corrected accordingly.

## Flags

| env (both PEs) | default | effect |
|---|---|---|
| `NVSHMEM_IBGDA_FT=1` | unset | v1: classification, mailbox, recovery API. Every item below requires it. |
| `NVSHMEM_IBGDA_FT_RING_CQ=1` | off | (A) send CQs created with `cc=0` (ring); device waits walk them in order. GPU NIC handler only (ignored, with a warning, otherwise). Decided before the first CQ is created and never changed. |
| `NVSHMEM_IBGDA_FT_BOUNDS=1` | off | (B) every RMA/AMO checks its remote range against the heap allocator's in-use chunks before anything is posted. |
| `NVSHMEM_IBGDA_FT_BOUNDS_GUARD=<bytes>` | 0 | (B, with `BOUNDS`) red zone after every symmetric allocation (rounded up to 512 B), allocated but published as free. Changes the heap layout; both PEs must use the same value (added before NVSHMEM's own size-symmetry check). |
| `NVSHMEM_IBGDA_FT_TEST_SKIP=<list>` | empty | (C) test-only: skip steps of the recovery resync or of the decline handling: `idx lock ibuf sticky cqfill dbr nerr dci psn finbar ringci`. Never for production. |
| `NVSHMEM_IBGDA_FAULT_CQ_COLLAPSED=0` | unset | fault-inject hook, unchanged: `cc=0, oi=0` with the stock device code (A1 only). |

**Flag off** (`NVSHMEM_IBGDA_FT` unset) behaves as v1 flag off. The only new work is one
`__constant__` flag test per RMA/AMO call (`state->ft_flags & BOUNDS`, 0 when off). Otherwise:

- The device poll reads the same `state->ft` pointer (NULL) and takes the stock loop.
- The host creates no thread, buffer or table, and the CQs get the stock `cc=1, oi=1`.
- The host library's heap hook returns after one cached `getenv`.

Struct sizes are unchanged (static asserts). The ring counter reuses the 8 bytes of v1's
`mvars.ft_gtime`, which v1 wrote and never read (the capture time is in the mailbox record). The
table pointer takes 16 of the device state's reserved bytes. Measured flag-off latency equals v1
flag off (A3).

## A. Ring send CQs

### A1. Stock NVSHMEM with `cc=0` (re-run; the old "init hangs" ran with the lock-holding watch thread)

Hook `NVSHMEM_IBGDA_FAULT_CQ_COLLAPSED=0` creates the send CQs with `cc=0, oi=0`. Setup: flag off
(stock device code), GPU NIC handler (auto), no watch thread. The v2 driver prints phase markers,
and a host thread copies the IBGDA device state and the first 8 slots of the send CQs 8 s after
start if the first barrier has not returned (copies on a non-blocking stream; the hung kernel does
not block them). Results in `results/20260925_v2/cc0/` (v2 build) and `cc0_v1build/` (the v1 build,
copied md5-checked from `~/gi-bundle/nvshmem_ft`).

|---|--:|---|---|---|

| v1, `cc=0` | 1 | returned | never returned | killed at 45 s |

INITDIAG rc_to_peer slot 0 op_own=0x00 opcode=0x0 owner=0 wqe_counter=2

**[measured]** The barrier posted 6 WQEs and rang them. The NIC completed all of them and wrote
two success CQEs to slots 0 and 1 (`wqe_counter` 2 and 5), exactly as a ring CQ should.
**[from source, consistent]** `ibgda_poll_cq` waits on the `wqe_counter` of slot 0 only
(`cq->cqe` is never advanced), so `cons_idx` stays at 3 and the wait for index 6 spins forever.
With stock device code a ring CQ cannot get past NVSHMEM's first collective, so neither a
fault-free put/quiet nor a fault can be run on it. The old invalidated result (init hangs) is
confirmed, now without the watch-thread artifact and with the cause shown. The collapsed CQ is
not what hid the error CQEs (that was the CPU proxy's doorbell-record bug, `../nvshmem_rootcause/`).
Stock NVSHMEM simply cannot use a ring CQ; v2 makes it walk one.

### A2. Design (`NVSHMEM_IBGDA_FT_RING_CQ=1`)

**Mechanism.**
- The send CQs are created with `cc=0` and overrun-ignore (`oi=1`), as stock does for its CQs. The
  device never writes the CQ doorbell record.
- Each send CQ has a consumer counter `ci` in the QP's management variables (`mvars.ft_ring_ci`).
- A waiter reads word 15 of slot `ci & (ncqes-1)`, which holds `wqe_counter` and `op_own` in one
  32-bit load. Waiters are `ibgda_poll_cq` (for `nvshmem_quiet`, fence and the WQE-slot wait), the
  bounded quiet, and the sentinel if one runs.
- An entry is new if its opcode is not 0xf (the 0xff creation fill) and its owner bit equals
  `!!(ci & ncqes)` (mlx5 owner rule).

- **Success CQE:** consumed with `atomicCAS(ci, ci + 1)`. Only the CAS winner advances `cons_idx`:
  it reads `cons_idx` after the CAS and adds `d = (uint16)(wqe_counter + 1 - cons_idx)`.
  - Every CQE before k was claimed before the CAS and none after it, so `cons_idx <= w` (w = the
    CQE's WQE index).
  - Flow control writes WQE w only after `cons_idx > w - nwqes`, so `cons_idx >= w + 1 - nwqes`.
  - Hence `1 <= d <= nwqes <= 32768`, and the new `cons_idx` is exactly w + 1 across 16-bit
    wraps.
  - A slower winner of an earlier CQE lands its `atomicMax` as a no-op.
  - A wait returns as soon as its own index is reached. A later CQE, possibly an error of a later
    operation, is left to the next wait.
- **Error CQE: never consumed.**
  - The first error CQE in completion order is the root cause (0xf5 local flush, 0x88 REM_ACCESS,
    0x81 RETRY_EXC). The trailing 0xf9 flushes land in later slots.
  - The root cause stays at `ci`. Any wait that reaches it records it with the v1 capture code
    (sticky record + mailbox, `path` = that waiter, `ring_ci` in the record) and returns -1.
    Every later wait returns -1 at its first read.
  - No thread has to be polling when the error arrives, so there is no sentinel and no in-loop
    timing window.
- **Overwrite bound.** The root cause can only be overwritten when the ring laps it, which needs
  more than ncqes CQEs after it. Until an error is recorded, flow control keeps at most nwqes <=
  ncqes CQEs unconsumed. Once it is recorded, an overwrite no longer matters: every 256 empty
  spins a waiter also checks the QP's sticky record, for a recorded ring that fail-fast posting
  later reused.
- **Recovery.** A QP reset does not reset its CQ; the NIC's CQ producer counter keeps running.
  - Commit restarts `ci` at that counter (`QUERY_CQ.producer_counter`, 24 bits), not at 0.
  - The value is cross-checked with a host scan of the ring from the old `ci`, which counts the
    unconsumed error CQE and its flushes.
  - A disagreement that a ring wrap cannot explain declines the commit.
  - The management variables are then written from the host (zero, plus the new `ci`).
  - The 0xff refill is kept, but a ring does not need it: stale entries fail the owner-bit test
    (C).
- **Cost on the success path:** one extra 64-bit load (`ci`) per wait, and one CAS per consumed
  CQE (put+signal+quiet consumes one CQE per operation).

## B. Device bounds check

### Design (`NVSHMEM_IBGDA_FT_BOUNDS=1`)

**What NVSHMEM already knows.** The symmetric-heap allocator (`mspace`, default
`NVSHMEM_USE_DLMALLOC=OFF`) keeps `inuse_chunks`: start and size of every allocated chunk, sizes
rounded up to 512 B (`NVSHMEMI_MALLOC_ALIGNMENT`). This includes NVSHMEM's own internal
allocations. The heap is symmetric, so an offset from the heap base names the same chunk on every
PE.

**Mechanism.**
- **Table.** After every symmetric allocation and free, the host library passes its in-use chunks
  (offsets from `heap_base`) to the IBGDA transport (`nvshmemt_ibgda_ft_heap_objects`, found with
  `dlopen(RTLD_NOLOAD)` each time). The transport keeps a device table with one 32-bit entry per
  512 B granule of the heap: the end granule of the chunk that holds the granule, 0 if free. Here
  the heap is 54 MiB, so 110 592 entries (432 KiB), rebuilt and copied at each allocation or free,
  both of which are collective.
- **Check.** Before an RMA/AMO is posted, the dispatchers (`nvshmemi_ibgda_rma(_nbi)`,
  `_rma_p/_g`, `_amo_nonfetch/_fetch`, `_put_signal` for both the data and the signal word)
  require `off + len <= heap_size`, `table[off >> 9] != 0` and `off + len <= table[off >> 9] <<
  9`. That is one dependent global load per range.
- **On violation.**
  - Nothing is posted.
  - A library record goes to the sticky record of the RC QP to that peer and to the mailbox:
    kind 2, class `OOB_WRITE` (or `OOB_READ` for get/g), fingerprint opcode 0 / syndrome 0 / why
    (1 outside the heap, 2 starts in free heap, 3 runs past its chunk), plus offset, length,
    chunk end and operation.
  - `nvshmemx_ibgda_ft_status(pe)` reports it, and `nvshmemx_ibgda_ft_quiet_bounded` returns -1
    (it now checks the sticky record before its index test).
  - The QP stays healthy (`nvshmem_quiet` itself returns normally, as for every FT error).
  - The driver's policy declines, since an addressing bug is not a transport fault.
- **Red zone (`NVSHMEM_IBGDA_FT_BOUNDS_GUARD`).** Each allocation gets `guard` extra bytes, and the
  chunk is published without them, so an overrun that starts at an object's end starts in "free"
  granules.

**What it cannot catch.**
- Granularity is the allocator chunk, not the application's intent.
- A range that lies wholly inside another allocated object passes. That includes an overrun that
  jumps past the red zone into the next object.
- An overrun into the padding of the object's own chunk passes (sizes are rounded up to 512 B).
- The existing F2a fault (`dst = dbuf + bytes`, `len = bytes`) is the first case without a red
  zone: `dbuf` and `sbuf` are adjacent 256 KiB chunks (layout printed by the driver: `dbuf` +
  0x2124a00, `sbuf` + 0x2164a00), so the misdirected put is a well-formed put to all of `sbuf`.
- Only the static heap (`NVSHMEM_DISABLE_CUDA_VMM=1`, as here) was tested. External buffers
  registered as symmetric are outside the table and fall back to the heap-level check.

- **Canary.** PE1 fills the region outside `dbuf` that the bad put would hit with a canary before

## Measured vs inferred

- **Measured:** every table above, with per-trial logs and `.meta` (md5 of driver, transport and
  host library on rain; identical on sunny by deploy check). Also measured:
  - the cc=0 queue dumps;
  - the ring counters at every commit;
  - the canary and `dbuf` checks;
  - the knob failure modes (signal values, classes, decline reasons, watchdog exits);
  - the latency distributions;
  - the stress-test counters.
- **From source, consistent with the measurements:**
  - why stock `cc=0` hangs (slot 0 only);
  - the exactness argument for `cons_idx` in ring mode (also exercised by the stress test);
  - that the root cause cannot be overwritten before it is recorded (flow control);
  - that the NIC re-executed stale WQEs in the `idx` control (signal +52 = the old operations
    still in the ring);
  - why `dbr` had no effect (the device writes the record before ringing).
- **Inferred, not tested:**
  - ring mode with several RC QPs per peer, DCI traffic, or several NICs;
  - fail-fast posting of more than ncqes WQEs after a recorded error (then the periodic sticky
    check is what ends a wait);
  - bounds with the VMM heap or external symmetric buffers;
  - get/AMO rejections: the code covers them, but only put-with-signal was tested;
  - multi-threaded (warp/block-scope) rejections;
  - a `psn`/`dci`/`dbr` failure mode (none was provoked);
  - v2 flag off under faults: not re-run. By construction the flag-off device and host paths are
    v1's (plus the one flag test). Measured flag off: fault-free runs verified (`smoke/`,
    `final/`, `mt_off`), latency equal to v1 flag off, and the `cc=0` hang identical to the v1
    build.

## Limitations and open issues

- **Ring mode costs** +0.34 us per put+signal at 4 KiB (one CAS per CQE plus the counter load). It
  needs the GPU NIC handler, and it leaves the CQ's overrun check off (`oi=1`, as stock).
- **The bounds check is chunk-level.** Without a red zone it cannot catch the existing F2a fault;
  with one it catches overruns that start at an object's end, not overruns that jump past the red
  zone into another object. Its cost (+0.64 us at 4 KiB) is on the posting path of every RMA/AMO.
  The red zone changes the heap layout (and must be the same on every PE).
- The table is copied whole at every allocation or free. That is 432 KiB here and grows with the
  heap (4 B per 512 B).
- An OOB record leaves the QP healthy and is sticky: `status` and the bounded quiet report it
  until a commit clears it. There is no "clear only the OOB record" API; the policy declines.
- `nvshmem_quiet` still returns `void` (as in v1); a kernel must ask `nvshmemx_ibgda_ft_status`.
- **Driver race found and fixed.** In the forced d = 0 test the target can verify the operation
  and send ITER_OK before the REQ reaches it. The v1 driver's handshake loop dropped that message,
  so the initiator then waited 60 s for it (3/3 in ring mode: `ringrec/*ringd0*`, rc 8/4). The
  v1 d = 0 runs happened not to hit the race. The v2 driver keeps the message (`STASH`); re-run
  in `final/` (11/11, fix path taken 9 times). The library was not involved: both commits and the
  ring counters were consistent.
- One node pair, one firmware (20.43.4100), RoCE v2, IB timeout 14, one RC QP per PE.
