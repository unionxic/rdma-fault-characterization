# NVSHMEM IBGDA fault tolerance v2: ring send CQs, device bounds check, resync negative controls

Patch: `nvshmem_ibgda_ft_v2.diff`, a full diff against NVSHMEM `7bb2e99c` +
`../nvshmem/nvshmem_ibgda_fault_inject.diff` + `../nvshmem_rootcause/nvshmem_nrc_proxy_sq_dbr.diff`
(the same base as `nvshmem_ibgda_ft.diff`). It contains v1, so apply one or the other. v1 design:
`DESIGN.md`. v1 results: `README.md`. The base includes the default-off fix knob for the CPU-proxy
doorbell-record bug (`nvshmem_nrc_proxy_sq_dbr.diff`). That bug (the proxy writes the send
producer index into word 0 of the QP doorbell record instead of word 1) is a regression from
upstream commit ce9d487 (2025-10): NVSHMEM 3.4.5 is correct, and every release from 3.5.x through
3.8.0 (and `devel` 7bb2e99c, the base here) still has it (`../nvshmem_rootcause/README.md`).

v2 answers three review points:

- **A.** The `cc=0` (ring CQ) result was invalidated and never re-run. A ring CQ is the simplest
  fix for root-cause loss on the collapsed CQ, yet a heavier resident sentinel thread was chosen.
- **B.** An out-of-bounds write that stays inside the heap MR (silent corruption) ended as
  "undetectable".
- **C.** The recovery resync items had no negative controls, but the summary listed them as
  verified.

Design rule (the user's): detection and recovery live inside the library (transport and device
code), not in the application. Everything in v2 sits behind `NVSHMEM_IBGDA_FT=1`.

A second review raised four more points; they are answered in **v2.1** (section "v2.1: second
review", same patch file). v2.1 changes three things. After an error, a QP is **parked** (posts no
longer ring its doorbell). A broken ring-walk invariant is **recorded** instead of consumed
silently. The sentinel's role is restated (detection, not classification). Statements that v2.1
corrected are marked "(v2.1)" where they stand.

A third review re-checked park; it is answered in **v2.2** (section "v2.2: third review", same
patch file). Park is now restricted to QPs whose every post is a device-scope atomic (all RC QPs,
shared DCIs) and sets bit 63 with `atomicOr`. A fetch (AMO fetch, `g`) whose completion failed
returns a poison value instead of a stale one. The Prepare stats report the real 64-bit producer
index. Park is off with the `CAPTURE=exit` diagnostic, where it hung. Marked "(v2.2)" where earlier
text changed.

## TL;DR

- **A1, stock `cc=0` re-run (GPU handler, no watch thread):** stock NVSHMEM cannot run at all on
  non-collapsed send CQs. The first `nvshmem_malloc` never returns (6/6 runs, v1 and v2 builds,
  flag off). The NIC delivered every CQE, but the device poll reads slot 0 only. Dump taken while
  it hung (both PEs, 5/5 runs): 6 WQEs posted and rung, slot 0 = CQE `wqe_counter` 2, slot 1 = CQE
  `wqe_counter` 5, `cons_idx` stuck at 3. No fault-free put and no fault could be tested.
- **A2, ring mode in v2 (`NVSHMEM_IBGDA_FT_RING_CQ=1`):** the device walks the ring by consumer
  counter and never consumes an error CQE, so the root cause waits at the consumer position until
  a wait reaches it.
  - Capture: the pattern that defeated v1's in-loop read is put+signal, then 200 us or 2 ms of
    compute, then `nvshmem_quiet` (F1 and F2b, 30 trials per cell). Ring mode kept the root cause
    in **90/90**, v1's in-loop read in 0/90, the sentinel in 90/90. The ring needs no resident
    thread **to classify**. (v2.1) It does not detect early: the fault is recorded when the
    kernel's own wait reaches it, 1.9 ms after posting in that pattern, against 0.1 ms with a
    sentinel (v2.1 §3).
  - Concurrency: 32 threads quiescing on one QP, 100-300 iterations of 256 put+signal+quiet, 2
    wraps of the 16-bit `wqe_counter`. All 9 ring runs verified byte-exact.
  - Single-GPU stress test of the walker: passed 8/8 configurations (up to 4.2 M WQEs, 64
    `wqe_counter` wraps, 128 concurrent waiters), and failed as it must (2/2) when the ring
    precondition was violated.
  - Recovery works in ring mode: F1 18/18, F3 9/9, F1 x5 9/9, and forced d = 0 11/11 after a
    driver-race fix (the library was not involved). In 188/188 commits the ring counter was
    consistent.
- **A3, fault-free cost (put+signal+quiet p50, 6 runs x 10k ops per cell):** v2 flag off = v1 flag
  off (4 KiB 12.48 vs 12.51 us; 256 KiB 40.18 vs 40.29 us). Ring mode +0.34 us at 4 KiB (+2.7 %
  vs the v2 collapsed classifier), +0.37 us at 256 KiB (+0.9 %). (v2.1) Across five sessions the
  ring's extra cost at 4 KiB ranged +0.05-0.34 us. Collapsed classifier and sentinel as in v1
  (within 0.1 us of flag off).
- **B, bounds check (`NVSHMEM_IBGDA_FT_BOUNDS=1`):** detected and not posted in 30/30 for each
  overrun that leaves the object's allocator chunk: into a freed gap, across the object's end, past
  the last object. The canary outside the object and the object itself were intact in 90/90. A
  write past the heap end was caught too (5/5). The existing F2a fault (`dst = dbuf + bytes`) was
  **not** detected (0/30, corruption 30/30). `dbuf` and `sbuf` are adjacent 256 KiB chunks, so that
  write is a well-formed write to all of `sbuf`, and no address-range check can reject it. With an
  optional 512 B red zone after every allocation (`NVSHMEM_IBGDA_FT_BOUNDS_GUARD=512`), the same
  fault was detected in 30/30 (and in 5/5 in blocking mode) with nothing corrupted. Cost: +0.64 us
  per put+signal at 4 KiB (+5.1 %), +0.58 us at 256 KiB (+1.4 %). No false positive in any
  fault-free run with the check on: 18 verified runs (15 x 200 put+signal, 3 x 25 600 concurrent
  put+signal), 24 latency runs of 10k ops, plus init, barriers and teardown.
- **C, negative controls (N = 5 per knob, F1 recovery unless noted):**
  - Necessary (the run fails without the step): device indices, sticky record, collapsed-CQ 0xff
    refill, host error record, finalize barrier skip, and in ring mode the ring-counter resync.
    - indices: the NIC re-executed the old WQEs left in the send queue. That gave 52 duplicate
      signal ADDs (signal 104 vs 52) and a data mismatch, 5/5.
    - sticky record: every later wait failed at once, and the run was declined 5/5.
    - collapsed-CQ refill: the stale trailing flush was read as a new error, and the run was
      declined 5/5.
    - host error record: the next fault (REM_ACCESS) was reported as the stale LOCAL_QP_ERR and
      "recovered" 6 times before the round limit, 5/5.
    - finalize barrier skip: teardown hung, F2b 5/5 and F4 3/3.
    - ring-counter resync (ring mode): the replay wait expired, 5/5.
  - Not needed in these tests (recovered 5/5 without the step): `post_send_lock`, `ibuf`, the
    doorbell-record zeroing, the DCI reset (DCIs idle here), fresh PSNs (no stale packets here). The
    0xff refill is not needed in ring mode either (owner bit). The v1 summary's "verified" is
    corrected accordingly.
- **v2.1 (second review), measured:**
  - **Posting after an error:** 8 threads kept posting up to 16 384 WQEs per kernel after the
    fault (send CQ 1024). The root cause was recorded in 155/155 ring runs, before the ring could
    lap it (the one run where the ring did lap its slot had recorded it earlier).
  - **Park fix.** The test exposed a v2 defect: fail-fast posting pushed the doorbell up to 16
    queues past the NIC, the NIC stopped flushing, and 3/5 recoveries were declined at the drain.
    v2.1 **parks** a failed QP (posts no longer ring it; no instruction added to the post path).
    Then at most 1023 WQEs are rung after the error (130/130 ring runs), the ring cannot lap, the
    root CQE stays in its slot, and burst recoveries succeeded 10/10 (final build 5/5).
  - **Ring invariant:** a broken invariant is now a RING_INVARIANT record with an error in 32/32
    (0.1 ms; with recovery on, declined 6/6). The v2 behaviour (emulated) hung or expired silently in 8/8.
  - **Early detection:** with a ring and no sentinel, detection waits for the kernel's next wait
    (post -> mailbox 1.95 ms here). A sentinel gives 0.10 ms, and on the ring its poll interval no
    longer matters for correctness: a 100 us sentinel lost the root cause 0/30 on the ring and
    12/30 on the collapsed CQ. A sentinel is still needed when the gap between an error and the
    next wait on that QP is longer than the detection latency the job needs.
  - **Cost:** final v2.1 flag off = v1 flag off (4 KiB 12.50 vs 12.48 us, 256 KiB 40.16 vs
    40.29 us, same session).
- **v2.2 (third review), measured:**
  - **Scope:** every post on an RC QP is already a device-scope `atomicMax` (`ibgda_get_rc` always
    reports "shared"), so parking an RC QP from another CTA or kernel does not mix scopes. Only
    exclusive DCIs post with `atomicMax_block`; v2.2 never parks them. Test with 4 CTAs posting on one RC QP and the sentinel kernel on: root cause kept 90/90,
    recoveries exact 80/80, with the park done by the sentinel kernel (37) or a posting CTA (43),
    in 68/80 while other CTAs were still posting.
  - **Fetches on a failed QP:** v2.1 returned a stale value (the ticket of the fetch 1024
    operations earlier: 456 125 stale values in 35 runs, parked or not), no hang, except with
    `CAPTURE=exit`, where park hung 5/5. v2.2 returns poison (all bits 1) and counts it: 0 stale in
    38 runs, no hang; flag-off fetch latency 9.888 vs 9.904 us.
  - **Stats:** a parked QP's `prod_before` read 0; now the real 64-bit index plus a parked flag.

| `NVSHMEM_IBGDA_FT_TEST_TRIP=ring_d:<n>` / `ring_d_silent:<n>` | unset | (v2.1) test-only: the n-th consumed ring CQE fails the ring-walk invariant: record + error, or v2's silent consumption. Ring mode only. |

**Flag off** (`NVSHMEM_IBGDA_FT` unset) behaves as v1 flag off. The only new work is one
`__constant__` flag test per RMA/AMO call (`state->ft_flags & BOUNDS`, 0 when off). (v2.1) Park
adds nothing to the post path: it only runs in the FT capture path. A first version tested a flag
per doorbell and cost +0.14 us at 4 KiB; it was replaced (v2.1 latency table). (v2.2) The fetch and
`g` paths do one more `__constant__` test (`state->ft`) after their wait (fetch p50 9.904 vs
9.888 us on v2.1, flag off). Otherwise:

- The device poll reads the same `state->ft` pointer (NULL) and takes the stock loop.
- The host creates no thread, buffer or table, and the CQs get the stock `cc=1, oi=1`.
- The host library's heap hook returns after one cached `getenv`.

Struct sizes are unchanged (static asserts). The ring counter reuses the 8 bytes of v1's
`mvars.ft_gtime`, which v1 wrote and never read (the capture time is in the mailbox record). The
table pointer takes 16 of the device state's reserved bytes. Measured flag-off latency equals v1
flag off (A3).

## A. Ring send CQs

### A1. Stock NVSHMEM with `cc=0` (re-run; the old "init hangs" ran with the lock-holding watch thread)

and a host thread copies the IBGDA device state and the first 8 slots of the send CQs 8 s after
start if the first barrier has not returned (copies on a non-blocking stream; the hung kernel does
not block them). Results in `results/20260925_v2/cc0/` (v2 build) and `cc0_v1build/` (the v1 build,

|---|--:|---|---|---|

**[measured]** The barrier posted 6 WQEs and rang them. The NIC completed all of them and wrote
two success CQEs to slots 0 and 1 (`wqe_counter` 2 and 5), exactly as a ring CQ should.
**[from source, consistent]** `ibgda_poll_cq` waits on the `wqe_counter` of slot 0 only
(`cq->cqe` is never advanced), so `cons_idx` stays at 3 and the wait for index 6 spins forever.
With stock device code a ring CQ cannot get past NVSHMEM's first collective, so neither a
fault-free put/quiet nor a fault can be run on it. The old invalidated result (init hangs) is
confirmed, now without the watch-thread artifact and with the cause shown. The collapsed CQ is
not what hid the error CQEs. That was the CPU-proxy doorbell-record bug (the proxy writes the
send producer index into word 0 of the QP doorbell record instead of word 1), a regression from
upstream commit ce9d487 (2025-10): NVSHMEM 3.4.5 is correct, and every release from 3.5.x through
3.8.0 (and `devel` 7bb2e99c, the base here) still has it (`../nvshmem_rootcause/README.md`).
Stock NVSHMEM simply cannot use a ring CQ; v2 makes it walk one.

### A2. Design (`NVSHMEM_IBGDA_FT_RING_CQ=1`)

**Mechanism.**
- The send CQs are created with `cc=0` and overrun-ignore (`oi=1`), as stock does for its CQs. The
  device never writes the CQ doorbell record.
- Each send CQ has a consumer counter `ci` in the QP's management variables (`mvars.ft_ring_ci`).
- A waiter reads word 15 of slot `ci & (ncqes-1)`, which holds `wqe_counter` and `op_own` in one
  32-bit load. Waiters are `ibgda_poll_cq` (for `nvshmem_quiet`, fence and the WQE-slot wait), the
  bounded quiet, and the sentinel if one runs.
- An entry is new if its opcode is not 0xf (the 0xff creation fill) and its owner bit equals
  `!!(ci & ncqes)` (mlx5 owner rule).

- **Success CQE:** consumed with `atomicCAS(ci, ci + 1)`. Only the CAS winner advances `cons_idx`:
  it reads `cons_idx` after the CAS and adds `d = (uint16)(wqe_counter + 1 - cons_idx)`.
  - Every CQE before k was claimed before the CAS and none after it, so `cons_idx <= w` (w = the
    CQE's WQE index).
  - Flow control writes WQE w only after `cons_idx > w - nwqes`, so `cons_idx >= w + 1 - nwqes`.
  - Hence `1 <= d <= nwqes <= 32768`, and the new `cons_idx` is exactly w + 1 across 16-bit
    wraps.
  - (v2.1) A d outside 1..ncqes means the invariant is broken. It is recorded (class
    RING_INVARIANT) and fails this and every later wait on the QP. v2 consumed the CQE silently,
    which left the waiter spinning (v2.1 §2).
  - A slower winner of an earlier CQE lands its `atomicMax` as a no-op.
  - A wait returns as soon as its own index is reached. A later CQE, possibly an error of a later
    operation, is left to the next wait.
- **Error CQE: never consumed.**
  - The first error CQE in completion order is the root cause (0xf5 local flush, 0x88 REM_ACCESS,
    0x81 RETRY_EXC). The trailing 0xf9 flushes land in later slots.
  - The root cause stays at `ci`. Any wait that reaches it records it with the v1 capture code
    (sticky record + mailbox, `path` = that waiter, `ring_ci` in the record) and returns -1.
    Every later wait returns -1 at its first read.
  - No thread has to be polling when the error arrives, so there is no sentinel and no in-loop
    timing window **for classification**. (v2.1) The fault is still recorded only when a thread
    polls the CQ; early detection needs a poller (v2.1 §3).
- **Overwrite bound.** The root cause can only be overwritten when the ring laps it, which needs
  more than ncqes CQEs after it. Until an error is recorded, flow control keeps at most nwqes <=
  ncqes CQEs unconsumed. Once it is recorded, an overwrite no longer matters: every 256 empty
  spins a waiter also checks the QP's sticky record, for a recorded ring that fail-fast posting
  later reused. (v2.1) Measured with up to 16 383 WQEs posted after the fault: recorded 155/155,
  including one run (without park) where the ring did lap its slot. v2.1 also parks a failed QP,
  so after an error at most nwqes - 1 more WQEs reach the NIC (1023 measured, 130/130 runs) and
  the ring cannot lap at all (v2.1 §1).
- **Recovery.** A QP reset does not reset its CQ; the NIC's CQ producer counter keeps running.
  - Commit restarts `ci` at that counter (`QUERY_CQ.producer_counter`, 24 bits), not at 0.
  - The value is cross-checked with a host scan of the ring from the old `ci`, which counts the
    unconsumed error CQE and its flushes.
  - A disagreement that a ring wrap cannot explain declines the commit.
  - The management variables are then written from the host (zero, plus the new `ci`).
  - The 0xff refill is kept, but a ring does not need it: stale entries fail the owner-bit test
    (C).
- **Cost on the success path:** one extra 64-bit load (`ci`) per wait, and one CAS per consumed
  CQE (put+signal+quiet consumes one CQE per operation).

### A2 results. Root-cause capture when the kernel computes between posting and waiting

The pattern that defeated v1's in-loop read (DESIGN §2): put+signal, then 200 us or 2 ms of
`clock64` compute, then `nvshmem_quiet` + `nvshmemx_ibgda_ft_status` (blocking mode, the
`capture_blocking` study of v1). Classification-only runs (the fault is declined), trials
interleaved across cells, 30 per cell. "Root cause kept" means the recorded class is the true one:
LOCAL_QP_ERR 5/0xf5 for F1, REM_ACCESS 10/0x88 for F2b. Collapsed in-loop and sentinel are the v2
build with `RING_CQ` unset (v1 code path).

- **[measured]** With the ring, the root cause (5/0xf5, or 10/0x88) was still at the consumer
  position when the wait started after the compute, and it was recorded then. With the collapsed
  CQ it had been overwritten by the trailing flush 5/0xf9 in every trial. The sentinel records it

## B. Device bounds check

### Design (`NVSHMEM_IBGDA_FT_BOUNDS=1`)

**What NVSHMEM already knows.** The symmetric-heap allocator (`mspace`, default
`NVSHMEM_USE_DLMALLOC=OFF`) keeps `inuse_chunks`: start and size of every allocated chunk, sizes
rounded up to 512 B (`NVSHMEMI_MALLOC_ALIGNMENT`). This includes NVSHMEM's own internal
allocations. The heap is symmetric, so an offset from the heap base names the same chunk on every
PE.

**Mechanism.**
- **Table.** After every symmetric allocation and free, the host library passes its in-use chunks
  (offsets from `heap_base`) to the IBGDA transport (`nvshmemt_ibgda_ft_heap_objects`, found with
  `dlopen(RTLD_NOLOAD)` each time). The transport keeps a device table with one 32-bit entry per
  512 B granule of the heap: the end granule of the chunk that holds the granule, 0 if free. Here
  the heap is 54 MiB, so 110 592 entries (432 KiB), rebuilt and copied at each allocation or free,
  both of which are collective.
- **Check.** Before an RMA/AMO is posted, the dispatchers (`nvshmemi_ibgda_rma(_nbi)`,
  `_rma_p/_g`, `_amo_nonfetch/_fetch`, `_put_signal` for both the data and the signal word)
  require `off + len <= heap_size`, `table[off >> 9] != 0` and `off + len <= table[off >> 9] <<
  9`. That is one dependent global load per range.
- **On violation.**
  - Nothing is posted.
  - A library record goes to the sticky record of the RC QP to that peer and to the mailbox:
    kind 2, class `OOB_WRITE` (or `OOB_READ` for get/g), error code fields opcode 0 / syndrome 0 / why
    (1 outside the heap, 2 starts in free heap, 3 runs past its chunk), plus offset, length,
    chunk end and operation.
  - `nvshmemx_ibgda_ft_status(pe)` reports it, and `nvshmemx_ibgda_ft_quiet_bounded` returns -1
    (it now checks the sticky record before its index test).
  - The QP stays healthy (`nvshmem_quiet` itself returns normally, as for every FT error).
  - The driver's policy declines, since an addressing bug is not a transport fault.
- **Red zone (`NVSHMEM_IBGDA_FT_BOUNDS_GUARD`).** Each allocation gets `guard` extra bytes, and the
  chunk is published without them, so an overrun that starts at an object's end starts in "free"
  granules.

**What it cannot catch.**
- Granularity is the allocator chunk, not the application's intent.
- A range that lies wholly inside another allocated object passes. That includes an overrun that
  jumps past the red zone into the next object.
- An overrun into the padding of the object's own chunk passes (sizes are rounded up to 512 B).
- The existing F2a fault (`dst = dbuf + bytes`, `len = bytes`) is the first case without a red
  zone: `dbuf` and `sbuf` are adjacent 256 KiB chunks (layout printed by the driver: `dbuf` +
  0x2124a00, `sbuf` + 0x2164a00), so the misdirected put is a well-formed put to all of `sbuf`.
- Only the static heap (`NVSHMEM_DISABLE_CUDA_VMM=1`, as here) was tested. External buffers
  registered as symmetric are outside the table and fall back to the heap-level check.

### 1. Posting after the error: can the ring lap the root cause?

**Argument (`ibgda_ft_ring_poll` header).**
- After an error, `cons_idx` stops at the failing WQE, because error CQEs are never consumed.
- A WQE with index >= `cons_idx` + nwqes can only be reserved after the slot wait
  (`ibgda_wait_for_slot_availability`) has polled the ring.
- That poll records the root cause before it returns -1 and lets posting go on.
- So at most nwqes CQEs are written from the root cause on before it is recorded, and its slot
  is rewritten only by the CQE ncqes later.
- nwqes = ncqes = `round_up_pow2(QP_DEPTH)` = 1024 here; v2.1 checks it at init (a ring QP
  with nwqes > ncqes fails the connect).

### 2. Ring-walk invariant: record instead of a silent hang

`d` is the advance the CAS winner computes for a consumed success CQE (A2 design). If it falls
outside 1..ncqes, the invariant is broken (a bug or memory corruption). v2 then consumed the CQE
without advancing `cons_idx` and without a trace, so a waiter that needed that completion spun
forever. v2.1 instead does five things:
- records class RING_INVARIANT (kind 3; sticky record with opcode 0xf, class 18);
- writes a mailbox record (ring counter, `wqe_counter`, `cons_idx`, d, bound);
- returns -1 from that wait;
- because of the 0xf opcode, fails every later wait on the QP (at the next 256-spin check or the
  bounded quiet's first check; from the code, not exercised: the driver stops at the first failed
  wait);
- parks the QP (§1).

The host logs `device ring-walk invariant violated ... d=0 (valid 1..1024)`. Policy: decline
(a recovery commit would reset the ring); measured 6/6 with recovery on.

Test knob (test-only): `NVSHMEM_IBGDA_FT_TEST_TRIP=ring_d:<n>` forces d = 0 at the n-th consumed
ring CQE of the PE. `ring_d_silent:<n>` emulates v2 (silent consumption). Runs: n = 100,
put+signal+wait, ring mode; the trip lands on iteration 89.

- **[measured] The ring replaces the sentinel for classification, not for early detection.**
  Without a poller the root cause is recorded (30/30, 30/30) only when the kernel's own wait
  reaches it: 1.95 ms after posting here, the length of the compute. A sentinel records it on

  record (the same `clock64` budget ran 1.9 ms at this session's SM clock).
- **With the ring, the sentinel's poll interval only bounds detection latency, not correctness.**
  A 100 us sentinel kept the root cause in 30/30 on the ring. On the collapsed CQ it lost it in
  12/30 (18/30 kept), because the trailing flush overwrites the slot within ≈60 us.
- **When a sentinel (or another poller) is still needed.** In ring mode a fault is recorded at
  the first poll of that QP's CQ after the error CQE arrives: a quiet or fence, a slot wait when
  the send queue is full, or the bounded quiet. Without a sentinel, detection latency = the time
  from the error to that poll. A sentinel is needed when that gap is longer than the detection
  latency the job needs, for example:
  - kernels that post and then compute for long before they wait;
  - kernels that post nbi and leave the quiet to a later kernel or to teardown;
  - QPs nobody waits on.
  In those cases the host would otherwise learn of the fault only at the next wait, so recovery
  or peer notification cannot overlap the compute. When every post is followed soon by a wait,
  no sentinel is needed, and the root cause is kept either way.

### 1. Park and the memory-model scope

**Where the scopes differ.** Every read-modify-write of `tx_wq.prod_idx` in the device code, and
its scope:

| access | scope | QPs it runs on |
|---|---|---|
| `ibgda_post_send<true>`, `ibgda_proxy_post_send<true>`: `atomicMax` | device (`.gpu`) | every QP that `ibgda_get_*` reports as shared among CTAs |
| `ibgda_post_send<false>`, `ibgda_proxy_post_send<false>`: `atomicMax_block` | block (`.cta`) | only QPs reported as not shared |
| `ibgda_submit_ready` (bounded quiet): `ibgda_post_send<true>` | device | RC |
| park (v2.1 `atomicMax`, v2.2 `atomicOr`) | device | the QP whose error was recorded, from any CTA or kernel |
| recovery (host `cudaMemcpy` of the management variables) | - | only while prepare found the QP quiescent (no kernel posting) |

- `ibgda_get_rc` sets `*out_shared_among_ctas = true` unconditionally (so do the qp_index APIs and
  `ibgda_get_amo_qp`'s RC branch). So **every post on an RC QP is a device-scope `atomicMax`**, and a
  device-scope park from the sentinel kernel or from another CTA is scope-compatible: all RMWs on
  the word are morally strong, and their single modification order gives the park semantics
  (a post before the park rings; every post after it sees a larger old value and does not).
- The not-shared (block-scope) path exists only for **exclusive DCIs**: `ibgda_get_dci` returns
  `shared = false` only under the CTA or WARP DCI map for an index below `num_exclusive_dcis`. On
  those, a park from another CTA or kernel would mix scopes on one address. It could happen: the
  sentinel polls every DCI CQ, and so does every CTA's `nvshmem_quiet` (it quiets all DCIs).
  (Stock NVSHMEM already mixes scopes there: `nvshmem_quiet` posts a CST WQE on every DCI with
  `ibgda_cst(qp, true)`, a device-scope `atomicMax`, while the owning CTA uses `atomicMax_block`.)

**Choice: park only QPs whose post path is device-scope** (option "park only from a context whose
scope matches", made explicit). `ibgda_ft_park` returns without parking for a DCI with index <
`num_exclusive_dcis` under the CTA or WARP DCI map. Every QP it parks is posted with device-scope
atomics only, from any CTA. Why this and not the alternatives:
- no instruction on any post path (a separate park word would add a load to every doorbell; forcing
  exclusive DCIs to device scope would change the stock post path);
- the RC QPs, the ones FT recovers, are unchanged;
- cost: an exclusive DCI with a recorded error keeps the v2 behaviour (fail-fast posts reach the
  NIC and are flushed). Classification is unaffected; recovery does not cover DCI traffic anyway.
- Park is now `atomicOr(bit 63)` instead of `atomicMax(2^63)`: same effect on posts, but the low
  63 bits keep the last rung index (item 3).

**Test** (`v21g_after3/`, final v2.2 driver): 4 CTAs x 8 threads post put+signal (512 B each) on

### 2. Fetch AMOs (and `g`) on a failed or parked QP

  - why `dbr` had no effect (the device writes the record before ringing);
  - (v2.2) that park never mixes atomic scopes: every RMW of an RC QP's `prod_idx` is a
    device-scope atomic (`ibgda_get_rc` always reports "shared"), and exclusive DCIs are not parked.
    Exercised on RC with the park done by the sentinel kernel and by other CTAs (v2.2 §1).
- **Inferred, not tested:**
  - ring mode with several RC QPs per peer, DCI traffic, or several NICs;
  - bounds with the VMM heap or external symmetric buffers;
  - get/AMO rejections: the code covers them, but only put-with-signal was tested;
  - multi-threaded (warp/block-scope) rejections;
  - a `psn`/`dci`/`dbr` failure mode (none was provoked);
  - (v2.1) that a RING_INVARIANT record fails every later wait on the QP (the driver stops at the
    first failed wait), and a real invariant violation (only forced by the test knob);
  - (v2.1) why the NIC stopped flushing when the doorbell ran queues ahead (Limitations);
  - (v2.1) park with several QPs per peer or DCIs (one RC QP per PE here); (v2.2) the
    exclusive-DCI exemption (no DCI traffic here);
  - (v2.2) the poison of `nvshmem_g`, of a bounds-rejected fetch, and of a fetch that failed with
    RETRY_EXC (only AMO fetch-add under F1 was run);
  - v2 flag off under faults: not re-run. By construction the flag-off device and host paths are
    v1's (plus the one flag test). Measured flag off: fault-free runs verified (`smoke/`,
    `final/`, `mt_off`), latency equal to v1 flag off, and the `cc=0` hang identical to the v1
    build.

## Limitations and open issues

- **Ring mode costs** +0.05-0.34 us per put+signal at 4 KiB across five sessions (one CAS per CQE
  plus the counter load). It
  needs the GPU NIC handler, and it leaves the CQ's overrun check off (`oi=1`, as stock).
- **The bounds check is chunk-level.** Without a red zone it cannot catch the existing F2a fault;
  with one it catches overruns that start at an object's end, not overruns that jump past the red
  zone into another object. Its cost (+0.64 us at 4 KiB) is on the posting path of every RMA/AMO.
  The red zone changes the heap layout (and must be the same on every PE).
- The table is copied whole at every allocation or free. That is 432 KiB here and grows with the
  heap (4 B per 512 B).
- An OOB record leaves the QP healthy and is sticky: `status` and the bounded quiet report it
  until a commit clears it. There is no "clear only the OOB record" API; the policy declines.
- `nvshmem_quiet` still returns `void` (as in v1); a kernel must ask `nvshmemx_ibgda_ft_status`.
- **Driver race found and fixed.** In the forced d = 0 test the target can verify the operation
  and send ITER_OK before the REQ reaches it. The v1 driver's handshake loop dropped that message,
  so the initiator then waited 60 s for it (3/3 in ring mode: `ringrec/*ringd0*`, rc 8/4). The
  v1 d = 0 runs happened not to hit the race. The v2 driver keeps the message (`STASH`); re-run
  in `final/` (11/11, fix path taken 9 times). The library was not involved: both commits and the
  ring counters were consistent.
- (v2.1) **Parking drops posts on a failed QP.** They still reserve and fill WQEs (`resv_head`,
  `ready_head`) but never reach the NIC. That is invisible to the operation's outcome (a failed QP flushes them), but a
  hypothetical consumer that inspects flush CQEs of the later WQEs would not get them.
- (v2.1) **Why the NIC stopped flushing is not known.** When the doorbell producer ran more than
  a queue ahead of its flush point, it stopped (counters in v2.1 §1), on this firmware. Parking
  withholds only the doorbell: the device still writes the later WQEs into send-queue slots the NIC
  may not have flushed yet. Yet in all 10 parked ring recoveries the NIC wrote exactly one CQE per
  rung WQE from the root cause on (`QUERY_CQ` - old `ci` = WQEs rung after the root + 1), and all
  15 parked burst recoveries (ring and collapsed) drained. So the doorbell running ahead, not the
  slot overwrite alone, is the likely trigger (inferred). Nothing
  depends on the NIC's behaviour beyond a queue.
- (v2.2) **An exclusive DCI is not parked.** It keeps v2's fail-fast posting after an error
  (posts reach the NIC and are flushed), so the NIC stall of v2.1 §1 remains possible there.
- (v2.2) **A poisoned fetch means "result unknown", and is conservative.** When the fault cuts a
  warp-coalesced batch, the AMOs of that batch that did execute are poisoned too (v2.1 returned
  their correct values: 130 in 10 ring T = 32 runs). The poison value (all bits 1) can also be a
  legitimate value; an application that needs certainty checks `nvshmemx_ibgda_ft_status` (or
  the counter) after the fetch, as for `nvshmem_quiet`.
- (v2.1) **Early detection still needs a poller** when the gap between an error and the next wait
  on that QP is longer than the detection latency the job needs: long compute between posting
  and waiting, the quiet deferred to a later kernel, or QPs nobody waits on (v2.1 §3).
- One node pair, one firmware (20.43.4100), RoCE v2, IB timeout 14, one RC QP per PE.
