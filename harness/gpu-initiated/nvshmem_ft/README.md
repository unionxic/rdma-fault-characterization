# nvshmem_ft: NVSHMEM IBGDA 장애 분류와 복구

NVSHMEM IBGDA(GPU 핸들러)에 장애 대응을 라이브러리 안에 넣었다. GPU가 원인 CQE를 분류해 호스트에 알리고, 일시적 장애는 해당 QP만 다시 세워 복구한다.
GIN에서 만든 GPU 쪽 오류 분류와 복구 방식을 NVSHMEM으로 옮긴 것이다.
기능은 기본으로 꺼져 있고, 끄면 원래 NVSHMEM과 같게 동작한다.

## 무엇을 쟀나

- **장애 5가지.** 로컬 QP 오류, 잘못된 rkey, 상대 QP 오류, 상대 프로세스 kill, MR 안쪽으로 넘친 쓰기(v2). 대기는 blocking(quiet)과 시간 제한 두 방식.
- **장애 대응판 v1(2026-09-24).** 분류, 복구, 장애 5번 연속, 원인을 읽는 위치, 기능을 끈 대조, 지연. 조건마다 3회, 연속 장애는 5회.
- **30회 재실행(2026-09-25).** v1의 분류, 복구, 거절을 조건마다 30회(거절과 연속 장애는 10회), 모두 220회.
- **장애 대응판 v2 계열(2026-09-25).** 링 CQ, 원격 주소 경계 검사, 재설정 단계별 음성 대조(단계마다 5회). v2.1과 v2.2는 리뷰 지적을 반영한 판이다.
- **조건.** rain(시작)과 sunny(대상), ConnectX-6 RoCE v2, IB 타임아웃 14, PeerMappingOverride 켬(GPU 핸들러), PE당 RC QP 1개.

## 결론

- **분류가 정확하다.** 첫 기록이 진짜 원인이었다.
  - 로컬 QP 오류 5/0xf5, 잘못된 rkey 10/0x88, 상대 QP 오류와 상대 프로세스 kill 12/0x81. GPU 기록에서 호스트가 읽기까지 중앙값 67 µs다(v1).
  - 로컬 QP 오류의 감지 시간은 대부분 다음 put을 기다린 시간이다. 장애가 작업 사이에 떨어지기 때문이다.
- **슬롯을 어디서 읽느냐가 분류를 정한다.** collapsed CQ에서는 뒤따르는 flush(5/0xf9)가 원인 CQE를 곧 덮는다.
  - 원래 대기가 끝나는 지점에서 읽으면 모두 flush였다. 대기 루프 안에서 읽으면 30회 중 21회 원인을 읽었다.
  - post와 대기 사이에 계산이 0.2–2 ms 끼면 루프 안 읽기는 원인을 하나도 읽지 못했다. 상주 감시 스레드(CQ만 계속 지켜보는 GPU 스레드)와
    링 CQ(v2)는 이때도 모두 읽었다.
- **일시적 장애는 잃거나 겹치는 작업 없이 복구된다.** 로컬 QP 오류와 상대 QP 오류는 모든 시행에서 복구됐다.
  - 매 시행 200개 작업이 비트 단위로 맞고 신호값도 정확했다. 복구 중에 다시 장애가 난 경우도 포함한다.
  - 커널이 돌아온 뒤 복구까지 약 3 ms다(v1 중앙값 3.08 ms, 2.69–5.67).
- **복구할 수 없는 장애는 거절하고 종료한다.** 잘못된 rkey(원격 접근 오류라 복구 대상 아님)와 상대 프로세스 kill(상대 죽음)은 거절됐다.
  - 상대 QP 오류와 상대 프로세스 kill은 오류 코드가 같다. OOB 소켓의 연결 끊김(FIN)으로만 가른다.
  - finalize는 v1에서 살아 있는 PE 모두 17–29 ms에 돌아왔고, 30회 재실행에서도 시작 쪽 PE0이 모두 돌아왔다. 원래 NVSHMEM은 여기서 멈춘다.
- **경계 검사(v2)는 객체 밖으로 넘친 쓰기를 보내기 전에 막는다.** 빈 틈, 경계 걸침, 마지막 객체 뒤로 쓰기를 모두 잡았다.
  - 바로 옆 객체로 넘친 쓰기(MR 안쪽으로 넘친 쓰기)는 경계 검사만으로는 잡지 못한다. 옆 객체에 정상으로 쓰는 것과 구분되지 않는다.
  - 512 B red zone을 두면 이 쓰기도 잡고, 아무것도 쓰이지 않는다.
- **기능을 끈 같은 빌드는 원래 NVSHMEM과 같다.** blocking 대기가 실패한 put을 성공으로 알렸고, 종료는 멈췄다. 기능을 켠 v1의 지연 비용은 4 KiB에서 +0.12 µs(1%)다.

## 한계와 주의

- **quiet는 여전히 결과값이 없다.** 커널은 장애 대응 상태 API를 따로 물어야 한다. barrier와 집합 연산은 오류 뒤 돌아오지만 오류를 전하지 않는다(소스로만 확인).
- **finalize가 돌아오는 것은 앱의 거절 경로가 중단 API를 부를 때뿐이다.** 종료 때 barrier를 건너뛰는 단계를 빼면 종료가 멈췄다(잘못된 rkey 5회, 상대 프로세스 kill 3회 모두). "finalize 17–29 ms"는 이 조건에서만 맞다.
- **루프 안 분류는 그 순간 대기 중인 스레드가 있어야 한다.** 없으면 상주 감시 스레드나 링 CQ가 필요하다.
  - 링 CQ는 분류만 지킨다. 빠른 감지는 아니다. 다음 대기 때 기록된다(이 패턴에서 post 뒤 1.95 ms, 상주 감시 스레드는 0.10 ms).
  - 상주 감시 스레드는 GPU 스레드 하나를 계속 쓰고, 실행 순서와 종료에 제약이 있다.
- **재설정 단계 중 꼭 필요한 것은 6가지였다.** 단계를 하나씩 빼 보니 나머지 5가지는 이 시험에서 효과가 없었다. v1의 "모두 검증됨"은 묶음으로만 확인된 것이다.
- **v2.1은 실패한 QP의 fetch에서 옛 값을 오류 없이 돌려줬다.** 일반 모드 35회 모두에서 456,125개였다.
  진단 모드 5회를 더한 40회로는 510,028개다(3회는 멈춰 값이 없음). v2.2는 모든 비트가 1인 표시값을 돌려준다(38회, 옛 값 0).
  v1도 같았다는 것은 추론이다. v1에서는 fetch를 돌리지 않았다.
- **v2.2는 일부만 다시 쟀다.** "상주 감시 스레드 없이 90/90"은 v2 빌드 결과다. 상대 QP 오류, 상대 프로세스 kill의 분류, 복구, 거절은 v2.2에서 다시 돌리지 않았다.
  이후 투명 복구 마무리 실험에서 v2.2로 다시 쟀다. 상대 QP 오류는 5회 모두 복구, 상대 프로세스 kill은 5회 모두 거절됐다.
- **GPU 핸들러만 된다.** 고치지 않은 CPU 프록시는 오류 기록조차 없고, 고친 프록시는 복구를 거절한다(각 2회만 확인).
- **대상 PE는 스스로 오류를 보지 못한다.** 시작 쪽이 OOB 소켓으로 알려 준다.
- **범위가 좁다.** 노드 한 쌍, 펌웨어 하나, RoCE v2, PE당 RC QP 1개, 한 번에 작업 하나. DCI 트래픽, 여러 QP, 여러 NIC, 3개 이상 PE는 재지 않았다.
- **30회 재실행은 펌웨어 명령 슬롯 하나가 샌 상태에서 돌았다.** 09-25 06:45에 GIN 투명 복구 1단계 측정 중 rain NIC의 슬롯 하나가 샜고,
  NVSHMEM 30회 재실행은 07:04–07:31에 돌았다. 영향은 따로 재지 않았다.
- **NVSHMEM 투명 복구의 첫 결과는 사전 등록 전의 기록이다.** 남은 항목 일부는 투명 복구 마무리 실험에서 사전 등록 실험으로
  닫았고(2026-10-07), 공식 3.8.0으로 옮겨 다시 쟀다(2026-10-08).
