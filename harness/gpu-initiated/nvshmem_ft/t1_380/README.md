# t1_380: NVSHMEM 투명 복구를 공식 3.8.0으로 옮기기

NVSHMEM 투명 복구의 결과는 지금까지 모두 devel `7bb2e99c`(GitHub 미러의 중간 snapshot)에서 나왔다. 같은 변경을 공식 release
v3.8.0-0에 옮겨, 같은 결과가 나오는지 측정 전에 고정한 예측으로 쟀다(태그 `prereg/nvshmem-t1-380-v1`).

## 무엇을 쟀나

- **옮긴 것:** 투명 복구 마무리 실험 빌드의 전체 변경을 공식 v3.8.0-0에 붙였다. 한 군데(`barrier.cpp`의 include 부분)만 손으로 맞췄다.
  NVSHMEM 이슈 #117의 두 줄 수정은 넣지 않았다. 투명 복구는 GPU 처리 방식에서만 켜지므로 그 버그와 무관하다.
- **잰 것:** 200회.
  - 재현 조건: 장애 없음, 작업 중 로컬 QP 오류, 상대 QP 오류, fetch 세 조건, heap 밖 쓰기 거절, 상대 kill 거절, finalize 없는 종료,
    QP 4개, 스위치 끈 대조.
  - 같은 측정 시간대에 devel 빌드로 같은 조건을 돌려 복구 시간을 비교했다.
  - CPU 프록시 조건을 새로 넣었다.
  - 장애 없는 지연은 공식 3.8.0 그대로와 devel 빌드를 기준으로 쟀다(120회).

## 결론

- **투명 복구는 공식 3.8.0에서도 같은 장애 동작을 보였다.** 장애 동작 예측 15개가 모두 맞았다.
  - 투명, 거절, finalize 없는 종료, QP 4개, 스위치 끈 대조가 devel과 같았다.
  - 같은 측정 시간대의 복구 시간 차이는 0.37 ms였다(중앙값 4.79 대 4.42 ms).
  - 이제 NVSHMEM 투명 복구 결과를 공식 release 기준으로 말할 수 있다.
- **CPU 프록시에서는 여전히 오류 완료가 오지 않는다.** 투명 복구는 꺼진 채였고, 장애 뒤 오류 완료가 0개였다.
  #117 수정이 공개되기 전에는 GPU 처리 방식에서만 쓸 수 있다.
- **장애 없는 지연은 예측과 달랐다(예측 3개 틀림).**
  - 투명 복구를 켠 지연은 두 빌드가 같았다.
  - 기능을 끈 이식 빌드가 4 KiB에서 0.67 µs 느렸고, 원인은 모른다.
  - 공식 3.8.0 그대로가 devel 기준보다 256 KiB에서 0.51 µs 빨랐다.

## 결과

| 조건 | 결과 | 예측 |
|---|---|---|
| 작업 중 로컬 QP 오류, 이식 / devel | 10/10, 10/10 투명. 복구 중앙값 4.79 / 4.42 ms | 맞음 |
| 상대 QP 오류, fetch 세 조건 | 모두 투명, fetch 값과 카운터 정확 | 맞음 |
| heap 밖 쓰기, 상대 kill | 5/5, 5/5 거절, 정리 22–26 ms | 맞음 |
| finalize 없는 종료, QP 4개 | 5/5, 5/5 투명 | 맞음 |
| CPU 프록시 | 10/10 투명 복구 꺼짐, 오류 완료 0 | 맞음 |
| 지연: 이식 대 devel, 공식 그대로 대 devel 기준, 이식 비용 | 4개 비교 중 1개만 범위 안 | 틀림 |

범위는 조건의 모든 시행에 걸친 범위다.

## 한계

- 재현 조건은 5회씩이다. 이번에는 실행된 fetch가 나오지 않아 "실행된 fetch만 거절" 쪽은 3.8.0에서 시험되지 않았다.
- 기능을 끈 이식 빌드가 느린 원인을 확인하지 않았다.
- 소켓 끊김 조건은 뺐다. PE 2개, 노드당 GPU 1개, RC QP만 쟀다.
