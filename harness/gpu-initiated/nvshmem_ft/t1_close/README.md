# t1_close: NVSHMEM 투명 복구 마무리

NVSHMEM IBGDA 투명 복구(QP 오류를 라이브러리 안에서 고쳐 앱 커널이 오류를 보지 않게 하는 기능)의 남은 항목 일부를
고치고, 측정 전에 고정한 예측으로 쟀다(태그 `prereg/nvshmem-t1-close-v1`).

## 무엇을 쟀나

- **고친 것:** 복구 1회가 느려진 회귀(복사 대기 방식), 응답 쪽 실행 수로 fetch를 다시 보낼지 정하는 규칙, finalize 없이
  끝날 때의 정리, 상대당 QP 4개일 때 기록 버퍼 넘침.
- **잰 것:** 조건 25개, 200회. 새 조건 8개(10회씩), 재현 조건 12개(5회씩, 지연은 40회), 대조 4개(5회씩).
- **조건:** rain(시작)과 sunny(대상), ConnectX-6, devel `7bb2e99c` 위 투명 복구 diff, GPU 처리 방식.

## 결론

- **실행 여부로 fetch를 가르는 규칙이 동작했다.**
  - 응답 쪽이 실행하지 않은 fetch는 다시 보내 투명하게 끝났다. 값과 상대 카운터가 정확했다.
  - 이미 실행된 fetch가 있을 때만 거절했다. 세 번 모두 상대 카운터가 한 개 더 많았다.
  - 이 거절을 끄고 다시 보내게 하면 실제로 두 번 적용됐다.
  - 오류 전파 규칙 5("실행 여부를 모르면 다시 보내지 말라")를 강제가 아닌 자연 발생 장애로 처음 확인했다.
- **리뷰에서 못 돌린 경우가 모두 동작했다.**
  - finalize 없이 끝나도 helper가 2.2 ms 안에 정리됐다.
  - 받는 방향만 끊긴 소켓도 다시 이어 투명했다.
  - 상대당 QP 4개도 라운드 하나로 복구했다.
- **예측이 틀린 것이 둘이다.**
  - 복구 시간: 복사 단계는 예전 값으로 돌아왔지만 handshake가 남아 중앙값 5.79 ms였다(예측 5.5 ms 이하).
  - 꽉 찬 GPU: 연결 수를 32로 늘려도 helper 복사가 멈춰 모두 거절됐다. 하드웨어 작업 큐 공유 가설은 지지되지 않았다.
- **회귀는 없었다.** 재현 조건 12개와 장애 없는 지연이 모두 예측 범위 안이었다.

## 결과

| 조건 | 결과 | 예측 |
|---|---|---|
| 로컬 QP 오류, 복구 시간 | 10/10 투명, 중앙값 5.79 ms(4.31–6.93) | 틀림 |
| 같은 조건, 옛 대기 방식 | 5/5 투명, 중앙값 8.04 ms | 맞음 |
| 상대 QP 오류 + 매 반복 fetch | 10/10 투명, fetch 1000개 정확 | 맞음 |
| 연산 사이 로컬 QP 오류 + 매 반복 fetch | 10/10 투명 | 맞음 |
| 작업 중 로컬 QP 오류 + fetch | 7회 투명, 3회 거절(실행된 fetch가 있던 시행만) | 맞음 |
| 실행되지 않은 fetch를 다시 보낸 시행(위 세 조건) | 27/27 투명, 값과 상대 카운터 정확 | - |
| 실행된 fetch도 다시 보냄(음성 대조) | 실행된 fetch가 있던 2회 모두 두 번 적용 | 맞음 |
| 받는 방향만 끊긴 소켓 뒤 로컬 QP 오류 | 10/10 투명 | 맞음 |
| finalize 없는 종료 | 10/10 rc 0, 종료 뒤 2.16–2.28 ms에 정리 | 맞음 |
| 상대당 QP 4개 | 10/10 투명, 라운드마다 QP 4개, 14.5–18.4 ms | 맞음 |
| 꽉 찬 GPU, 연결 32개 | 0/10 투명, 10/10 거절 | 틀림 |
| 재현 조건 12개, 지연 | 모두 예측대로. 투명 켬 4 KiB +2.21 µs | 맞음 |

범위는 조건의 모든 시행(또는 라운드)에 걸친 범위다.

## 한계

- PE 2개, 노드당 GPU 1개, RC QP만 쟀다. DCI 경로와 주소 끊김은 재지 않았다.
- 소켓 끊김은 이 실험 포트에만 건 차단이라 실제로는 약 3.5 s였다.
- 복구 시간이 시행 순서에 따라 갈린 원인과, 꽉 찬 GPU에서 복사가 멈추는 원인을 모른다.
- devel `7bb2e99c` 기반이다. 공식 3.8.0으로는 이후 따로 옮겨 쟀다.
