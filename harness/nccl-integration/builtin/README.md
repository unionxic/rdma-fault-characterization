# builtin: NCCL 내장 복원력과 다중 요청 복구

NCCL은 2.29.7에서 IB 전송에 port failover를, 2.30.3에서 port recovery를 넣었다. 이 기능이 노드마다 RoCE 포트가 하나인 이 테스트베드에서
무엇을 하는지 쟀다. 같은 장애를 같은 날, 같은 실행기로 이 저장소의 다중 요청 복구(NCCL 2.23.4)에도 넣어 나란히 비교했다. 판정은 측정 전에
고정한 예측 27개로 했다.

## 무엇을 쟀나

- **구성:** rain과 sunny, ConnectX-6 RoCE v2 직결, 노드마다 GPU 하나와 활성 포트 하나, IB 타임아웃 14. 2 rank all-reduce와 방송을 돌리고 매
  반복 두 rank의 결과 버퍼 전체를 bit 단위로 검사했다.
- **라이브러리와 설정:**
  - NCCL 2.32.3에 장애 주입 훅만 더한 빌드(복구 코드 없음). 설정은 복원력 끔, port recovery 변수만 켬, port failover 켬, failover와
    recovery 켬 네 가지다.
  - 다중 요청 복구 빌드(NCCL 2.23.4). 복구를 켜고 끈 두 가지다.
- **장애:**
  - 송신 QP를 ERR로, 수신 QP를 ERR로.
  - 받는 중 상대 프로세스를 SIGKILL.
  - 수신 QP를 상대에게 알리지 않고 ERR로(64 MiB 방송, 256 KiB all-reduce).
  - 장애 없는 all-reduce 시간(64 KiB, 16 MiB)도 쟀다.
- **횟수:** 장애 시행 195회, 장애 없는 실행 100회. 2.32.3의 새 조건은 조건마다 10회, 나머지는 5회다. 링크, 주소, 드라이버는 건드리지 않았다.

## 결론

- **포트가 하나면 NCCL의 내장 복원력은 아무 장애도 막지 못한다.**
  - 첫 오류 CQE에서 "남은 장치 없음"으로 바로 치명 판정했다. 앱은 복원력을 끈 것과 같은 ncclRemoteError를 받았다.
  - 다른 장치로 넘기기, 확인 읽기, port recovery는 295회 동안 한 번도 시작되지 않았다.
  - port recovery 변수만 켜면 아무것도 바뀌지 않는다. failover를 함께 켜야 쓰인다.
- **다중 요청 복구는 같은 장애에서 작업을 살렸다.**
  - 송신, 수신 QP 오류를 약 2.2–2.3 ms에 앱 모르게 복구했다.
  - 받는 중 상대가 죽으면 관리망 소켓의 FIN을 보고 약 50 ms 만에 오류를 올렸다. NCCL은 2.23.4든 2.32.3이든 그 죽음을 12 s 시간 제한까지
    보지 못했다.
- **NCCL 2.23.4의 오류 경로는 장애를 틀린 결과로 바꿨다.**
  - 한 rank의 수신 QP가 고장 나 그 rank가 abort하자, 상대 rank는 그 all-reduce를 오류 없이 마쳤다. 결과의 1/8이 틀렸다(5/5).
  - 2.23.4는 오류 뒤에도 진행 스레드가 돌고, abort한 커널이 덜 만든 데이터를 내보낸다.
  - 2.32.3은 첫 오류에서 진행 스레드를 멈춘다. 같은 장애에서 틀린 결과가 없었다(30/30).
- **abort도 달라졌다.** 2.32.3의 `ncclCommAbort`는 오류 뒤 약 0.5 s에 모두 돌아왔고, 2.23.4는 한 번도 돌아오지 않았다.
- **2.32.3에서는 알리지 않은 수신 QP 오류도 조용하지 않다.** 장애를 낸 rank가 자기 수신이 비워진 것을 보고 바로 오류를 올렸다.
- **장애가 없을 때의 비용.**
  - failover는 16 MiB에서 차이가 없고 64 KiB에서 +1.7 %였다. recovery는 비용을 더하지 않았다.
  - 다중 요청 복구는 16 MiB에서 +0.1 %였다. 64 KiB에서는 +3.75 %로 미리 정한 3 %를 넘었다. 다만 실행 사이 흩어짐이 그만큼 커서 64 KiB
    비용은 가르지 못했다.
- 예측 27개 중 26개가 맞았다. 틀린 하나는 다중 요청 복구의 64 KiB 비용이다.

## 결과

| 장애 | NCCL 2.32.3(끔, failover, failover와 recovery) | 다중 요청 복구 켬 | 다중 요청 복구 끔(원본 2.23.4 경로) |
|---|---|---|---|
| 송신 QP 오류 | 장애 낸 rank가 0.03–0.10 ms에 오류. failover는 치명 판정 줄을 남김(35/35) | 투명 복구 5/5, 2.27–2.48 ms | 0.05–0.10 ms에 오류 5/5 |
| 수신 QP 오류 | 장애 낸 rank가 0.03–0.15 ms에 오류, 상대는 3.5–3.8 s 뒤 재시도 초과로 오류(30/30) | 투명 복구 5/5, 2.17–2.39 ms | 장애 낸 rank는 오류, 상대는 632–650 ms에 오류 없이 틀린 결과(5/5) |
| 받는 중 상대 SIGKILL | 12 s 시간 제한까지 오류 없음(30/30) | kill 요청 뒤 0.30–0.31 s에 오류(5/5) | 시간 제한까지 오류 없음(5/5) |
| 수신 QP를 알리지 않고 ERR | 장애 낸 rank 자신이 0.05–0.21 ms에 오류(60/60) | 방송은 투명 복구 5/5, all-reduce는 시간 제한까지 멈춤 5/5 | 재지 않음(그 빌드의 훅은 복구를 켰을 때만 걸린다) |
| 장애 없는 all-reduce 시간 차이(16 MiB, 64 KiB) | failover 대 끔 −0.15 %, +1.73 %. recovery를 더한 차이 −0.07 %, −1.70 % | 끔 대비 +0.13 %, +3.75 % | 비교 기준 |

- 시각은 장애에서 앱 오류까지다. 2.32.3 열의 범위는 설정 셋의 모든 시행을 합친 범위이고, 나머지 열은 그 조건의 모든 시행에 걸친 범위다.
  kill 시각에는 kill을 보낸 ssh 왕복(약 0.25 s)이 들어 있다.
- 비용은 실행 10회 중앙값의 차이다. 제외한 시행은 없다.

## 한계

- 노드마다 활성 포트가 하나라 failover와 recovery가 실제로 동작할 경로가 열리지 않았다. 장치가 둘일 때는 재지 않았다. rain의 두 번째
  포트를 켜는 것은 링크를 바꾸는 일이라 클러스터 규칙상 하지 않았다.
- port recovery를 실제 포트 이벤트(link down, flap)로 시험하지 않았다. 장애는 소프트웨어로 QP를 ERR로 옮긴 것과 SIGKILL뿐이다.
- 1 ms보다 짧은 시각에는 로그를 받는 파이프와 ssh 지연이 들어 있다. 그래서 설정끼리 비교하지 않는다.
- 64 KiB 비용 차이는 실행 사이 흩어짐(4.8–18 %) 안에 있다.
- 장애를 내지 않은 rank는 실행기가 6 s 뒤에 끝냈다. 그 뒤의 일은 보지 않았다.
- 2.32.3과 2.23.4의 비교는 NCCL 버전과 복구 코드가 함께 다르다. 2 rank, 노드 한 쌍이다.
