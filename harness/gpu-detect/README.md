# gpu-detect: GPU 주도 라이브러리의 장애 감지를 application 호출 밖으로

GPU가 직접 통신하는 두 라이브러리(NCCL GIN, NVSHMEM)는 application이 완료를 확인하는 호출 안에서만 장애를 감지했다. 그래서 수정하지 않은 공식
예제가 신호만 기다리는 동안 생긴 장애에 멈췄다(blind-apps). 두 라이브러리에 호출 밖의 감지를 더하고, 같은 예제에서 측정 전에 고정한 예측 41개로
쟀다.

## 무엇을 쟀나

- **바꾼 것.**
  - GIN: 복구 스레드가 복구 중이 아닐 때 주기마다(기본 10 ms) 자기 QP의 상태를 NIC 펌웨어에 묻는다. 오류 상태인 QP를 찾으면 장애 기록을 만들어
    보통 복구를 연다.
  - NVSHMEM: 정상 종료하는 프로세스는 라이브러리 연결을 닫기 전에 작별 메시지를 보낸다. 작별 없이 연결이 닫히면 상대가 죽었다고 보고 거절한 뒤
    프로세스를 오류 코드로 끝낸다(fail-stop). 끝내지 않는 정책(release)을 고르면 GPU의 대기를 풀어 준다.
  - 함께 고친 것: 앞 실험 리뷰가 남긴 세 항목, 다음 실험(복원 계층)이 채울 정책 자리 아홉, 복구를 확정한 응답 쪽이 시작 쪽을 잃었을 때의 죽음 판정.
- **조건.** NCCL GIN ring exchange와 NVSHMEM ring-reduce 공식 예제(코드 그대로), 노드 둘, rank 둘. 장애는 QP 오류, 원격 접근 권한 회수, SIGKILL,
  1–8 s 멈춤, 장애 없음이고 시각과 대상은 시드로 뽑았다. 대조는 감시 없는 앞 라이브러리 둘, 같은 라이브러리의 감시 끔, 앞 NVSHMEM 라이브러리다.
  GIN 드라이버(랭크 2개와 4개)로 기존 동작, 함께 고친 것, 장애 없는 지연도 쟀다.
- **잰 것.** 예제 시행 130회, 드라이버 시행과 지연 실행 118회. 다른 에이전트가 채점 코드를 보지 않고 원자료에서 다시 셌다.

## 결론

- **GIN 예제의 QP 오류가 멈추지 않고 복구된다.** 감시를 켜자 무작위 시각의 QP 오류 32회가 모두 application 모르게 복구됐다(감시 주기 1, 10,
  100 ms). 감시 없는 앞 라이브러리는 12회 모두, 같은 라이브러리에서 감시를 끄면 4회 중 3회가 두 rank 모두 아무 줄 없이 멈췄다.
- **감지 시간은 주기만으로 정해지지 않는다.** 10 ms 주기에서 감지 중앙값은 18.6 ms였고 감지 뒤 약 11 ms에 통신이 재개됐다. 오류 상태의 QP에 원인을
  알려 주는 완료 기록이 없으면 감시는 상대의 거절을 50 ms 기다리는데, 이것이 짧은 주기의 감지 시간을 정했다(1 ms 주기에서 중앙값 41 ms). 감지
  시간이 주기를 따른다는 가설은 이 점에서 틀렸다. 장애 없는 지연은 주기 1 ms에서도 바뀌지 않았다.
- **NVSHMEM 예제는 상대가 죽어도 멈추지 않고 오류로 끝난다.** 살아남은 프로세스가 0.5 ms 안에 상대의 죽음을 판정하고 0.1 s 안에 오류 코드로
  끝났다. 원격 접근 회수에서도 두 프로세스가 0.11 s 안에 끝났다. 앞 라이브러리는 같은 장애에 모두 멈췄다.
- **release 정책은 멈춤만 푼다.** 10회 모두 프로세스가 스스로 끝났지만 9회는 결과가 틀렸다. 받지 못한 데이터는 오지 않으므로 application이 거절을
  확인해야 한다.
- **거짓 양성이 없다.** 몇 초 멈춘 프로세스와 장애 없는 실행 30회에서 감지, 거절, 죽음 판정이 하나도 없었다. 정상 종료는 작별 메시지로 구분됐다.
- **기존 동작은 그대로이고 함께 고친 것도 설계대로 동작했다.** 복구를 확정한 응답 쪽이 시작 쪽을 잃어도 이제 다른 생존 rank처럼 2 s 뒤 대기가
  풀린다(앞 계층은 풀리지 않음). 정책 자리는 hold를 요청하거나 rank마다 정책이 달라도 경고 한 줄 뒤 기존 fail-fast와 같았다.
- **측정 전에 고정한 예측 41개가 모두 맞았다.** 감시 끔 대조 1회는 장치가 장애를 넣는 도중에 잡아 빠르게 복구했다(허용한 1회 안).

## 한계

- 원인을 알려 주는 완료 기록이 없으면 감지는 50 ms 기다림에 묶인다. 감시는 자기 쪽 QP 상태만 보므로 상대 쪽만 망가진 장애는 상대의 감지를 기다린다.
- GIN kill에서 살아남은 rank는 오류를 바로 보지만 예제는 끝나지 않았다. 그 원인은 따로 보지 않았다.
- fail-stop은 거절을 스스로 처리하는 application도 끝낸다. release는 데이터를 주지 않는다.
- 정책 자리는 fail-fast에서만 쟀다. hold 정책은 복원 계층이 채운다.
- 노드 한 쌍, rank 둘(드라이버는 넷까지), 셀마다 3–16회이고 셀 안의 대상 rank가 고르지 않다. 장애는 소프트웨어로 주입했고, 연구 빌드에는 시험
  스위치가 있다.
