# 06_recovery: 오류 종류별 복구 비용

오류가 난 QP를 다시 쓰게 만드는 방법 세 가지의 시간을 오류 종류별로 쟀다. QP만 재설정, 자원 전부 재생성, 드라이버 재적재다.
다중 QP에서 다른 QP가 영향을 받는지, 카운터로 재전송 소진을 미리 알 수 있는지도 쟀다.
수치는 옛 클러스터(225 요청 ConnectX-6, 224 응답 ConnectX-5)에서 2026-05-17–18에 쟀다.

## 무엇을 쟀나

- **오류 4가지.**
  - 수신 버퍼 없음(RNR): 응답 쪽이 수신 버퍼를 올리지 않은 채 SEND를 받는다. rnr_retry는 0이다.
  - 원격 접근 오류: 응답 쪽이 MR을 해제한 뒤 요청 쪽이 옛 rkey로 쓴다.
  - 원격 요청 거절: 응답 쪽 MR에 원격 쓰기 권한이 없다.
  - 재전송 소진: 응답 쪽이 자기 QP를 ERR로 바꾼다. retry_cnt는 7이다.
- **방법마다 10회.** 감지, 복구, 복구 뒤 재전송 확인을 따로 쟀다. 드라이버 재적재는 재전송 소진에서만 쟀다.
- **다중 QP.** QP 2개 중 하나에만 재전송 소진을 내고 다른 QP의 처리량을 봤다. 두 QP에 서로 다른 오류를 동시에 내기도 했다(10회).
- **조기 감지.** 재전송 소진 중 NIC 카운터를 polling하다가 오르면 바로 QP를 ERR로 바꾸고 복구했다.

## 결론

- **복구 시간은 오류 종류보다 방법이 정한다.** QP만 재설정은 1.3–2.8 ms, 자원 전부 재생성은 6.9–9.6 ms, 드라이버 재적재는 7.9 s다.
  - 드라이버 재적재는 QP만 재설정의 약 2,845배다.
- **QP만 재설정해도 양쪽이 같이 움직여야 한다.** RESET을 거치면 PSN을 다시 맞춰야 하기 때문이다.
  원격 접근 오류와 요청 거절은 응답 쪽 MR도 다시 등록한다.
- **전체 시간은 감지가 정한다.** NAK 오류는 감지가 245–489 µs라 합계 1.7–1.8 ms다.
  재전송 소진은 복구가 2.8 ms여도 감지가 3.74 s라 합계도 3.74 s다.
- **복구 방법은 오류 코드만으로 정해진다.** 카운터를 읽을 필요가 없다. 카운터 읽기는 약 7.5 ms로 복구보다 느리다.
  - 재전송 소진만 상대가 살아 있는지 TCP로 따로 확인해야 한다. NAK가 왔다면 상대는 살아 있다.
- **QP만 재설정하면 다른 QP는 멈추지 않는다.** 이웃 QP 처리량은 5,885 → 6,036 ops/10 ms로 오차 범위였다.
  자원 전부 재생성은 공유 자원을 지우므로 이웃 QP도 14,995 µs 동안 멈춘다.
- **어느 QP가 어떤 오류인지는 CQE만 안다.** CQE는 10/10 맞혔다. 카운터는 포트 단위 합(+2)만 보였다.
- **카운터를 보면 재전송 소진을 훨씬 일찍 안다.**
  - 적응형 재전송 카운터(roce_adp_retrans)를 보면 감지 16.6 ms, 복구까지 18.4 ms다. 그냥 기다리는 경우(약 3.7 s)보다 약 203배 빠르다.
  - ACK 타임아웃 카운터(local_ack_timeout_err)를 보면 복구까지 1,058 ms다. 느리지만 오탐이 거의 없다.

## 결과

| 오류 (status / vendor_err) | 감지 | QP만 재설정 | 자원 전부 재생성 | 합계 (QP만 재설정) |
|---|--:|--:|--:|--:|
| 수신 버퍼 없음 (13 / 0x87) | 245 µs | 1,416 µs | 7,793 µs | 1,671 µs |
| 원격 접근 오류 (10 / 0x88) | 480 µs | 1,342 µs | 6,878 µs | 1,830 µs |
| 원격 요청 거절 (9 / 0x8a) | 489 µs | 1,310 µs | 6,960 µs | 1,818 µs |
| 재전송 소진 (12 / 0x81) | 3.738 s | 2,773 µs | 9,633 µs | 3.741 s |

값은 [recovery_results_summary.md](recovery_results_summary.md)의 평균이다. 방법마다 10회다.
드라이버 재적재는 재전송 소진에서 복구 7,889,068 µs(7.9 s)였다.

## 한계와 주의

- **원격 접근 오류와 원격 요청 거절은 처음 5회의 감지가 느렸다.** NIC 캐시 예열로 보인다(예: 5.3 ms → 480 µs).
  [docs/experiments/03](../../../docs/experiments/03_recovery.md)은 뒤 5회를 안정값으로 본다.
- **표의 평균 범위가 칸마다 다르다.** 원격 접근 오류와 원격 요청 거절의 감지, 원격 요청 거절의 복구와 합계는 뒤 5회 평균이다.
  나머지는 대체로 10회 평균이다. 레포의 표로 다시 계산하면 몇 칸이 수십–수백 µs 다르다.
  수신 버퍼 없음 표의 합계 열에는 카운터 읽기(약 7.3 ms)가 들어 있어서, 위 합계와 다르다.
- **수신 버퍼 없음은 rnr_retry 0으로 쟀다.** 재전송 없이 바로 소진된다. 새 테스트베드는 6이다.
  예전 기록에는 이 오류의 복구 비교가 재실행 대기로 남아 있다.
- **이웃 QP 정지 시간은 직접 잰 값이 아니다.** 14,995 µs는 복구 시간과 공유 자원 파괴에서 추론했다.
  이웃 QP 처리량 6,036은 장애를 유지한 구간의 값이고, 복구 순간만 따로 잰 창은 없다.
- **적응형 재전송 카운터는 일시적 혼잡에서도 오른다.** 한 번 오른 것으로 장애라 판단하면 오탐이 난다. 문턱값은 정하지 않았다.
- **드라이버 재적재는 옛 클러스터에서만 쟀다.** NIC 전체를 리셋하므로 같은 NIC의 다른 연결도 모두 끊긴다.
- **배수 표기가 문서마다 다르다.** recovery_results_summary.md는 2,847배로 적었다. 계산하면 2,845배다.
- **정의가 새 테스트베드와 다르다.** 여기서 자원 전부 재생성은 PD, CQ, QP, MR을 모두 다시 만든다.
  QP만 재설정은 필요하면 MR 재교환을 포함한다. 새 테스트베드 값(0.8 ms 안팎, `../../../harness/`)과 직접 비교하지 않는다.
