# RDMA 장애 특성화와 복구

RDMA 통신에서 장애가 났을 때 그 정보가 NIC에서 application까지 어디서 남고 어디서 사라지는지에 대한 측정.
남은 정보로 원인을 얼마나 구분할 수 있는지, 언제 application을 고치지 않고 안전하게 복구할 수 있는지에 대한 확인.
대상은 CPU verbs, NCCL, 그리고 GPU가 직접 통신을 시작하는 GPU-initiated RDMA 스택(NVIDIA NCCL GIN, NVSHMEM IBGDA).

GPU-initiated 스택에서는 GPU 커널이 NIC에 직접 요청을 올리므로, 실패한 요청의 오류가 application에 닿지 않고 조용히 멈추거나
틀린 값으로 끝나는 경우가 생김. 이 저장소는 그 지점을 찾아 측정하고, 라이브러리 안에서 고치는 작업의 기록.

## 요약

- **NVIDIA 라이브러리 문제 네 건 발견과 보고.** NVSHMEM의 CPU 프록시가 doorbell record 주소를 잘못 계산해 장애 뒤 application이
  멈추는 문제([NVIDIA/nvshmem#117](https://github.com/NVIDIA/nvshmem/issues/117), NVIDIA 내부 수정 완료), release 빌드가 오류
  완료를 버리는 문제([#120](https://github.com/NVIDIA/nvshmem/issues/120)), NCCL GIN에서 실패한 put이 device 코드에 보이지 않는
  문제([NVIDIA/nccl#2483](https://github.com/NVIDIA/nccl/issues/2483)), 지원하지 않는 설정값을 받아 멈추는
  문제([#2480](https://github.com/NVIDIA/nccl/issues/2480)).
- **장애 전파 규칙 다섯 가지 정리.** 장애 정보가 계층을 올라가며 사라지는 양상을 측정하고, 결과를 보기 전에 세운 예측으로 검증.
- **네 건 모두 release 소스에서 수정.** 실패한 요청이 반환값, 조회, host 경고를 통해 원인과 함께 application에 전달.
- **원인 보존.** 뒤따른 flush가 CQE의 원인을 덮어써도, NIC가 QP context에 보관하는 첫 오류를 읽어 원인 복원.
- **오류 분류의 근거 재정립.** 드라이버가 정의한 CQE syndrome 13개 중 10개 재현, 두 라이브러리가 실제로 낼 수 있는 6개만 분류에 포함.
- **상대 죽음의 조기 판정(NCCL GIN).** 죽은 rank에게 보내던 ring 이웃의 host 오류 스레드가 약 0.5 s에 판정(원본은 약 58 s 정지). 오판 0회.
- **작은 정상 경로 비용.** 원본 대비 NCCL −0.1–+0.7%, NVSHMEM +1–2%.
- **투명 복구는 설계와 측정 뒤 중단.** 실패한 QP를 다시 세워 떠 있던 요청을 이어 보내는 방식을 두 장비 사이 860회로 측정.
  막히는 곳: QP를 두 방향이 같이 씀, 메시지의 첫 PSN을 알 수 없어 여러 패킷 write의 29%가 메시지 중간에서 다시 시작(오류 없는
  데이터 손상), 응답 쪽을 다시 세운 뒤의 atomic은 끝나지 않음. 고칠 수 있는 고장의 몫도 작음(공개된 운영 연구에서 스위치·케이블이
  작업 중단의 8.4%로 상한, 대부분은 죽음 판정이 다루는 프로세스·GPU·장비 고장). 장애 뒤의 길은 원인과 함께 오류 반환 → shrink →
  그 step 재실행.

## 연구 질문

1. 장애가 나면 NIC, 완료 기록(CQE), 라이브러리, API, 호스트 중 어디까지 오류가 전달되는가
2. 남은 정보로 장애 원인을 몇 가지로 구분할 수 있는가
3. 어떤 장애를 application 수정 없이, 데이터를 잃거나 중복하지 않고 복구할 수 있는가

## 작업 방식

- **사전 등록(v1):** 2026-10-06부터 실험마다 가설, 예측, 판정 기준, 반복 수를 측정 전에 고정하고 Git 태그(`prereg/...`)와 해시로 기록.
  사전 등록 실험 24건, 모두 종료. 등록 뒤 바뀐 것은 실험 폴더의 `DEVIATIONS.md`에 날짜와 이유 기록
- **Blind test(v1):** 장애 일정을 무작위로 정해 봉인하고, 정답을 모르는 판정자가 판정을 먼저 커밋한 뒤 개봉
- **검증:** v1은 고정한 판정식을 그대로 적용하는 스크립트로 채점, 채점 코드를 보지 않는 독립 재집계와 코드 리뷰. 틀린 예측도 그대로 보고. v2는 단계마다 독립 코드 검사
- **데이터:** 원시 로그는 GitHub Release(`data-...`), 체크섬은 [`v1/DATA.md`](v1/DATA.md)
- **표시:** v2 기록은 서술마다 `[측정]`, `[추론]`, `[미확인]`을 구분

## 범위와 한계

- **장비:** 노드 한 쌍과 NIC 한 종류(ConnectX-6). mlx5 기반 스택으로 범위 한정
- **장애 종류:** 소프트웨어로 주입한 장애. 케이블이나 펌웨어 결함 같은 물리 장애는 미포함
- **vendor_err:** 드라이버 헤더에 정의가 없어 측정으로 정한 값. 펌웨어 20.43.4100 한 가지에서 측정
- **GPU:** 워크스테이션용 GPU 두 장(Quadro RTX 5000, RTX A4000). NCCL의 rank 4개 구성과 NVSHMEM은 GPU 한 장에 프로세스 둘
- **죽음 판정:** 죽은 rank에게 보내던 ring 이웃만 판정. counter로 기다리는 GPU 대기는 판정으로 풀리지 않음. 스위치가 있는 망의 실제 혼잡에서는 미확인
- **복구:** 투명 복구는 만들지 않음(근거와 측정은 `v2/RECORD.md` 4.3절). 죽은 rank의 교체는 step 재실행 위에서 가능(shrink
  12–18 ms, 그 뒤 grow 328–335 ms; rank 죽음 뒤 한 실행에서 측정, application 상태 복사는 미확인). 같은 번호로 끼워 넣는 제자리
  교체는 범위 밖. 장애는 모두 소프트웨어로 주입(실제 경로 고장은 재시도가 끝난 뒤, 약 47 s 뒤에야 `0x15`)
- **초기 연구:** `v1/experiments/`와 `v1/docs/`는 다른 클러스터에서 한 것이고, 일부 수치는 현재 환경에서 재측정하지 않음
