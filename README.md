# RDMA 장애 특성화와 복구

RDMA 통신에서 장애가 났을 때, 그 정보가 NIC에서 응용까지 어디서 남고 어디서 사라지는지 측정한다. 남은 정보로 원인을
얼마나 구분할 수 있는지, 언제 응용을 고치지 않고 안전하게 복구할 수 있는지도 보인다. 대상은 CPU verbs, NCCL, 그리고 GPU가
직접 통신을 시작하는 GPU-initiated RDMA 스택(NVIDIA NCCL GIN, NVSHMEM IBGDA)이다.

## 요약

- **NVIDIA NVSHMEM 버그를 찾아 보고했다.** NVSHMEM 3.5.x–3.8.0의 CPU 프록시 경로는 NIC에 알리는 doorbell record 주소를 잘못
  계산해, 통신 장애가 나도 오류가 전달되지 않고 응용이 멈춘다. 공식 3.8.0에서 직접 확인해
  [NVIDIA/nvshmem#117](https://github.com/NVIDIA/nvshmem/issues/117)로 보고했고, NVIDIA 내부 조치가 완료됐다.
- **장애 전파를 규칙 다섯 가지로 정리했다.** 장애 정보가 NIC에서 응용까지 올라가며 어디서 사라지는지 측정해 규칙으로 정리했고,
  결과를 보기 전에 세운 예측으로 검증했다.
- **응용을 고치지 않고 라이브러리 안에서 장애를 복구했다.** NCCL GIN과 NVSHMEM에서 장애 난 연결을 다시 세워 응용이 오류 없이
  통신을 이어 가게 했다. 장애 난 연결만 다시 세우도록 바꿔, 장애를 감지한 뒤 복구에 걸리는 시간을 11.4 ms에서 3.0 ms로 줄였다. 복구할 수 없는
  장애는 응용에 오류로 알리고, 죽은 rank를 빼고 통신기를 줄여 이어 가게 했다.

## 연구 질문

1. 장애가 나면 NIC, 완료 기록(CQE), 라이브러리, API, 호스트 중 어디까지 오류가 전달되는가.
2. 남은 정보로 장애 원인을 몇 가지로 구분할 수 있는가.
3. 어떤 장애를 응용 수정 없이, 데이터를 잃거나 중복하지 않고 복구할 수 있는가.

## 주요 결과

| 주제 | 결과 | 폴더 |
|---|---|---|
| 정보가 사라지는 지점 | 장애 정보는 위 계층으로 갈수록 줄어든다. GIN은 NIC에서 구분되던 장애가 대기 API에서는 정상과 구분되지 않고, NVSHMEM은 실패한 쓰기를 성공처럼 반환한다. 받는 쪽은 오류를 전달받지 못한다 | `harness/gpu-initiated/propagation/` |
| 원인 구분 | 오류 코드만으로는 장애 7가지가 5가지로만 구분된다. 상대 프로세스가 살아 있는지 확인하면 6가지로 구분된다. 죽은 상대는 커널이 자원을 지우는 순서에 따라 다른 오류 코드로 보인다 | `harness/`, `harness/teardown_order/` |
| 살아 있는 상대 | 상대가 살아 있어도 QP가 요청을 받을 수 없으면 프로세스가 죽었을 때와 같은 오류가 온다. 탐지기는 제어 연결이 닫히거나 응답이 늦으면 살아 있는 상대를 죽었거나 복구할 수 없다고 판정한다. 오판이 시작되는 정지 시간은 소스의 마감 상수와 측정한 지연으로 미리 맞혔다. NIC의 혼잡 알림 카운터는 혼잡이 아니라 재전송을 센다 | `harness/live_peer/` |
| 완료 계약 | 오류 상태의 NIC는 doorbell record 값까지만 완료를 만든다. 이 규칙으로 NVSHMEM 버그와 여러 스택의 동작을 설명했다 | `harness/gpu-initiated/completion_contract/` |
| 감지 시간 | 재전송이 끝나 오류가 보이기까지 IB 타임아웃 14에서 3.5–3.8 s, 기본값 20에서 58.5–58.8 s 걸린다. 이 시간을 미리 계산하는 모델을 만들었다 | `harness/ack_timeout/` |
| 복구(CPU, NCCL) | CPU verbs는 장애 난 QP만 다시 세워 약 0.8 ms에 복구한다. NCCL은 송신 QP와 수신 QP에 낸 장애를 복구했고 기본 설정에서 중앙값 2.26 ms가 걸렸다. 상대 프로세스가 죽으면 오류로 알렸고, 상대의 수신 QP가 조용히 오류가 되면 대부분 멈췄다. 같은 장애에서 NCCL 2.32.3의 내장 복원력(port failover, port recovery)은 포트가 하나인 이 환경에서 한 번도 동작하지 않았다. NCCL 2.23.4는 복구를 끄면 수신 QP 장애를 틀린 결과로 바꿨다 | `harness/`, `harness/nccl-integration/` |
| 복구(GPU) | GPU에서 원인을 분류해 로컬 QP 오류를 호스트가 아는 시간을 9.4 s에서 약 15 ms로 줄였다. 원본은 실패한 쓰기를 성공으로 보고했다. GIN과 NVSHMEM에서 응용 수정 없이 장애를 복구했고, 장애 난 연결만 다시 세워 감지 뒤 복구 시간을 11.4 ms에서 3.0 ms로 줄였다. 관리망이 끊기거나 한쪽 방향으로만 끊겨도 살아 있는 상대를 죽었다고 보지 않는다. 복구를 거절하면 응용의 대기가 오류로 끝나고, 죽은 rank를 뺀 통신기 줄이기가 약 17 ms에 된다. 랭크 4개에서도 쌍마다 복구했지만, 한 랭크가 죽으면 나머지끼리의 받기도 실패한다. NVSHMEM 복구는 공식 3.8.0에서도 같게 동작했다 | `harness/gpu-initiated/` |

## 작업 방식

- **사전 등록:** 2026-10-06부터 실험마다 가설, 예측, 판정 기준, 반복 수를 측정 전에 고정하고 Git 태그(`prereg/...`)와 해시로 남겼다.
  사전 등록 뒤 바뀐 것은 실험 폴더의 `DEVIATIONS.md`에 날짜와 이유를 적었다. 사전 등록 실험은 17건이고 모두 끝났다. 그 전(2026년 9월)의
  결과는 사전 등록 없이 쟀고, 일부는 이후 사전 등록 실험에서 다시 쟀다.
- **검증:** 채점은 고정한 판정식을 그대로 적용하는 스크립트로 했고, 채점 코드를 보지 않는 독립 재집계와 코드 리뷰를 따로 거쳤다.
  예측이 틀린 경우도 그대로 보고했다.
- **데이터:** 원시 로그는 GitHub Release(`data-...`)에 올리고 체크섬을 [`DATA.md`](DATA.md)에 적었다.
- **도구:** 구현, 실행, 문서 작업에 AI 코딩 도구(Claude Code)를 썼다. 그 작업 규칙이 [`CLAUDE.md`](CLAUDE.md)와 `.claude/`에 있다.
  실험 설계와 판단은 연구자가 정했다. 독립 재집계와 코드 리뷰도 채점 코드를 보지 않는 별도의 AI 에이전트가 했다.
- **기록:** 모든 변경은 브랜치와 PR로 합쳤다. 규칙은 [`docs/GIT_WORKFLOW.md`](docs/GIT_WORKFLOW.md)에 있다.

## 범위와 한계

- **장비:** 노드 한 쌍과 NIC 한 종류(ConnectX-6)에서만 쟀다. 범위를 mlx5 기반 스택으로 한정한다.
- **장애 종류:** 소프트웨어로 주입했다. 실제 link down은 공유 링크라 시험하지 않았다.
- **GPU:** 소비자용 GPU만 썼다. Hopper(SM90)가 필요한 DeepEP는 돌리지 않았다.
- **복구 수정본:** 시험 코드를 뺀 운영 빌드가 있지만 연구용 패치다. 중단 신호가 통신기마다 하나라, 한 상대를 거절하면 건강한 상대와의
  대기도 실패한다. GIN 커널이 도는 동안 응용이 CUDA 호출(커널 첫 적재, 메모리 할당, 스트림 생성)을 하면 복구가 막힌다. 4 rank는 GPU 두 개를 나눠 써서 쟀고, 실제 하드웨어
  장애에서는 재지 않았다.
- **기존 기능:** NCCL 2.29.7 이후의 port failover와 port recovery는 다른 포트가 있어야 동작한다. 노드마다 포트가 하나인 이 환경에서만
  비교했다.
- **초기 연구:** `experiments/`와 `docs/`의 내용은 다른 클러스터에서 한 것이고, 일부 수치는 이 실험 환경에서 다시 재지 않았다.
