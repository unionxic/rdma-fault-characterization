# RDMA 장애 특성화와 복구

RDMA 통신에서 장애가 났을 때, 그 정보가 NIC에서 응용까지 어디서 남고 어디서 사라지는지 측정한다. 남은 정보로 원인을
얼마나 구분할 수 있는지, 언제 응용을 고치지 않고 안전하게 복구할 수 있는지도 보인다. 대상은 CPU verbs, NCCL, 그리고 GPU가
직접 통신을 시작하는 GPU-initiated RDMA 스택(NVIDIA NCCL GIN, NVSHMEM IBGDA)이다. 아주대학교 소프트웨어학과 학부
자기주도연구로 2026년 9–10월에 진행했다.

## 요약

- **NVIDIA NVSHMEM 버그를 찾아 보고했고, NVIDIA가 수정했다.** NVSHMEM 3.5.x–3.8.0의 CPU 프록시 경로는 NIC에 알리는
  doorbell record 주소를 잘못 계산해, 통신 장애가 나도 오류 완료가 생기지 않고 응용이 멈춘다. 공식 3.8.0의 완료 큐를 직접 읽어
  확인했고(오류 완료 0/5, 고치면 5/5), [NVIDIA/nvshmem#117](https://github.com/NVIDIA/nvshmem/issues/117)로 보고했다. NVIDIA는 하루
  만에 내부에서 고치고 이슈를 닫았다.
- **장애 전파를 설명하는 규칙 5가지를 세우고, 결과를 보기 전에 예측해 검증했다.** 325회 캠페인에서 계층별 원인 구분 예측이 20개 중
  19개 맞았다. 스택 14개는 소스 코드만 보고 결과 방향을 예측해, 잴 수 있는 7개 조건(55회)에서 모두 맞혔다([`MODEL.md`](MODEL.md)).
- **응용 수정 없이 라이브러리 안에서 장애를 복구했다.** GIN 투명 복구 95/95. 장애 난 QP 쌍만 다시 세워 복구 시간을 11.4 ms에서
  3.0 ms로 줄였고, 그동안 다른 통신은 멈추지 않았다. NVSHMEM은 실행되지 않은 작업만 다시 보내 중복 없이 복구했다(27/27).
- **살아 있는 상대를 죽었다고 잘못 판정하는 조건을 처음으로 쟀다(125회).** 데이터 경로는 프로세스 생존을 모르고, 탐지기는 제어
  연결과 응답 시간만 본다.

## 연구 질문

1. 장애가 나면 NIC, 완료 기록(CQE), 라이브러리, API, 호스트 중 어디까지 오류가 전달되는가.
2. 남은 정보로 장애 원인을 몇 가지로 구분할 수 있는가.
3. 어떤 장애를 응용 수정 없이, 데이터를 잃거나 중복하지 않고 복구할 수 있는가.

## 주요 결과

| 주제 | 결과 | 근거 |
|---|---|---|
| 정보가 사라지는 지점 | 위 계층으로 갈수록 줄기만 한다. GIN은 NIC에서 네 묶음으로 갈리던 장애가 blocking 대기에서는 정상과 구분되지 않고, NVSHMEM은 실패한 put을 성공처럼 반환한다. 받는 쪽은 오류 통지를 한 번도 받지 못했다 | `harness/gpu-initiated/propagation/` |
| 원인 구분 | 오류 코드만으로는 장애 7가지가 5묶음으로 갈린다. 상대 생존 확인을 더하면 6묶음이다. 죽은 상대는 커널이 자원을 지우는 순서에 따라 다른 코드로 보인다 | `harness/`, `harness/teardown_order/` |
| 오판 | 살아 있어도 QP가 받을 수 없으면 kill과 같은 오류가 온다(55/55). 제어 연결이 닫히면 "죽음"(10/10), 마감보다 오래 멈추면 "복구 불가"(20/20)로 판정됐다. 혼잡 알림 카운터는 혼잡이 아니라 재전송을 센다 | `harness/live_peer/` |
| 완료 계약 | 오류 상태의 NIC는 doorbell record 값까지만 완료를 만든다. 이 한 가지로 NVSHMEM 버그와 14개 스택의 결과 방향을 설명했다 | `harness/gpu-initiated/completion_contract/` |
| 감지 시간 | 재전송 소진은 IB 타임아웃 14에서 3.5–3.8 s, 기본값 20에서 58.5–58.8 s다. 예측 모델이 처음 보는 설정 55회 중 52회를 1.5 ms 안으로 맞혔다 | `harness/ack_timeout/` |
| 복구(CPU, NCCL) | CPU verbs는 해당 QP만 재설정해 약 0.8 ms에 복구한다. NCCL은 30/30 복구, 중앙값 2.26 ms다 | `harness/`, `harness/nccl-integration/` |
| 복구(GPU) | 장치 쪽 원인 분류로 호스트가 오류를 아는 시간이 9.4 s에서 1 ms 미만이 됐다. GIN 투명 복구 95/95, 받는 쪽 대기 해제 20/20, 관리망 재연결 20/20, QP 쌍만 재설정으로 복구 시간 약 4분의 1. NVSHMEM 투명 복구는 공식 3.8.0에서도 같게 동작했다(15/15) | `harness/gpu-initiated/` |

## 작업 방식

- **사전 등록:** 실험마다 가설, 예측, 판정 기준, 반복 수를 측정 전에 고정하고 Git 태그(`prereg/...`)와 해시로 남겼다. 사전 등록 뒤
  바뀐 것은 실험 폴더의 `DEVIATIONS.md`에 날짜와 이유를 적었다. 사전 등록 실험은 12건이다.
- **검증:** 채점은 고정한 판정식을 그대로 적용하는 스크립트로 했고, 채점 코드를 보지 않는 독립 재집계와 코드 리뷰를 따로 거쳤다.
  예측이 틀린 경우도 그대로 보고했다.
- **데이터:** 원시 로그는 GitHub Release(`data-...`)에 올리고 체크섬을 [`DATA.md`](DATA.md)에 적었다.
- **도구:** 구현, 실행, 문서 작업에 AI 코딩 도구(Claude Code)를 썼다. 그 작업 규칙이 [`CLAUDE.md`](CLAUDE.md)와 `.claude/`에 있다.
  실험 설계와 판단은 연구자가 정했고, AI가 만든 결과는 위의 사전 등록과 독립 재집계로 검증했다.
- **기록:** 모든 변경은 브랜치와 PR로 합쳤다. 규칙은 [`docs/GIT_WORKFLOW.md`](docs/GIT_WORKFLOW.md)에 있다.

## 진행 중

- 장애 난 QP 쌍만 재설정할 때 응답 쪽도 자기 QP를 확인하게 하기, 오판이 시작되는 경계 재기, 관리망이 한쪽 방향으로만 끊길 때의
  오판 고치기.
- NVIDIA의 #117 수정이 공개되면 그 릴리스로 다시 재기.

## 범위와 한계

- **장비:** 노드 한 쌍과 NIC 한 종류(ConnectX-6)에서만 쟀다. 범위를 mlx5 기반 스택으로 한정한다.
- **장애 종류:** 소프트웨어로 주입했다. 실제 link down은 공유 링크라 시험하지 않았다.
- **GPU:** 소비자용 GPU만 썼다. Hopper(SM90)가 필요한 DeepEP는 돌리지 않았다.
- **초기 연구:** `experiments/`와 `docs/`의 내용은 다른 클러스터에서 한 것이고, 일부 수치는 이 실험 환경에서 다시 재지 않았다.
